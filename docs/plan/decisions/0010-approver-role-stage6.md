# 0010. approver 역할은 6단계에서 결정

- 날짜: 2026-11-05
- 담당: 6단계 M1(예정), 5단계 WEB3(예정)

## 문제

1단계 API 결정 11은 "2단계 owner만, editor는 5단계 역할 설계에서"라고 미뤘다. 5단계는 editor 승인을 허용하지 않고 owner만 유지하며, 6단계는 `approver` 역할을 새로 제안한다. 역할 이름과 결정 시점이 엇갈려, 지금 역할 enum·마이그레이션을 만들지 정해야 한다.

## 선택지

1. 5단계에서 approver를 도입한다.
2. 5단계는 owner만 유지하고, approver 도입 여부·위임 범위는 6단계에서 정한다.
3. approver 없이 owner만 영구 유지한다.

## 채택

2번. **5단계는 owner만**이고 editor는 승인할 수 없다. **approver 역할의 도입 여부·위임 범위는 6단계 M1에서 결정**한다. 지금은 역할 enum·마이그레이션·화면을 만들지 않는다.

## 이유

- 다중 사용자·초대·위임은 6단계 범위이고, 5단계는 로그인과 단일 owner 중심이다.
- 1단계 API 결정 11을 지금 바꾸지 않고, 6단계에서 "owner+approver, 승인·reopen만" 같은 확장을 결정 기록으로 남기게 한다.
- 역할을 미리 만들면 5단계 권한 매트릭스와 시험이 확정되지 않은 규칙을 떠안는다.

## 영향

- `stage-1-api.md:42`(2단계 owner만)와 `stage-5.md` 2.1(editor 승인 불가)을 유지한다.
- 6단계 M1이 approver 도입 시 API 결정 11 확장을 결정 기록으로 남기고, `stage.approve`·`stage.reopen` 범위와 `edition.complete`·`edition.reopen_completion`은 owner만이라는 경계를 정한다.
- WebMCP·에이전트 토큰은 계속 승인할 수 없다.

## 재검토 조건

- 6단계 M1 착수 시(기본 재검토 시점).
- 5단계에서 다중 사용자·승인 위임 요구가 먼저 생길 때.
