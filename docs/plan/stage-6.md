## 1. 목표

**PES를 한 사람·한 에이전트·한 방향 화면에서, 여러 에이전트와 여러 사람이 같은 연구 기록을 안전하게 나눠 쓰는 도구로 넓힌다.** 6단계가 끝나면 다음이 참이어야 한다.

1. **2단계에서 붙인 Codex CLI·OpenCode TUI**가 Claude Code와 **같은 PES API/MCP·같은 자격 체계·같은 오류 의미**로 작업하고, 6단계는 이 어댑터를 회귀한다. 추가 에이전트는 후보·계약 시험만 한다. 어느 에이전트도 `project.json`·DB를 직접 쓰지 않는다.
2. owner/editor/reader가 한 프로젝트에서 역할별로 일하고, 같은 글을 동시에 고쳐도 **덮어쓰기 없이 새 버전·충돌 표시**로 남는다. **approver 역할의 도입 여부와 도입 시 위임 범위는 M1에서 결정**(0010)하며, 도입하면 승인은 owner 또는 허가된 approver 사람만 하고 감사 가능하다. 도입하지 않으면 5단계처럼 owner만 승인한다.
3. Linear에는 **사람이 '할 일로'에서 고른 항목**만(제목+사람이 쓴 요약, UI 결정 11·F12, 연구 내용 자동 포함 없음), Notion에는 **사람이 고른 보고서 버전 사본**만 한 방향으로 보낸다. 전송 전 상관키·영수증·payload hash·시도·목적지 ID가 남고, 응답 유실은 `unknown`으로 남기며 왕복 동기화는 하지 않는다.
4. 한 프로젝트의 **채택 책임자(에이전트 lease) 하나**를 유지한다. 이 제한은 에이전트의 결과 채택에만 걸리고 사람의 답·첨언·허가된 직접 편집을 막지 않는다. 여러 worker는 서로 다른 대상에 동시에 제안하고, 채택은 충돌 없이 직렬화된다.
5. hc-team은 이미 0단계부터 PES 개발에 쓰이고 있다. 6단계에서는 지금까지의 운영 결과(주기·테스트·리뷰 지적·사람 재작업)를 평가하고, 적용 범위·제외 경계·중단 기준을 문서로 갱신한다. Codex·OpenCode TUI는 2단계 PR20b로 옮겼으므로 6단계 hc-team 평가 대상으로 고정하지 않는다.
6. 마지막으로 미뤄 둔 **hwpx 변환**을 실제 Windows 한글 환경에서 확인한다. 표·그림·각주·긴 한글이 깨지지 않고, 실패하면 조용히 다른 형식으로 대체하지 않고 실패를 기록한다. 변환은 어느 런타임에서도 부를 수 있는 로컬 명령으로 감싸는 것을 우선한다.

**하지 않는 것**: 실시간 공동 편집(CRDT/OT), Linear·Notion 양방향 동기화, 조직 SSO/SCIM, 공개 API·웹훅, 모바일 앱·오프라인, 다중 테넌트 과금, 5단계 WEB10의 **350 MB 안전 정지·유료 전환 검토 신호와 500 MB 하드 캡**을 넘어서는 추가 운영 확장(프로젝트별 D1 분리 등). 6단계는 5단계의 안전 정지·하드 캡 계약을 승계하고, 프로젝트별 분리 같은 추가 확장은 후속 검토·운영 백로그로 넘긴다.

## 2. 주제와 결정

### 2.1 범위·순서·묶음

- **정할 것**: 새 이슈의 순서와 병렬 묶음, 6단계에서 끝낼 것과 운영으로 넘길 것.
- **선택지**: (A) 모두 병렬, (B) **계약·권한·영수증 기반 → 동시 편집·어댑터 → 교차 시험·hc-team → 통합·문서 → hwpx 최종**, (C) hwpx부터.
- **판단 기준**: 선행 의존, 외부 전송의 되돌리기 어려움, 동시성 위험, hwpx의 수동 검증 시간, Linear 예산.
- **추천**: **B**. 6단계 신규는 `E1~E2`(내보내기), `M1~M3`(사람·worker 동시성), `G3`(2단계 어댑터 회귀·추가 에이전트 후보), `H1`(hc-team 운영 평가), `X1~X2`(hwpx·통합) **9개**다. **Codex CLI·OpenCode TUI는 2026-11-05 사용자 결정으로 2단계 PR20b로 옮겼고, 6단계 G1·G2는 제거한다.** 누적은 `roadmap.md` 2절 참고.
- **필수 DAG**: `M1 → M2`, `E1 → E2`, `M1·M3·E2 → G3`, `PR20b·21 → G3`, `X2`는 E1·E2·M1~M3·G3·H1 뒤, `X1`은 X2 뒤다. **E2는 G3을 기다리지 않는다.** H1은 시작 조건(hc-team 스킬 버전·권한·CI 확인)과 완료 조건(평가 보고서·규칙 갱신 PR 병합)을 분리해, H1 완료가 G3 착수를 막지 않게 한다.
- **권장 일정**: B0 `M1 ∥ M3 ∥ E1` → B1 `M2 ∥ E2` → B2 `G3` → B3 `X2` → B4 `X1`. H1은 B0~B2에 걸친 운영·문서 작업이다. hwpx를 맨 마지막에 두는 것은 브리프의 유예 결정(`00-brief.md:45`)을 그대로 따르는 것이다.

### 2.2 다른 에이전트 — 2단계 이관과 6단계 후보

- **이미 정해진 것**: 2026-11-05 사용자 결정으로 **Codex CLI·OpenCode TUI 어댑터는 2단계 PR20b**가 맡는다. Claude Code·Claude 앱 보장은 그대로다. 6단계의 G1·G2는 제거한다.
- **정할 것**: 6단계에서 추가 에이전트(Gemini 등)를 실제로 붙일지, 후보로만 남길지, G3를 2단계 어댑터 회귀에 어떻게 쓸지.
- **선택지**: (A) 6단계에 추가 에이전트를 넣지 않고 G3를 2단계 회귀로만 쓴다, (B) **2단계 어댑터 회귀 + Gemini 등 추가 에이전트는 후보·계약 시험만**, (C) 6단계에 새 에이전트 어댑터를 바로 추가한다.
- **판단 기준**: 2단계에서 이미 붙인 어댑터의 회귀 위험, 새 에이전트의 실제 수요·도구 지원, 코어 분기 금지, 어댑터 노트의 중립성, 6단계 범위 팽창.
- **추천**: **B**. G3는 **2단계 PR20a의 Claude Code·Claude 앱과 PR20b의 Codex CLI·OpenCode TUI 어댑터를 회귀**하고, M1·M3·E2·A 회귀를 교차 검증한다. Gemini 등 추가 에이전트는 **후보·계약 시험만** 두고, 실제 어댑터 이슈는 수요가 확인될 때 별도로 만든다. 2단계 PR20a가 `claude-code`·`claude-app`을 맡고, D4 노트는 `opencode`(A)·`claude-code`·`claude-app`에 PR20b가 `codex`·`opencode-tui`를 더한다(`docs/adapters/`). OpenCode TUI는 사람이 직접 켜는 화면판이며, PES가 서버로 돌리는 방식 A의 OpenCode와 다르다. 승인·reopen·정책·토큰·삭제·외부 export는 어떤 에이전트 도구에도 넣지 않는다.

### 2.3 여러 사람 — 역할·승인·초대

- **정할 것**: **approver를 도입할지, 도입하면 위임 범위를 어디까지 할지(0010)**, editor가 승인할 수 있는지, 소유권 이전·초대·마지막 owner 보호, 같은 질문에 여러 사람이 답할 때의 규칙, 초대된 사람의 외부 AI 경로.
- **선택지**: (A) 5단계처럼 **owner만 승인(approver 미도입)**, (B) **프로젝트 역할 `approver`를 도입하되 승인·reopen에 한정하고 owner는 항상 승인 가능, 정족수는 두지 않음**, (C) editor면 누구나 승인.
- **판단 기준**: 연구 책임의 단일성, 감사, 최소 권한, 마지막 owner 보호, 중요 동작 step-up, 외부 에이전트 배제, 초대된 사람의 자료 경로.
- **추천**: **B(도입할 경우)**. **도입 여부와 위임 범위는 0010에 따라 M1에서 사용자 결정으로 확정**한다. 도입하면 `approver`는 **`stage.approve`·`stage.reopen`에 한정한 권한 확장**이며, `edition.complete`·`edition.reopen_completion`은 owner만 한다. API 6절 동작 표·capabilities·UI 권한 표를 함께 갱신하고, Go 재허용·토큰·삭제·멤버·판 시작은 owner에게 남긴다. 도입하지 않으면 5단계처럼 owner만 유지하고 역할 마이그레이션·권한 확장을 만들지 않는다.
  - **승인 주체**: approver를 도입한 경우 owner 또는 허가된 approver 사람만 `stage.approve`·`stage.reopen`을 할 수 있고, 도입하지 않으면 owner만 한다. 어느 경우든 `edition.complete`·`edition.reopen_completion`은 owner만 한다. `assurance=verified` 값이나 `human_id` 선언만으로 통과시키지 않고, 서버가 현재 멤버·권한·5분 내 재인증·대상 snapshot/rev를 검증한다. 에이전트 토큰·WebMCP는 승인할 수 없다.
  - **소유권 이전**: **5단계 WEB3이 구현하는 원자적 소유권 이전 계약을 재사용**한다. 프로젝트당 owner 최대 1명, `projects.owner_user_id`, 과거 `project_policy_versions.changed_by_user_id` 보존을 위한 FK 마이그레이션·검사·이전 전후 시험은 **WEB3에서 인계**받고, M1은 그 계약을 새로 설계하거나 처음 만들지 않는다. 이력을 새 owner로 덮어쓰지 않는다.
  - **질문 배정**: `questions.intended_actor_id` 재배정에 이력·rev·사건을 남긴다. 배정 뒤 옛 응답자 제출, 배정 변경 전 제출, 미배정·필수 질문, 서로 다른 사람의 동시 제출을 시험하고, 과거 답은 당시 질문/폼·실제 응답자에 보존한다. PR8·U2 계약과 연계한다.
  - **초대와 외부 AI**: 초대 수락 화면에 현재 Go 전송 허용 상태와 연결된 외부 에이전트를 보여 준다. editor가 자기 Claude 앱을 OAuth로 연결하면 프로젝트 자료가 그 사람 계정의 외부 AI로 간다. owner가 프로젝트별로 "멤버의 외부 에이전트 연결 허용"을 켜고 끌 수 있게 하며, 기본은 허용하지 않는다.
  - **초대 정책**: 초대는 owner만, 7일 1회, 기본 reader, 공개 링크 없음. 마지막 owner는 제거할 수 없고 소유권 이전은 owner의 step-up으로만 한다.
  - **검토 순서**: 승인 위임 계약 확정 → 소유권·배정 기록 → 화면·회귀 순으로 검토한다. 구체 설계 뒤 독립 배포·되돌리기가 필요하면 근거와 예산을 갖춰 분할하며, 표별로 쪼개지 않는다.

### 2.4 동시 편집 — 낙관적 버전, 실시간 병합 없음

- **정할 것**: 같은 글을 두 사람이 동시에 고칠 때의 병합 방식, 잠금, 충돌 화면, 승인본 보호.
- **선택지**: (A) 실시간 CRDT/OT, (B) **새 버전 + `base_version_id`/rev 낙관적 동시성, 409 충돌, 사람이 해결**, (C) 문서 전체 잠금.
- **판단 기준**: 덮어쓰기 0, 감사·버전 보존, 한글·Markdown·표, 구현 비용, 4단계의 "실시간 공동 편집 비목표"와의 일관성.
- **추천**: **B**. 모든 편집은 새 버전이고 `based_on_version_id`를 붙인다. 기준 버전이 바뀌면 409와 현재/기대 버전을 보여 주고 자동 병합하지 않는다. **409로 거부된 편집은 로컬 초안·별도 제안으로 보존**하고, 실패한 tx를 성공 버전으로 부분 저장하지 않는다. 사람은 한쪽을 고르거나 새 버전에 다시 적용한다. 승인·게시 스냅숏은 수정하지 않고, 고치려면 새 버전+stale+재승인을 거친다. 직접 편집과 제안 모드는 S4-PR25·S4-U11의 규칙을 그대로 쓰고, 6단계는 다중 사용자 충돌·감사만 더한다. 시험은 두 사람·사람 대 worker·재접속·권한 회수 뒤 편집을 포함한다. "누가 편집 중" 표시는 선택적이며 문서 잠금으로 쓰지 않는다. CRDT/OT는 6단계에 넣지 않는다.

### 2.5 Linear·Notion 한 방향 내보내기

- **정할 것**: 목적지별 보낼 내용, 목적지 상태, 영수증 스키마, 미리보기·자격정보·재시도, 응답 유실, 부분 생성, 왕복 여부.
- **선택지**: (A) 양방향 동기화, (B) **PES가 원본이고 사람이 고른 정확한 버전만 한 방향 전송 + 영속 영수증**, (C) 연구 내용 전체 자동 전송.
- **판단 기준**: 연구 내용 노출 최소화, 중복 생성 방지, unknown을 성공으로 표시하지 않음, 감사, Go 전송 정책과의 분리.
- **추천**: **B**. Linear는 **사람이 '할 일로'에서 고른 항목**을 제목+사람이 쓴 요약으로 보낸다(UI 결정 11·F12, 연구 내용 자동 포함 없음). Notion은 사람이 고른 **보고서 버전 사본**만 보낸다. 여기서 "읽기 전용 사본"은 **PES로 동기화하지 않는 사본**이라는 뜻이며, Notion 편집 권한을 제한한다는 보장은 아니다.
  - **목적지 상태**: 목적지별 **미설정/미지원/활성**을 구분하고, UI의 "할 일로" 기본은 PES 다음 라운드 할 일로 유지한다. 연구 할 일이 자동으로 Linear 이슈가 되지 않아야 한다.
  - **식별자·상관키**: E1 계약에 project_id, 요청자 actor, 정확한 버전/snapshot·파일 manifest, 목적지 계정/워크스페이스·리소스 범위, payload hash, **전송 전에 정한 목적지 상관키**를 명시한다. 외부 ID/URL은 성공 뒤 얻는 결과이므로 상관키를 대체하지 못한다. 같은 키·다른 목적지/payload는 거부하고, 미리보기 승인 뒤 payload나 목적지가 바뀌면 다시 확인한다.
  - **unknown 뒤 재전송**: PES 요청 멱등 ≠ 외부 생성 멱등이다. 목적지별 멱등/상관키 확인 방법을 정하고, **확인할 수 없으면 unknown 유지·자동 재전송 금지**로 쓴다. 사용자의 재전송 요청에도 이미 생성됐을 가능성을 보여 준다. "중복 0"은 확인 가능한 경로·조건에 한정한다.
  - **비동기·부분 성공**: 작업·영수증·사건은 같은 DB tx에 만들고 네트워크는 커밋 뒤 실행한다. **202는 완료가 아닌 영속 접수**이며, 재시작 뒤 operation/시도 조회와 sending 복구가 가능해야 한다. Notion 페이지/블록처럼 여러 요청이면 부분 생성 결과·외부 ID·재개 지점을 보존하고 전체 sent와 구분한다.
  - **Go와 export 분리**: **Go ON은 export 동의가 아니다.** 미리보기에 목적지 계정, 포함/제외, 민감 내용 경고, 비활성 이유를 보여 주고, 저장된 payload 조회와 실제 송신 모두 현재 권한·프로젝트·대상 버전을 검사한다. 권한 회수 뒤 아직 안 나간 작업의 처리도 정한다.
  - **새 표 계약**: `export_jobs`·`export_attempts`에 프로젝트 복합 FK·상태 전이·유일성·불변 기록·멱등/0행 실패·사건/영수증 같은 tx·SQLite/D1 동일 의미를 귀속하고, DDL·`check_ddl.py`를 갱신한다. `outbound_dispatches`(Go 정책 FK)를 재사용하지 않는다. 자격정보는 서버 secret/OS 키체인에만 두고 DB·로그·프롬프트에 넣지 않는다. WebMCP·에이전트 토큰은 export를 실행할 수 없다.
  - **`export_jobs` 상태·전이**: 아래 상태를 계약으로 확정한다. `outbound_dispatches`는 Go 전송 정책·manifest 기록이며 이 표와 다른 표다. 상태 이름이 겹쳐도 같은 표·전이로 취급하지 않는다.

| 상태 | 뜻 | 전이 |
|---|---|---|
| `prepared` | 작업·영수증 생성, 사람 승인 전 | `authorized` 또는 `blocked` |
| `authorized` | 사람 step-up 승인 완료, 전송 전 | `sending` 또는 `blocked` |
| `sending` | 전송 시도 중, 응답 미확정 | `partial`·`sent`·`failed`·`unknown` |
| `partial` | 일부 목적지 객체 생성, 재개 지점 있음 | `sending`(재개)·`sent` |
| `sent` | 전체 성공, 외부 ID 확정 | 종료 |
| `failed` | 명확한 실패, **외부 객체 생성 없음 확인** | 종료(자동 재전송 없음) |
| `unknown` | 응답 유실, 생성 여부 미확인 | 목적지 확인 뒤 `sent`·`partial`·`failed`, 확인 전 자동 재전송 금지 |
| `blocked` | 권한 회수·정책 또는 사람이 보내기 전 취소해 미전송 | 종료(사람 확인, 사유 기록) |

- **취소·승인 증거**: `cancelled`를 별도 상태로 두지 않는다. 보내기 전 사람 취소는 `blocked`(사유 `cancelled_by_human`)로 끝내고, `sending` 중 취소 시도는 성공으로 바꾸지 않고 `unknown`으로 남겨 목적지 확인 뒤 `sent`·`partial`·`failed`로 종결한다. 이미 만들어진 외부 객체는 DB 롤백으로 지우지 않는다. 사람 승인은 actor·시각·대상 payload hash·목적지에 고정하고, 송신 직전 현재 권한·프로젝트·대상 버전을 다시 검사한다(2.5).

### 2.6 다중 worker 동시 채택

- **정할 것**: 한 프로젝트에서 여러 worker가 동시에 낼 때의 채택 권한, child의 자격, 대상 충돌, 현재 버전 갱신, 부모 상태 전파, 인계.
- **선택지**: (A) 여러 worker가 각자 현재 버전을 직접 쓴다(프로젝트당 실행 담당 하나라는 stage-1 결정과 충돌), (B) **한 프로젝트의 채택자(에이전트 lease/fence) 하나 + 여러 child worker의 최소 권한 제안, 채택만 직렬화**, (C) worker 하나만 허용.
- **판단 기준**: stage-1-db 15의 "프로젝트마다 실행 담당 하나" 유지, 유실·덮어쓰기 0, 감사, A/B 동일 의미, 비용.
- **추천**: **B**. `project_leases`의 프로젝트 단위 lease/fence와 "부모 run이 유일한 업무 채택자"(`stage-1-runners.md:57`)를 유지한다. **lease는 에이전트의 결과 채택을 제한하며 사람의 답·첨언·허가된 직접 편집을 막지 않는다.** 사람 편집과 부모 채택이 경쟁하면 같은 rev/기반 검증으로 한쪽을 거부하고 초안·제안을 보존한다.
  - **child 자격**: child는 부모 자격을 상속하지 않는 **최소 권한 제안 통로**를 쓴다(또는 격리된 제안 파일을 부모가 수집). claim·채택·결과 제출·승인 권한은 주지 않는다. child run 행과 `parent_run_id`만으로 권한 분리가 완성되지 않는다.
  - **전파·예산**: 부모 OFF·만료·중단·`waiting_human`·담당 반납은 child의 반출·제출도 중단한다. 재개는 부모의 새 claim·현재 정책·잔여 예산을 확인한다. child·reviewer·재시도·인계가 누적 예산을 초기화하지 않고 unknown 예약을 유지하며, 최대 병렬 수는 측정 뒤 상한을 둔다.
  - **채택 actor·출처**: 채택된 업무 버전의 actor는 부모 run/actor와 `mutation_commits`·`object_versions`가 일치해야 한다. child의 작업/역할/세션·원 제안 hash·모델·근거는 별도 출처로 보존하고, `parent_run_id`만으로 작성자를 증명하지 않는다.
  - **관계 종류**: `parent_run_id`는 worker 자식과 인계 run에 모두 쓰이므로 관계 종류를 구분한다. reviewer는 부모가 lease를 놓은 뒤 별도 run/새 claim으로 독립 판단한다.
  - **채택 단위**: 다른 객체를 한 tx에 채택하는 batch는 전체 롤백한다. 같은 객체에 두 제안이 오면 409로 한쪽만 채택하며 자동 병합하지 않는다. "동시 채택"은 **동시 제안 후 직렬 채택**을 뜻하며, 여러 독립 채택자가 같은 프로젝트를 동시에 쓰는 것은 6단계 범위가 아니다.

### 2.7 hc-team 운영 평가·규칙 갱신

- **정할 것**: 지금까지 hc-team으로 처리한 PES 개발 이슈의 품질·비용·경계, 앞으로의 적용 규칙.
- **사실**: hc-team은 leader·tester·worker·gatekeeper·reviewer가 Linear 이슈를 처리하는 사용자 환경의 스킬이다. PES 개발에는 이미 0단계부터 쓰고 있다 — `ai/SEL-11` PR #2가 병합됐고 `ai/SEL-12~19`가 worktree·PR로 이어졌다. 따라서 "6단계에서 hc-team 파일럿"이라는 전제는 사실과 다르다.
- **추천**: H1을 **파일럿이 아니라 운영 평가·규칙 갱신 문서 PR**로 바꾼다. Codex·OpenCode TUI는 2단계 PR20b로 옮겼으므로 6단계 hc-team 파일럿 대상으로 묶지 않는다.
  - **평가 항목**: 이슈 주기, 테스트·CI 통과, 독립 리뷰 지적, 사람 재작업, worktree 격리, 공개 저장소 자료 경계, 중단·전환 사례.
  - **갱신할 규칙**: 어떤 이슈를 hc-team에 맡기는지, 제외 경계(사람 자격·마이그레이션·외부 자격 변경·보안), 이슈 하나=PR 하나, 사람이 병합, gate 실패·범위 팽창·실자료 유입 시 중단과 일반 개발 전환, 실패 기록.
  - **시작 조건**: hc-team 스킬의 버전·권한·CI 확인. **완료 조건**: 평가 보고서·규칙 갱신 PR 병합. 2단계 PR20b 등 기존 이슈는 평가 대상 중 하나일 수 있지만 완료 조건으로 묶지 않는다. "PR 2개 성공"만을 유일한 종료 조건으로 두지 않는다.
  - **자료 경계**: 실제 사본·토큰·캡처·payload는 저장소 밖에 두고 PR에는 익명 요약만 남긴다.

### 2.8 hwpx 변환 — 마지막 확인

- **정할 것**: 웹 이후 변환을 어디서 실행할지, 어떤 도구·인터페이스를 쓸지, 파생본·등록 증거, 무엇을 통과로 볼지, 실패 시 대체.
- **선택지**: (A) Cloudflare Worker/Container에서 Go 바이너리 실행, (B) **로컬 runner/CLI가 설치된 hwpx-uri를 호출해 `report.hwpx`를 만들고 업로드·등록**, (C) hwpx를 포기하고 docx/PDF만.
- **판단 기준**: 사용자 환경의 `hwpx-uri` 스킬 설명에 "Go 단일 바이너리"가 적혀 있다. 다만 CLI 인자·설치·OS 지원·자동화 인터페이스는 확인되지 않았으므로 **X1 시작 조건에서 확인**한다. 연구 자료 위치, Worker 실행 제한, Windows 한글 재현, 실패를 숨기지 않음, 공개 저장소에 실자료 금지를 함께 본다.
- **추천**: **B**. PES는 변환기를 다시 구현하지 않는다.
  - **실행 경계**: 변환을 스킬 호출이 아니라 **어느 런타임에서도 부를 수 있는 로컬 명령**(바이너리 직접 호출)으로 감싼다. 안 되면 "B(Claude)에서만 hwpx"라는 한계를 적고, A(OpenCode)·Codex 경로의 지원 여부를 표로 남긴다.
  - **파생본**: `report-uri.md`는 승인 원고와 다른 **파생본**으로 보존하고, 기반 보고서 버전·변환기 버전·입력/이미지 hash·출력 hash를 남긴다. 업로드 ready와 보고서 버전 등록을 구분하며, 변환 실패는 정식 산출물로 채택하지 않는다. 재실행은 같은 파일명 덮어쓰기가 아니라 보존/멱등 계약을 따른다. X1이 검증하는 범위가 단계 보고서인지 최종 보고서인지 명시한다.
  - **검증**: 합성 한국어 보고서(표 3개 이상, 그림/이미지, 각주, 긴 제목, 출처 부록)로 자동 구조 검사(zip/XML, 이미지 참조, 스타일·각주 번호)를 하고, Windows 한글에서 표 머리·그림·각주·쪽 나눔을 확인한다. Mac은 가능한 범위에서 같은 파일을 연다. 실패 경로(바이너리 없음, 깨진 md, 누락 이미지, 지원하지 않는 차트)를 함께 본다.
  - **증거 분리**: 합성 자동, Windows 수동, 실자료 허용/미허용, 도구 미설치/실패를 **네 가지 증거로 나눠** 기록한다. 실자료 미허용을 자동 허용으로 간주하지 않는다.
  - **실패 시**: 명시적 오류를 내고 등록하지 않는다. docx/PDF 안내는 "HWPX 미완료"와 구분되는 별도 안내로만 하고, 조용한 대체 성공으로 표시하지 않는다. 사용자가 허용한 실제 보고서 사본 1개로 최종 확인하고 한계를 문서에 남긴다.

### 2.9 경계

- 6단계는 **한 프로젝트의 연구 기록을 안전하게 넓히는 단계**다. 조직 단위 권한·SSO·SCIM, 공개 API·웹훅, 실시간 공동 편집, 모바일 앱·오프라인, 다중 테넌트 과금, Linear·Notion 왕복 동기화는 넣지 않는다. 프로젝트별 D1 분리는 **5단계 WEB10의 완료 조건이 아니라 후속 검토**다. 6단계는 5단계의 **350 MB 안전 정지·유료 전환 검토 신호와 500 MB 하드 캡**을 승계하고, 그 뒤의 추가 운영 확장(프로젝트별 D1 분리·다중 테넌트·조직 단위 격리 등)만 판단한다. 5단계의 안전 정지·하드 캡 계약을 6단계에서 뒤집거나 다른 일정으로 바꾸지 않는다.

## 4. 이 단계 구현 이슈

이슈 하나 = PR 하나. **1단계에서 확정된 번호는 PR1~22(2단계에서 20a·20b로 분할)·U1~U6뿐이다.** PR23~25·U7~U12는 4단계 초안이므로 `S4-PR23`처럼 접두어를 붙이고, 5단계는 `WEB0~14`, 3단계 WebMCP는 `S3-W1`로 쓴다. 6단계는 새로 필요한 것만 `E`(export), `M`(multi-user/multi-worker), `G`(agents), `H`(hc-team), `X`(final)로 붙인다. 표·테이블별 하위 이슈는 만들지 않는다(`stage-1-db.md:33`).
