이미 있는 **SEL-1~31 = 31개**를 기준으로 하고, 2~6단계에서 새로 만드는 구현 이슈를 더한다.

| 기존(재설계 전) | SEL-1~10 | 10 |
| 0단계 구현 | SEL-11~19, SEL-31 | 10 |
| 계획·설계 | SEL-20~30 (이 로드맵 SEL-30 포함) | 11 |

- **Linear 한도 260 대비**: 96개 사용, **164개 여유**. 결함·보안·운영·계획 변경 이슈를 넣을 여유가 충분하다. 이 여유 안에 미리 잡을 예비분: 3단계 U4·U1 분할(+1~2), T1에서 나온 결함 PR, 단계별 결함·보안 PR, **legacy JSON 읽기 경로 제거 정리 PR 1개(조건부)**.
- 구현 이슈만 보면 **75개**(0단계 구현 10 + 2~6단계 65)이고, 계획·기존 이슈는 21개(SEL-1~10 + SEL-20~30)다.
- **세는 규칙**: Linear SEL ID 기준이다. 각 단계 문서의 누적 합계는 쓰지 않고 이 표를 가리킨다.
- 단계 문서들은 "0단계 11 + 계획 11"로 SEL-20을 두 번 세어 1씩 많다. SEL ID 기준 바른 값: 2단계 뒤 54, 3단계 뒤 63, 4단계 뒤 72, 5단계 뒤 87, 6단계 뒤 96.
- **SEL-1~31만 있다는 것은 계획 문서 기준이다.** SEL-32 이후가 이미 있는지는 등록 직전 Linear로 확인한다.

## 3. 단계 사이 의존 관계와 먼저 해 볼 실험

### 3.1 큰 흐름

```text
0단계 게이트(SEL-11~19·31, AGENTS.md)
  └→ 2단계 PR1 → PR4 → (PR5·7·10) → … → PR13·14 → WEB0(5단계 번호, 계약 픽스처 직후) → PR17·18 → PR19·20a·20b → PR21·22
       └→ 3단계 U1 → U2 → U4 → U5/U6 (U3은 U1·PR14 뒤, W1/R1은 조건부, T1은 U1~U6 뒤)
            └→ 4단계 PR23 → PR24, PR25(PR6·U4 뒤, PR23과 독립) → U7~U12
                 └→ 5단계 WEB1 → WEB2·3·4 → WEB5·6·7·8·9 → WEB10·11·12 → WEB13·14
                      └→ 6단계 E1·E2 / M1~M3 / G3 / H1 → X2 → X1
```

- **0→2**: 0단계 게이트 전에는 PR1에 착수하지 않는다. PR1~18은 게이트 뒤 조건부, PR19·20a·20b·21·22는 SEL-18·19 결과 뒤. PR20a는 Claude Code·Claude 앱, PR20b는 Codex CLI·OpenCode TUI이며 20b는 20a의 공통 MCP bridge·계약을 쓴다.
- **2→3**: U1의 기술 선행은 PR14·18이고, 단계 게이트는 "2단계 사용자 승인"이다. U3은 U1·PR14 뒤, U4는 U1·U2 뒤, U5는 U1·U2·U4 뒤, U6은 U1~U4 뒤다. T1은 U1~U6 뒤이며, 사용자가 켠 W1·R1만 조건부 선행으로 둔다.
- **WEB0(번호는 5단계, 실행은 2단계)**: 2단계 PR4·13의 언어 중립 계약 픽스처가 나온 직후로 앞당긴다. 결과가 "TS 이식"이면 그때 2~4단계 구현 언어를 다시 정한다.
- **3→4**: PR23은 PR4·6·7·9·10·14와 U3·U4, PR24는 PR23·14, PR25는 PR4·6·7·9·13·14와 U4를 선행으로 한다. U7은 PR23·17·U1·U3·U4, U8은 PR24·U7·U1, U9는 U3·U4·PR10·14·19·20a·20b, U10은 U3·U4·PR5·6·10·14·19·20a·20b, U11은 PR25·U1·U4, U12는 U1~U4·U6·PR18·21·U5를 선행으로 한다.
- **4→5**: WEB1은 PR1·2·4·13·14·18·U1, WEB2는 WEB1·PR4, WEB5는 WEB2·3·4·PR13·14·20a·20b, WEB6은 WEB4·PR5·19, WEB7은 WEB6·PR19·21·WEB12, WEB9는 WEB1·2·3·PR3·9·11·12·15·16·17을 선행으로 한다.
- **5→6**: M1은 WEB2·3·PR4·10·14·PR8·U2, M3는 PR1·2·4·5·7·9·10·13·21·WEB4·6·7·12, G3은 PR20b·21·M1·M3·E2, E1은 PR4·10·14·WEB2·3·4·11을 선행으로 한다. X2는 E1·E2·M1~M3·G3·H1 뒤, X1은 X2 뒤다.
- **조건부**: W1·R1은 3단계에서 미실시할 수 있고 4단계의 필수 전제가 아니다. T1은 사용자 허용이 있을 때만 4단계 U12 게이트 입력으로 쓴다.

## 6. 계획서끼리 어긋나는 곳(불일치와 정한 규칙)

1. **누적 이슈 집계 — 닫힘.** 각 단계 문서는 누적 수를 `roadmap.md` 2절로 통일했다. SEL ID 기준 2단계 뒤 54, 3단계 뒤 63, 4단계 뒤 72, 5단계 뒤 87, 6단계 뒤 96. 과거 63/72/76/87/97 표기는 폐기한다.
2. **5단계 이슈 수 — 닫힘.** WEB0~WEB14=15개로 통일한다. 6단계 문서의 "5단계 14"는 WEB0이 빠진 계산이었고 제거했다.
3. **번호 규칙을 정한다.** 4단계 문서는 PR23~25·U7~U12를 4단계 신규 번호로 쓰고, 6단계 문서는 `S4-PR23`·`S4-U7`처럼 접두어를 붙였다. Linear 제목은 `[4단계 PR23]`·`[5단계 WEB0]`처럼 단계를 붙이고, 문서 안 교차 참조는 `S4-PR23`·`S3-W1` 접두어를 쓴다. 4단계 문서도 이 규칙을 따른다.
4. **D1 8GB와 5GB/500MB가 충돌한다.** 6단계는 "D1 8GB 도달 전 프로젝트별 DB 분리"라 하고 8GB를 "5단계 초안의 운영 검토 임계값"이라 부르지만, 5단계는 Free 계정 5GB·DB당 500MB·DB 10개를 적고 500MB에 가까울 때 분리를 검토한다. 8GB는 5단계 문서에 없고 Free 계정 상한과도 맞지 않는다. 이 값은 6단계 최종 대조에서 고치는 중이다.
5. **실제 프로젝트 시험이 PR22와 T1 두 곳에 있다.** 결론: PR22는 이전·기존 화면 파일럿(A 실행 없음)이고, T1은 같은 사본(사용자가 허용하면)으로 새 작업 공간 기능을 시험한다. 실제 자료 시험의 결과 기록은 각 단계 게이트가 갖고, 같은 runbook·백업을 재사용한다.
6. **OneDrive·병행 기간 — 닫힘.** DB 결정 2(실행 중 DB 파일 동기화·공유 안 함 → OneDrive 동기화 금지)와 결정 4(전환 뒤 `project.json` 읽기 전용·이중 쓰기 금지 → 병행 기간 없음)로 이미 정해졌다(`stage-1-db.md:19·21`).
7. **승인 역할 이관 — 닫힘, 정상 이관.** API:42는 editor 결정을 5단계로 넘겼고, 5단계가 "editor 승인 불가"로 정했으며, 6단계가 별도 `approver`를 사용자 결정으로 올렸다(`stage-1-api.md:42`, 5단계 2.2, 6단계 6절 2번).
8. **표 수 기준이 54개에서 멈춰 있다.** 1단계 DB·DDL은 54개 표를 기준으로 하고, 4단계는 `edition_carryovers`·`completed_snapshot_id`, 5단계는 로그인·알림·runner 보조 표, 6단계는 `export_jobs`·`export_attempts`를 더한다. **규칙**: 새 표·열을 만드는 PR은 `schemas/stage-1-ddl-draft.sql`(또는 이후 마이그레이션 기준 문서)·`check_ddl.py`·`stage-1-db.md`의 표 수를 함께 갱신한다(4단계 PR23이 이미 이렇게 쓴다). 최종 표 수는 그 기준 문서가 가진다. 1단계 UI의 "새 표 없음"은 3단계 화면 범위라 충돌은 아니지만, 읽는 사람이 전체 기준으로 오해할 수 있다.
