## 1. 목표

**보고서가 끝난 뒤에도 같은 프로젝트를 2판·3판으로 이어 가거나 멈출 수 있게 하고, 갈림길·반대 의견·직접 편집을 연구 기록으로 남긴다.** 1단계에서 정한 판·버전·스냅숏·결정·가정·첨언 구조를 실제 작업 흐름으로 연결하고, 3단계까지 병행하던 기존 화면을 새 작업 공간으로 기본 대체한다.

이 단계가 끝나면 사용자는 다음을 할 수 있어야 한다.

- 완료한 판을 멈추거나, 앞 판의 결정·가정·결과물·출처 중 **일부만 골라** 새 판으로 가져가고 유지/수정/제외를 기록한다.
- 두 판·두 라운드의 차이와 이력을 **버전·근거·사람 단위**로 확인한다.
- 갈림길에서 **방향 2~3개를 짧게 맛보고** 하나를 고른다.
- 근거와 어긋나는 요청에 AI가 **반대 의견**을 내고, 사람이 이유를 남기고 결정한다.
- 글을 **직접 고치거나 제안으로 남기며**, 원문을 덮어쓰지 않는다.
- 기존 화면 대신 **새 작업 공간이 기본**이 되고, 문제가 생기면 이전 화면으로 되돌릴 수 있다.

비목표: 웹 이전·로그인·권한(5단계), 여러 사람·여러 에이전트(6단계), 외부 내보내기(6단계), hwpx 변환(전체 개발 맨 마지막), 완전한 WYSIWYG, 실시간 공동 편집, 자동 판 생성·자동 갈림길 분기, AI 거부권, 영구 삭제.

## 2. 주제와 결정

stage-0 7절과 1단계 설계서의 합의 결정은 **다시 정하지 않는다.** 아래에서 **4단계 제안**이라고 표시한 것은 1단계 합의가 아니라 이 계획서가 새로 정하는 값이다. 특히 판 완료의 주체·조건, 완료 해제 기한, 프로젝트별 opt-in, 실제 프로젝트 1개 확인, 이전 화면 유지 기간은 1단계에서 확정된 세부값이 아니다.

### 2.1 판의 생애 — 시작·완료·멈추기·다시 열기

**이미 정해진 것:** 프로젝트마다 활성 판 하나([stage-1-db.md:22](stage-1-db.md#L22), [DDL:159](schemas/stage-1-ddl-draft.sql#L159)), 판 시작은 소유자 사람만([stage-1-api.md:25](stage-1-api.md#L25)), run `complete`는 승인·봉인이 아님([stage-1-api.md:22](stage-1-api.md#L22)), 전송 허용·실행·답 제출·승인·반영은 다른 사실([stage-1-ui.md:44](stage-1-ui.md#L44)).

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 완료 시점·주체 (4단계 제안) | 여섯 단계 승인 즉시 자동 완료 / 소유자 사람의 "이 판 마침" / 프로젝트 보관 시 완료 | 승인≠완료, 실수 방지, 사후 수정 가능, 감사 | **소유자 사람의 명시적 완료.** 대상 판에 **미종결 run(queued·running·waiting_human) 없음**, 여섯 단계의 **현재** 승인, **stale 없음**, 미처리 필수 응답 없음(명시적 deferred는 사유 확인), 실행 차단 상태 없음이 조건이다. 서버가 명령 시점에 다시 검사하고, 완료는 `editions.status='completed'`·`completed_snapshot_id`·`projects.active_edition_id` 해제·event·영수증을 **한 tx**로 쓴다. 종료된 과거 run은 지우지 않는다. |
| 완료 해제 (4단계 제안) | 불가 / 새 판 전까지 소유자만 / 언제든 | 과거 스냅숏 보존, 새 판과의 충돌 | **새 판이 생기기 전까지 소유자만.** 해제는 완료 스냅숏을 지우지 않고 `completed_snapshot_id` 포인터만 해제하며, 후속 판이 있으면 거부한다. 후속 판이 없으면 `projects.active_edition_id`를 그 판으로 되돌린다. 단계 승인·stale·현재 단계 포인터는 **보존**하고, 이후 편집은 PR 6 규칙(현재 승인 포인터 해제·뒤 단계 stale)을 따른다. 해제도 새 event·새 영수증이다. |
| 다음 판 준비 | 활성 판과 draft 병행 / 완료·보관 뒤에만 / 자동 생성 | 활성 판 하나, lease 범위, 실수 방지 | **완료·보관 뒤에만, 소유자 사람이 시작.** draft 병행은 6단계의 미합의 제안으로 남긴다. |
| 멈추기·보관 | 완료=프로젝트 archived / 완료는 판만, 프로젝트는 active / 삭제 | "이어 가거나 멈춘다"의 의미, 복구 | **완료는 판만, 프로젝트는 active 유지.** `archived`는 완료·미완료 판 모두에 쓸 수 있으나, **미종결 run·lease가 없을 때만** 보관하고, 미완료 보관은 완료로 가장하지 않고 `completed_snapshot_id`를 만들지 않는다. 미완료 보관판에서 다음 판을 시작하면 기준 고정본을 **마지막 봉인 라운드 → 마지막 승인 단계 → 이월 미리보기 시점의 as-of manifest** 순서로 정하고, 어느 것을 썼는지 `edition_carryovers`에 남긴다. |
| 기획부터 다시 | 이월 결과를 승인으로 인정 / 새 판은 plan pending, 이월은 참고 / 이전 승인 복사 | 승인≠이월, 재검토 보장 | **새 판의 첫 단계는 plan이고, 이월 결과를 승인으로 인정하지 않는다.** "기획 유지"를 골라도 plan 승인은 새로 받는다. 이월된 결정·가정·결과물은 입력이고, 여섯 단계 승인은 새로 받는다. |
| 옛 프로젝트의 1판 완료 (Z2) | 이전 승인을 완료로 인정 / 현재 소유자의 명시적 완료 / 완료 불가 | 이전 기록 보존, 실제 사용자, 감사 | **현재 소유자의 명시적 완료.** 2단계에서 이전된 프로젝트의 `legacy_unverified` 승인은 "옛 기록의 승인"으로 인정하되, 완료는 지금 소유자가 새 human actor로 눌러야 한다. 가짜 사람을 만들지 않고, 합성 legacy fixture로 1판 완료→2판 시작을 시험한다. |

### 2.2 새 판으로 넘기기 — 유지·수정·제외

**이미 정해진 것:** 판 범위 결정·가정은 원본 버전을 고정해 새 판에 복사하고 유지/수정/제외를 기록하며, 프로젝트 공통 결정은 참조하되 새 판 기준 스냅숏에 당시 버전을 고정한다. 전송 정책은 판 복사로 바뀌지 않는다([stage-1-db.md:23](stage-1-db.md#L23)). 답은 그때 본 질문 버전에 묶고 새 버전에 자동 승계하지 않는다([stage-1-db.md:24](stage-1-db.md#L24)). 결과물의 재사용은 새 판의 새 객체 + `artifacts.origin_version_id`이며, 결정·후속·가정·출처의 실제 계보는 아래 표를 따른다([stage-1-db.md:76](stage-1-db.md#L76)).

**계보는 종류마다 실제 열이 다르다.** 모든 객체에 같은 `origin_version_id`가 있다고 가정하지 않는다.

| 종류 | 실제 계보 | 이월·비교에서 |
|---|---|---|
| 결과물 | `artifacts.origin_version_id` ([SQL:340](schemas/stage-1-ddl-draft.sql#L340)) | 새 판 새 객체의 원본 버전. `object_versions.based_on_version_id`는 같은 객체 안 버전만 가리킨다([SQL:300](schemas/stage-1-ddl-draft.sql#L300), [SQL:313](schemas/stage-1-ddl-draft.sql#L313)). |
| 결정 | `decisions.originated_from_version_id` ([SQL:614](schemas/stage-1-ddl-draft.sql#L614)) | 새 결정 버전의 원본. |
| 후속 | `followups.origin_version_id` ([SQL:754](schemas/stage-1-ddl-draft.sql#L754)) | 새 판 할 일의 원 후속. |
| 가정 | 전용 계보 열 없음 | `edition_carryovers`의 원본/대상 객체·버전 기록으로 보장한다. |
| 출처 | 전용 계보 열 없음 | `edition_carryovers` + `source_versions`·`citations`로 보장한다. URL만으로 합치지 않는다. |

PR 24는 위 실제 열과 `edition_carryovers`를 함께 조회하고, 없는 열을 있는 것처럼 다루지 않는다.

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 기본 선택 | 전부 이월 / 빈 판 / 선별 이월 | "일부 빼고" 지원, 낡은 결론 방지, 마법사 길이 | **선별 이월 + "전부/빈 판" 단축.** 프로젝트 공통 `adopted` 결정은 선택 대상이 아니라 항상 참조하고 새 판 스냅숏에 버전을 고정한다. 기본 체크: 판 범위 `adopted` 결정(유지), `confirmed` 가정(유지+`needs_review=1`), 승인 단계의 결과물(참고 복사), 그 결과물이 인용한 출처. 기본 제외: 답·질문·승인·단계 상태·열린 라운드·초안·lease/run·전송 정책·토큰·사건·dispatch. 제안·철회·폐기·거절 항목은 보이되 기본 미체크. **유지도 현재 유효성을 새로 확인한 것으로 표시하지 않는다.** |
| 유지·수정·제외의 뜻 | 유지=같은 객체 / 수정=원본 덮어쓰기 / 제외=삭제 | 원본 불변, 감사, 재검토 | **유지**=같은 내용으로 새 객체+원본 계보. **수정**=새 판에 새 버전, 결정은 `proposed`, 가정은 `proposed`+`needs_review=1`; plan에서 다시 채택·확인. **제외**=새 판에 객체 없음, 이유 기록, 대상 객체·버전은 NULL 허용, 옛 판은 그대로. |
| 대상·제외 | 모든 표 / 결정·가정만 / 결정·가정·결과물·출처 | 답·승인 자동 승계 금지, 유용성 | **결정·가정·결과물·출처만.** 답·질문·승인·run·lease·전송 기록은 이월하지 않는다. 열린 `next_round_task` 후속만 "다음 판 할 일로 복사"를 따로 허용한다. |
| 기록 | event payload만 / `version_relations`+event / 새 표 | 항목별 조회·감사, D1 호환 | **신규 `edition_carryovers` 표 + `editions.completed_snapshot_id` 열(PR 23).** 원본 판·원본 객체/버전, 대상 판·대상 객체/버전, 유지/수정/제외, 이유, actor, tx를 남긴다. 같은 대상 판·원본 버전·처리 구분의 중복을 금지하고(제외는 대상 NULL 허용), 프로젝트/판/객체/버전/tx 참조 일치와 완료 스냅숏의 같은 판·`scope='edition'`을 서비스가 검증한다. 별도 번호 마이그레이션으로 기존 DB에서도 시험한다. 새 표·열의 이유는 `docs/plan/decisions/`에 기록한다. |
| 프로젝트 공통 결정 | 복사 / 참조만 / 무시 | 새 판 기준 고정, 나중 변경과의 구분 | **참조 + 새 판 기준 스냅숏의 manifest에 버전 고정.** **원본 프로젝트 결정의 새 버전**과 **판이 보는 참조 기준의 갱신**을 구분한다. 원본이 바뀌면 새 결정 버전이고, 판은 "고정된 버전"과 "최신 공통 결정"을 함께 보여 주며 사람이 명시적으로 갱신할 때만 새 기준 기록을 만든다. 이전 기준 스냅숏은 바꾸지 않는다. |
| 결과물·출처 연결 (B02) | 새 판 객체로 재연결 / 옛 정확한 버전 참조 | 인용·파일 보존, 감사 | **새 판 객체로 재연결하되 정확한 원본 버전을 가리킨다.** `artifact_components`·각주 순서(`citations`)·`version_relations`·`version_files`를 이월 규칙에 포함한다. 사용자가 인용 출처를 제외하면 **경고하고 옛 버전 참조를 남긴다.** 원문·hash·`ready` 파일은 보존하고, URL만으로 합치거나 `retrieved_at`을 새 확인처럼 바꾸지 않는다. |
| `next_round_task` 이월 (B03) | 복사 안 함 / 새 판 할 일로 복사 / 자동 적용 | 대상 단계·라운드, 원 후속 보존 | **새 판 할 일로 복사.** 대상 단계를 매핑하고 첫 라운드 전이면 `round_id=NULL`로 둔다. 원 후속 계보를 남기고 새 상태는 **미적용**, 원 후속은 자동 적용·해결하지 않는다. 새 판 반영 내역에서 구별한다. |

전송 정책은 새 판을 만들어도 복사·초기화하지 않는다. 현재 프로젝트 정책과 Go OFF/ON 이력이 그대로 적용된다([stage-1-db.md:23](stage-1-db.md#L23), [stage-1-api.md:29](stage-1-api.md#L29)). 3단계 UI의 "새 표 없음"은 3단계 화면 범위의 결정이고, 이 표·열은 4단계 DB/API 확장이다.

### 2.3 판·라운드 비교와 이력

**이미 정해진 것:** 채택·저장한 결과 버전과 공유·인쇄본은 모두 보존하고([stage-1-db.md:26](stage-1-db.md#L26)), 라운드·단계·판 스냅숏이 있다([stage-1-db.md:60](stage-1-db.md#L60)). 되돌리기도 새 기록으로 남긴다([notion-linear.md:137](research/notion-linear.md#L137)).

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 비교 단위 | 판만 / 판·라운드 / 판·라운드·단계 | 연구 질문, 스냅숏 존재, 화면 복잡도 | **판↔판과 라운드↔라운드부터.** 단계 비교는 그 둘에서 파생한다. 판은 완료 스냅숏, 라운드는 봉인 스냅숏을 기준으로 하며, **열린 라운드도 비교 범위에 포함**하고 "진행 중(잠정)"으로 표시한다. |
| 비교 방법 | 전문 텍스트 diff / 구조화 요약 / 구조화+상세 diff | 의미, 오탐, 긴 한글·표, 성능 | **구조화 요약 + 같은 계보일 때만 상세 diff.** 결정·가정·결과물·출처·승인 상태를 표로 먼저 보여 주고, 실제 계보(2.2의 열·이월 기록)로 이어진 같은 객체만 텍스트 diff한다. 계보가 없으면 "새 항목/이월 제외"로 표시하고 유사도로 맞추지 않는다. |
| 열린 판 | 현재 읽기 모델 비교 / 비교용 스냅숏 저장 / 완료 판만 | 쓰기 부작용, 잠정 표시, 인쇄와의 구분 | **현재 읽기 모델 + 하나의 사건 경계.** 비교 요청 시작 시 `(database_instance_id, cursor_epoch, event_seq)`를 고정하고 **페이지 사이에 같은 경계를 넘긴다.** epoch가 바뀌거나 커서가 무효면 처음부터 다시 읽고 서로 다른 시점을 섞지 않는다. 비교만을 위해 스냅숏을 만들지 않는다. 인쇄는 기존처럼 출력 시점 고정본을 따로 만든다([stage-1-ui.md:45](stage-1-ui.md#L45)). |
| 이력 | event 원문만 / 사람이 읽는 타임라인 / 새 이력 표 | 감사, 화면 가독성, 중복 저장 | **event+스냅숏으로 타임라인을 계산.** 판 시작·완료·해제, 단계 승인·reopen, 이월, 방향 채택, 반대 의견 해소, 직접 편집을 보여 준다. 토큰 스트림·heartbeat는 넣지 않는다([stage-1-runners.md:71](stage-1-runners.md#L71)). 새 이력 표는 만들지 않는다. |
| 되돌리기 | 현재 판 덮어쓰기 / 새 버전·새 판 / 삭제 | 원본 보존, 감사 | **현재 판을 과거로 덮어쓰지 않는다.** "이 버전에서 새 버전" 또는 "이 판에서 새 판"만 허용하고 모두 새 event·새 버전으로 남긴다. |
| 인쇄 회귀 (B07) | 비교 화면 인쇄 / U6 재사용 | 고정본 보존, 오해 방지 | **U6을 재사용한다.** U7·U8에서 새 판의 정확한 버전·완료본/열린 판을 U6에서 고르고, 모든 판 인쇄는 판별 고정 manifest 묶음으로 재출력한다. 비교 화면을 승인본·고정 인쇄본으로 오인시키지 않는다. |

### 2.4 갈림길에서 방향 2~3개 맛보기

**이미 정해진 것:** 갈림길에서 방향 2~3개를 맛보기로 보여 준다([00-brief.md:27](00-brief.md#L27)). 결정은 프로젝트/판 범위의 살아 있는 기록이다([stage-1-db.md:96](stage-1-db.md#L96)). 판 시작은 사람만 한다([stage-1-api.md:25](stage-1-api.md#L25)).

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 형식 | 방향마다 실제 판·브랜치 생성 / 같은 판의 제안 결정 2~3개 / 대화로만 | 비용, 감사, 상태 분열 방지 | **같은 판의 `proposed` 결정 2~3개.** 각 방향은 결정 후보 버전이고, 채택 전에는 새 판·새 run을 만들지 않는다. 한 묶음은 **묶음 ID·기반 버전·정확한 후보 버전 목록**을 가져야 하며, 하나 채택/나머지 철회는 **원자 명령**이다. 기존 metadata·manifest로 표현 가능한지 먼저 검토하고, 부족할 때만 새 표·열을 제안한다. |
| 개수·분량 | 2개 / 2~3개 / 5개 이상, 초안 전체 | 비교 가능성, 비용, 읽는 시간 | **2~3개, 방향당 1쪽 이내.** 완성 원고가 아니라 방향·핵심 주장·근거·가정·위험·예상 비용/기간·포기하는 것만 쓴다. |
| 내용 요건 | 자유 서술 / 고정 틀 | 근거 연결, 환각 방지 | **고정 틀.** 방향명, 한 문단 의도, 핵심 주장 3~5개, 정확한 출처 버전과 발췌, 가정, 위험, 예상 비용/기간, 이 방향을 고르면 빠지는 것. 출처가 부족해도 **미검증 가정과 확인할 근거를 표시한 대안**은 허용한다. 차이를 설명할 근거조차 없을 때만 "나눌 근거 부족"으로 생성하지 않는다. |
| 트리거·비용 | 기획 시작마다 자동 / 기획 시작+범위·방법이 갈릴 때 / 사람이 요청할 때만 | 유료 run, 소음, 시의성 | **기획 시작과 범위·방법이 갈리는 지점, 사람이 요청할 때.** 라운드당 최대 한 묶음. **이미 사람이 시작한 run 안의 제안**은 새 run 없이 만들고, **새 유료 run**은 사람의 실행 동작·현재 정책·예약 예산 검사를 거친다. "요청 시 추가"는 새 묶음 요청이며 라운드 상한에 계상하고, 같은 묶음의 교체·재생성은 새 run 없이 한다. 방향마다 후속 run을 자동으로 만들지 않는다. A는 프로젝트 예산에 계상하고, B는 프롬프트 복사나 외부 제안으로 받는다. |
| 채택 | AI가 하나 선택 / 사람이 하나 채택 / 모두 유지 | 사람 권한, 감사, 재현 | **소유자 사람이 하나 채택.** 채택은 `adopted` 결정+이유, 나머지는 `revoked`+이유를 **한 tx**로 쓴다. 다음 라운드 할 일이나 기획 수정으로 이어지고, 판 생성·run 시작은 자동으로 하지 않는다. 후보 버전이 바뀌었거나 중복 클릭·부분 실패면 전체를 거부한다. |

### 2.5 근거와 맞지 않는 요청에 AI 반대 의견

**이미 정해진 것:** 근거와 맞지 않는 요청에 AI가 반대 의견을 낸다([00-brief.md:28](00-brief.md#L28)). reviewer는 별도 run으로 실행하고 메인의 기대 결론을 주지 않는다([stage-1-runners.md:58](stage-1-runners.md#L58)). 승인은 사람만 한다([stage-1-api.md:25](stage-1-api.md#L25)). **reviewer만 반대 의견을 만든다는 것은 기존 합의가 아니다.** 4단계 제안은 작업 AI도 반대를 제기하고, 필요할 때만 독립 reviewer를 쓰는 것이다.

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 효력 | 해결될 때까지 차단 / 참고 의견만 / 참고+확인 필요 | 사람 권한, 감사, 형식적 통과 방지 | **참고+채택·승인 시 명시적 확인.** AI가 거부권을 갖지 않고, 사람이 이유를 남기면 진행할 수 있다. 확인 없이 넘어가지는 않는다. |
| 근거 요건 | 느낌·요약 / 정확한 출처 버전+발췌 / 출처 없이 반대 | 오탐, 신뢰, 검증 가능성 | **정확한 출처 버전+발췌, 또는 채택된 결정·확인된 가정·검증된 근거와의 충돌.** 문체·취향은 반대 사유가 아니다. 자료를 못 읽었으면 "확인 불가"로 표시하고 반대 의견으로 꾸미지 않는다. **근거·취향·확인 불가를 구별한다.** |
| 생성자 | 작업한 AI가 스스로 / reviewer 별도 run / 사람만 | 독립성, 비용, 조기 발견 | **작업 AI도 반대 의견을 제기할 수 있다.** 작업 AI의 것은 **자기 점검**으로 표시하고, 독립 검토가 필요한 경우(고위험 변경·새 근거·사용자 요청·승인 직전)에만 부모가 담당을 반납하고 reviewer가 새 claim/fence로 별도 결과를 낸다. 이를 **독립 검토**로 표시한다. 같은 모델의 다른 세션을 "다른 모델 검증"이라 하지 않는다. 모든 반대에 별도 run을 강제하지 않는다. |
| 시점 | 요청 접수 / 결과 채택 / 승인 직전 | 조기 발견, 소음 | **요청 접수(기획·범위), 결과 채택, 승인 직전 세 곳.** 그 외에는 사람이 요청할 때만. |
| 기록·override | 스레드 댓글만 / review 결과물+스레드+결정 / 삭제 | 감사, 재검토, 버전 고정 | **`review` 결과물+`conflicts`+스레드+결정.** 확인·override는 **대상 요청·결과·출처·반대 의견의 정확한 버전**에 고정하고, 새 근거·새 결과에 옛 확인을 자동 승계하지 않는다. 채택·승인 명령이 **같은 tx에서 확인 증거를 검사**하며, UI 체크만으로 통과하지 않는다. override는 `adopted` 결정과 이유로 남기고, 반대 의견은 "사람이 이유를 남기고 진행함"으로 해소한다. 삭제하지 않는다. 반대 의견만으로 단계를 자동 stale로 만들지 않고, 사람이 reopen한다. |

### 2.6 직접 편집·제안 모드

**이미 정해진 것:** 3단계 결과 글은 읽기 전용+첨언이고, 첨언→`edit_text` 제안→기반 대조→새 버전 채택은 3단계에 이미 있다. 직접 편집·제안 모드는 4단계다([stage-1-ui.md:38](stage-1-ui.md#L38)). `applied`는 결과 버전 또는 실제 적용된 후속의 증거와 tx가 필요하다([stage-1-db.md:211](stage-1-db.md#L211), [stage-1-ui.md:101](stage-1-ui.md#L101)).

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 기본 모드·권한 | 사람만 직접 / 사람·AI 모두 직접 / 모드 선택 | 원문 보존, 신뢰, 감사 | **사람은 기본 직접, AI는 기본 제안.** 직접 편집은 **기존 원고를 재작성하는 권한**이며 A/B `result.submit` 계약 전체를 바꾸지 않는다. AI 직접은 run·객체별로 소유자가 켠 경우에만 허용하고, 서버가 run·객체·기준 버전·범위·회수 여부를 검사한다. `run_targets` 존재만으로 허용의 증거로 삼지 않는다. 승인·게시본은 AI도 직접 편집하지 않는다. |
| 버전·충돌 | 원문 덮어쓰기 / 새 버전+기준 버전 / 자동 병합 | 무손실, 동시 편집 | **항상 새 버전+`based_on_version_id`.** 기준 버전이 바뀌면 409와 현재/기대 버전을 보여 주고 자동 병합하지 않는다. 사람이 run 중에 고쳐도 되고, 에이전트의 제출은 기준 불일치로 실패하게 한다(lease는 사람 편집을 막지 않는다, [stage-1-db.md:32](stage-1-db.md#L32)). 재기반은 사용자가 확인하는 새 요청이다. |
| 승인 후·완료 판 | 그 자리 수정 / 새 버전+stale / 금지 | 승인 무효화, 감사 | **승인 후에는 PR 6 규칙 준용: 새 버전+현재 승인 포인터 해제+과거 승인 보존+해당 단계와 뒤 단계 stale+재승인.** 완료 판은 읽기 전용이고, 고치려면 완료 해제(새 판 전) 또는 새 판을 쓴다. 게시·승인 스냅숏은 수정하지 않는다. |
| 제안 수락·거절 | 자동 적용 / 소유자 사람이 수락·거절 / AI가 수락 | 사람 권한, 증거 | **소유자 사람이 수락·거절하고 이유를 남긴다.** 수락은 새 버전+`applied_tx_id`+결과 버전, 거절은 제안과 이유를 보존한다. U4의 후속 상태·적용 tx·결과 버전을 재사용하고, AI가 사람 제안을 자동 수락하지 않는다. |
| 편집기·모바일 | 완전한 WYSIWYG / Markdown+미리보기 / 원문만 | 한글·표, 구현 비용, 접근성 | **Markdown+미리보기, 표는 Markdown 원문 편집.** 모바일 제한은 **새 편집 기능만**이며, 기존 모바일 답·의견 응답·오류 확인·인쇄 미리보기·복사 대안은 유지한다. 데스크톱 200% 확대를 모바일로 오인해 핵심 동작을 숨기지 않는다. |

새 버전을 만들면 U4의 앵커 재판정을 다시 돌린다. 결과는 exact/moved/ambiguous/lost로 남기고, **원래 앵커·인용문·원 버전은 보존**하며, 옛 기반 제안은 충돌로 표시한다. 초안은 U7·U11에서 입력 보존 범위·키를 정하고, 성공은 서버 영수증 뒤에만 표시하며, 타임아웃·409·응답 유실은 같은 키로 확인한다. 이 보장을 기기 간·탭 종료 복구로 확대하지 않는다.

### 2.7 기존 화면을 새 작업 공간으로 기본 대체

**이미 정해진 것:** 3단계는 기존 대시보드·질문 폼과 병행하고, 기본 진입 전환은 기존 읽기·답·승인·reopen·인쇄·딥링크가 합성 자료와 Windows/Mac에서 확인된 뒤 4단계에서 한다. 기존 ask 링크는 당시 set/버전으로 연결한다([stage-1-ui.md:47](stage-1-ui.md#L47)). 빠른 답·장애 대비 경로와 내보낸 고정 HTML은 구분해 보존한다([stage-1-ui.md:109](stage-1-ui.md#L109)). **프로젝트별 opt-in, 실제 프로젝트 1개 확인, 이전 화면 유지 기간은 4단계 제안이다.**

| 정할 것 | 선택지 | 판단 기준 | 추천과 이유 |
|---|---|---|---|
| 전환 방식 | 한 번에 전부 / 프로젝트별 opt-in 후 기본 / 계속 병행 | 되돌리기, 사용자 습관, 링크 | **프로젝트별 opt-in → 게이트 통과 뒤 기본.** 새 화면에서 답·승인·reopen·인쇄·딥링크를 확인한 프로젝트부터 켜고, 사용자가 기본 전환을 승인하면 기본으로 넓힌다. |
