## 2. SQL(DDL 001)이 보장하는 것

DDL이 직접 거부하는 것:

- **다른 프로젝트 행 끼워 넣기**: 업무 표의 `(project_id, id)` 복합 FK와 `(project_id, ...)` 참조가 프로젝트 경계를 넘는 연결을 거부한다.
- **끊긴 참조**: FK가 없는 행·버전·단계·라운드를 가리키는 쓰기를 거부한다. 삭제는 기본 `RESTRICT`라 연구 기록을 함께 지우지 않는다.
- **형식 위반**: 상태 enum, 단계 `key`/`ordinal` 대응, `allow_opencode_go` 0/1, 사용량 문턱 50~100, JSON `json_valid`/`json_type` 모양, 64자 hash, 음수 rev/fence 등.
- **중복**: slug, 프로젝트별 표시 번호·버전 번호, `(project_id, policy_rev)`, `(project_id, actor_id, client_request_id)` 등.
- **부분 UNIQUE**: 프로젝트당 owner 하나, 활성 판 하나, 단계당 열린 라운드 하나.
- **초기값**: 정책 기본 전송 허용(`allow_opencode_go=1`), A 기본 모델(`opencode-go/deepseek-v4.1-flash`), 사용량 문턱 90, `db_meta` 형식.
- **사건 번호**: `events.event_seq`는 `AUTOINCREMENT`로 증가하며 `(project_id, event_seq)`·`(tx_id, tx_index)`가 유일하다. 연속 번호는 보장하지 않는다.

DDL이 **보장하지 않는** 것: 아래 3절.

## 5. SQLite 최소 버전과 근거

**최소 SQLite 3.38.0** (`SQLITE_MIN_VERSION`).

- DDL이 쓰는 **JSON 함수**(`json_valid`, `json_type`)는 SQLite 3.38.0(2022-02-22)부터 기본 빌드에 포함된다. 그 전에는 JSON1 확장이 빌드에 따라 빠질 수 있었다.
- DDL의 **부분 UNIQUE 인덱스**는 3.8.0부터, **DEFERRABLE INITIALLY DEFERRED FK**·`ON DELETE RESTRICT`·`AUTOINCREMENT`는 그보다 오래된 기능이라 3.38.0이 실질 하한을 결정한다.
- Node 26의 `node:sqlite`는 SQLite 3.54.1을 내장한다(2026-11-05 로컬 확인). CI의 Windows·macOS 잡이 실제 `sqlite_version()`을 출력한다.
- 런타임 버전만 보고 기능을 가정하지 않는다(stage-2 2.6 A). `connect()`가 **실제 `sqlite_version()`**과 **`json_valid`·`json_type` 실행 결과**를 확인하고, 아니면 연결을 닫고 명확한 오류를 낸다. 버전 비교는 `sqlite_version_at_least()` 순수 함수로 분리해 낮은 버전 문자열을 시험한다.

## 6. 연결·PRAGMA·정수 방침

- **드라이버**: `node:sqlite` `DatabaseSync`. 별도 드라이버 의존성 없음.
- **foreign_keys**: `PRAGMA foreign_keys=ON` 뒤 `PRAGMA foreign_keys`가 1인지 확인한다. 켜지지 않으면 연결 실패.
- **busy_timeout**: WAL 단계가 끝난 뒤 5000ms로 설정하고 실제 값을 확인한다. 짧은 tx(`BEGIN IMMEDIATE`)와 함께 쓴다.
- **WAL**: 파일 DB는 `busy_timeout`을 0으로 두고 현재 `journal_mode` 읽기와 필요 시 `PRAGMA journal_mode=WAL` 적용을 **한 루프·한 기한**에서 수행한다. 이미 `wal`이면 그대로 두고, 아니면 전환해 `wal`인지 확인한다. 읽기와 전환 모두 `SQLITE_BUSY`면 같은 10ms→최대 100ms 백오프로 `BUSY_TIMEOUT_MS`(또는 `wal_busy_timeout_ms`) 상한까지 재시도하고, 상한을 넘으면 원래 오류를 `cause`로 담은 오류로 연결을 닫는다. 경과 시간은 단조 시계(`performance.now()`)로 잰다. `:memory:`는 건너뛴다. WAL의 `-wal`/`-shm` 파일은 SQLite가 만드는 연결 부산물이다.
- **부모 폴더**: DB 파일의 부모 폴더만 `mkdir -p` 한다. 객체 폴더·세션·토큰·백업 등 다른 파일은 PR1이 만들지 않는다.
- **정수는 bigint**: 모든 prepared statement에 `setReadBigInts(true)`를 적용한다. SQLite INTEGER는 `number`로 읽지 않는다. 2^53 초과 값의 손실을 막기 위해 `2^53+1` 왕복을 시험한다. API의 10진 문자열 계약은 PR13이 이 위에 얹는다.
- **tx 콜백은 동기만**: native async 함수는 `BEGIN` 전에 거부하고, 동기 함수가 thenable을 반환하면 롤백·오류로 처리한다. 반환된 thenable은 실행하지 않으며, unhandled rejection 방어는 native `Promise`에만 내장 rejection 핸들러를 붙인다. tx는 동기 콜백 계약이며, 콜백이 스스로 시작한 비동기 작업(이미 생성된 Promise의 후속 실행)은 취소할 수 없다 — 타입(`never`)과 실행 전 async 거부로 막는다.
- **PES_HOME**: 프로젝트 폴더만 옮긴다. DB `~/.pes/pes.db`·객체 `~/.pes/objects/` 경로는 바뀌지 않는다(stage-2 2.7). `PES_DB`·`PES_OBJECTS` 우회 변수는 PR1에 없다.

## 7. bootstrap이 만드는 행과 만들지 않는 것

`bootstrap_project(db, input, deps)`는 **한 tx**에서 아래를 만든다. 어느 한 행이라도 실패하면 전부 롤백한다.

- `users` 1행(owner), `actors` 1행(`kind='human'`, owner user), `projects` 1행(`status='staging'`으로 시작해 마지막에 `active`), `project_members` 1행(`role='owner'`).
- `mutation_commits` 1행(영수증)과 `events` 1행. PR4부터 bootstrap은 명령 서비스를 지나며, `project_policy_versions.tx_id`가 참조하는 영수증과 사건을 같은 tx에 남긴다. 영수증 재생·멱등은 8절.
- `project_policy_versions` 1행(`policy_rev=1`, `allow_opencode_go=1`, 기본 모델·문턱 90, `changed_by_kind='human'`).
- `editions` 1행(`edition_no=1`, `status='active'`)과 `stages` 6행(`plan`~`publish`, `ordinal` 1~6, `status='pending'`).
- `counters` 9행(객체 kind별 `next_no=1`).
- 포인터: `editions.current_stage_id`=plan 단계, `projects.active_edition_id`, `projects.current_policy_id`, `projects.status='active'`.

만들지 않는 것: **열린 라운드**(PR6). 명령 서비스·`events`·영수증 재생은 PR4(8절)가 맡는다. `PR13`의 `project.create`가 이 기본기를 API 계약으로 감싼다.

## 8. 변경 명령 서비스(PR4)가 보장하는 것

PR4부터 모든 업무 쓰기는 `scripts/pes_core/commands.ts`의 `CommandService` 하나를 지난다. 외부 호출은 `execute()`(async 래퍼, 예외는 rejection)를 쓰고, 동기 호출자인 `bootstrap_project`는 같은 핵심인 `execute_sync()`를 쓴다. tx 안에는 `await`가 없어 명령 실행 중 이벤트 루프에 양보하지 않는다. `bootstrap.ts`는 `bootstrap_project` 시그니처만 유지하고 내부에서 `project.bootstrap` 명령을 서비스로 실행한다. 업무 표 INSERT/UPDATE/DELETE SQL은 `commands.ts`에만 있다.

- **실행 순서**: 닫힌 등록표(`COMMANDS`) → 프로젝트·행위자 확인(`forbidden`/`not_found`) → 현재 정책(`policy_denied`) → 영수증 재생(`client_request_id`+`request_hash`) → rev → 변경 → `events`+`mutation_commits`. 전부 한 tx다.
- **멱등**: 같은 키·같은 요청은 저장된 결과를 재생하고 아무것도 쓰지 않는다. 같은 키·다른 요청은 `idempotency_key_reuse`로 거부한다. `request_hash`는 명령과 payload만 덮고 `base_control_rev`는 덮지 않으므로, 낡은 base로 다시 보내도 재생이 rev 검사보다 먼저 동작한다.
- **영수증 장기 보존**: `mutation_commits`·`events`를 UPDATE/DELETE하는 경로가 없고, 재생은 시간이 지나도 유효하다.
- **정책 우선**: 인증·권한·현재 정책 검사가 영수증 재생보다 먼저다. OFF 뒤에는 OFF 전에 성공한 결과가 재생되지 않는다.
- **원자성**: 조건부 UPDATE가 0행이거나 events/영수증 INSERT가 실패하면 tx 전체를 롤백하고 성공으로 보이지 않는다. 실패한 시도는 영수증을 남기지 않으므로 같은 키로 다시 실행할 수 있다.
- **닫힌 표면**: 표 CRUD·임의 SQL·ops 명령은 등록표에 없다. 새 쓰기는 도메인 명령 하나로만 추가한다.
- **오류 번역**: SQLite UNIQUE·PRIMARY KEY 제약만 `ApiError("conflict", "UNIQUE constraint conflict")`로 바꾼다. 원문(표·열 이름)은 메시지·`details` 어디에도 넣지 않는다. FOREIGN KEY·NOT NULL·CHECK 등 다른 SQLite 오류는 tx 롤백 뒤 원래 오류를 그대로 던진다.

### 8.1 request_hash 정규화 (언어 중립)

영수증의 `request_hash`는 다음 규칙으로 계산한다. 다른 언어 구현도 같은 입력에서 같은 64자 hex를 내야 한다(영수증을 장기 보존하고 재생 판정에 쓰므로).

1. **입력 스냅샷**: 명령 진입 시 payload를 `JSON.stringify`→`JSON.parse` 한 번으로 고정한다. `JSON.stringify`는 `toJSON`을 적용하고 getter를 한 번 읽는다. 최상위 `undefined`·함수·심볼만 있는 payload는 `null`로 정규화한다. 순환 참조·BigInt는 `invalid_payload`다. 이후 해시·정책 사본·검증·실행은 모두 이 스냅샷만 쓴다.
2. **해시 대상 문자열**: `command + "\n" + canonical_json(snapshot)`을 UTF-8로 인코딩한 바이트.
3. **canonical_json**:
   - 객체 키는 **UTF-16 코드 유닛 순서**(JavaScript `Array.prototype.sort()` 기본)로 정렬한다. 키와 문자열 값은 ECMAScript `JSON.stringify` 규칙으로 인용·이스케이프한다.
   - 배열은 순서를 유지한다.
   - 숫자·불리언·`null`은 ECMAScript `JSON.stringify` 출력 그대로다. 스냅샷은 `JSON.parse` 결과이므로 NaN·Infinity는 없고, `-0`은 `0`으로 직렬화된다.
   - 공백·개행을 넣지 않는다.
4. **해시**: 위 문자열의 SHA-256, 소문자 16진수 64자.
5. **포함/제외**: `command`와 payload 스냅샷만 포함한다. `base_control_rev`·`project_id`·`actor_id`·`via`·`client_request_id`는 해시에 넣지 않는다. 영수증 조회 키는 `(project_id, actor_id, client_request_id)`이고 해시는 요청 본문 비교에만 쓴다.

예: command `project.set_topic`, payload `{"n":1,"topic":"가"}` → 해시 대상 `project.set_topic\n{"n":1,"topic":"가"}` → SHA-256 `54877204a50ae33ca4e175d46813a1f760859a78124c138ea3d66c83eb0fc3fa`.

### 8.3 run·lease·fence(PR5)

`scripts/pes_core/commands/runs.ts`가 `run.create`·`run.claim`·`run.heartbeat`·`run.wait`·`run.complete`·`run.release`·`run.handoff`·`run.interrupt`·`run.record_receipt`를 정의하고, `scripts/pes_core/runs.ts`의 공개 함수는 각각 `CommandService.execute` 한 번만 호출한다. 모든 run 쓰기는 8절의 실행 순서(등록표 → 프로젝트·행위자 → 정책 → 영수증 재생 → rev/lease → 변경 → `events`+영수증)를 그대로 지나며 한 tx다.

- **create(PR13)**: `run.create`는 사람 owner만 실행한다. 입력은 `{actor_id, mode, runtime, provider, model}`뿐이고, 대상 actor는 그 프로젝트의 활성 멤버여야 한다. `runs` 행은 `status='queued'`, `role='worker'`, `started_at=NULL`로 만들고 **lease를 만들거나 fence를 바꾸지 않는다**. 따라서 이 run의 첫 `run.claim`은 fence 1이다. 영수증·사건은 `run.created`이고 사건은 `run_id`를 담는다. 영수증의 `run_id`는 비워 둔다: `mutation_commits`의 `(project_id, run_id, actor_id)` FK는 run 소유 actor를 요구하는데 이 명령의 actor는 owner이므로, run 식별은 결과와 사건이 담당한다.
- **claim**: `ctx.base_control_rev`가 주어지면 영수증 재생 **뒤**, 같은 tx 안에서 저장된 `projects.control_rev`와 BigInt로 비교한다(정규화 10진 문자열은 2^53·int64 초과도 그대로 비교, 불일치는 `rev_conflict`). 따라서 같은 키·같은 요청은 그사이 rev가 바뀌어도 원래 결과를 재생한다. 프로젝트에 활성·미만료 lease가 없을 때만 run을 만들거나 재개한다. run은 `running`, lease는 `active`, `fence`는 이전 값 + 1(첫 lease는 1)이다. `run_id` 재개는 `queued`·`waiting_human`·`blocked_usage`·`interrupted`에서 되고, `running`이어도 활성·미만료 lease가 없으면(보유자가 죽어 lease만 만료) 같은 actor가 이어받는다(SEL-56 F1, 8.20: 만료 lease는 되살리지 않고 `run.interrupted`(`lease_expired`) 사건으로 정리한 뒤 새 lease·fence+1, A는 미정산 dispatch가 있으면 `conflict`). 살아 있는 lease가 있으면 `conflict`다. `succeeded`·`failed`·`cancelled`는 거부한다. `blocked_usage`를 재개하면 `go_block_reason`·`go_blocked_at`·`go_block_reset_at`을 함께 지운다(DDL의 `go_block_reason IS NULL OR status = 'blocked_usage'` 제약). 재개 payload에 `parent_run_id`나 `role`이 있으면 `invalid_payload`다. 만료된 lease를 대신할 때 그 lease의 run이 아직 `running`이면 같은 tx에서 `interrupted`로 끝내고(`ended_at` 설정) `events.run_id`가 그 옛 run인 interrupt 사건을 남긴다. 이미 끝난 run은 건드리지 않는다. 다음 `fence`가 `Number.MAX_SAFE_INTEGER`를 넘으면 쓰기 전에 `conflict`로 거부한다.
- **가드**: claim을 뺀 모든 run 명령은 `project_leases` 행이 그 프로젝트의 **활성·미만료**(`now < expires_at`) lease이고 `lease_id`·`fence`·`run_id`·소유 행위자가 정확히 같을 때만 통과한다. 아니면 `conflict`이고 아무것도 쓰지 않는다. 만료(`now >= expires_at`)·해제된 lease는 되살리지 않으며, 새 claim만 새 `lease_id`와 더 높은 `fence`를 만든다.
- **heartbeat**: `expires_at = max(기존 expires_at, now + lease_ttl_ms)`, `heartbeat_at = max(now, acquired_at)`로 연장하고 `fence`는 바꾸지 않는다. 시계가 되감겨 now < acquired_at이면 heartbeat_at은 acquired_at이고, expires_at은 어떤 경우에도 기존 값보다 줄지 않는다(TTL 설정이 더 작은 서비스가 같은 lease를 갱신해도 기존 만료를 당기지 않는다). 만료 경계(`now == expires_at`)에서는 거부한다. 답·사건에는 계산식이 아니라 저장된 `expires_at`을 싣는다.
- **wait**: run을 `waiting_human`으로 바꾸고 lease를 `released`로 놓으며(가드의 `fence`는 보존), 같은 tx에 사건과 영수증을 남긴다. 대기 중에는 다른 run이 claim할 수 있고, 재개는 새 claim·새 `fence`다.
- **complete**: `succeeded`(기본) 또는 `failed`로 run을 끝내고 lease를 놓는다. 승인·봉인·단계 변경은 하지 않는다. `release`·`handoff`는 run을 `queued`, `interrupt`는 `interrupted`로 둔다.
- **입력 영수증**: `applied`는 같은 프로젝트의 `mutation_commits.id`인 `applied_tx_id`가 있을 때만 인정한다. 중복 반영 방지 범위는 **같은 인계 흐름**이다. `parent_run_id` 사슬을 거슬러 뿌리 run을 찾고, 그 뿌리에서 파생된 모든 run(조상·후손·형제)이 이미 `applied`한 입력은 다시 적용하지 않고 `already_applied: true`로 답하며 저장된 `applied_tx_id`를 바꾸지 않는다. 뿌리가 다른 독립 run은 서로 막지 않는다. 인계 뒤 원본 run을 재개하거나 형제 run을 파생해도 같은 흐름에서는 한 번만 반영된다.
- **영수증·사건**: run 명령의 영수증은 `run_id`·`lease_id`·`fence`를, 사건은 `events.run_id`를 남긴다. 거부·검증 실패는 영수증도 사건도 남기지 않는다.
- **설정**: `lease_ttl_ms`·`heartbeat_interval_ms`는 `scripts/pes_core/config.ts`에만 있다. 서비스는 `process.env`를 읽지 않는다. API/CLI 같은 합성 지점이 `resolve_run_config(overrides, process.env)`로 env를 명시해 넘기고, 주입된 `RunConfig`가 없으면 서비스는 설정 기본값만 쓴다. 주입값도 생성자에서 `resolve_run_config(overrides, {})`로 검증·복사·동결하며, 잘못된 값은 생성 시점에 거부한다. 우선순위는 주입값 > env > 기본값이며, 양의 안전 정수만 받고 heartbeat가 TTL보다 짧아야 한다.

### 8.4 내용 버전·출처·연결(PR7)

`scripts/pes_core/commands/content.ts`가 `content.*` 8개 명령을 정의하고, `scripts/pes_core/content.ts`의 공개 함수는 각각 `CommandService.execute` 한 번만 호출한다. 모든 명령은 8절 실행 순서를 그대로 지나며 한 tx다. 같은 파일이 `result.submit`(PR13)도 정의하되 `RESULT_COMMAND_ENTRIES`라는 별도 동결 묶음으로 내보내고, 공개 래퍼 `submit_results`는 `scripts/pes_core/results.ts`에 두어 `content.ts`에서 재수출한다(기존 content 명령 8개 표면을 그대로 유지).

- **결과 묶음(PR13)**: `result.submit` 입력은 `{run_id, lease_id, fence, results:[{op:'append_version', ...}]}`이고 항목은 1~20개다. 각 항목의 `op`는 `append_version`뿐이며 그 밖의 키는 `content.append_version`이 허용하는 필드로 제한한다. 현재 활성·미만료 lease(정확한 `run_id`·`lease_id`·`fence`·소유 actor)를 요구하고, `ctx.base_control_rev`가 있으면 항목 검증 뒤·lease 검사 전에 현재 `projects.control_rev`와 BigInt로 비교한다(낡으면 `rev_conflict`, 아무것도 쓰지 않음). 빈 결과 목록은 rev 검사보다 먼저 `invalid_payload`다. 같은 키·같은 요청은 rev가 바뀌어도 영수증 재생이 우선한다. 모든 항목의 버전 id·번호를 먼저 계획한 뒤 영수증 1행을 쓰고, 같은 tx에서 버전 행들을 쓴다(`object_versions.tx_id`가 그 영수증을 참조하므로 순서가 고정된다). 한 항목이라도 실패하면 영수증·버전·사건이 모두 롤백되고, 성공하면 `result.submitted` 영수증 1행과 항목별 `result.submitted` 사건(`run_id` 포함)을 남긴다. 같은 키·같은 입력은 저장된 결과를 재생하고 같은 키·다른 입력은 `idempotency_key_reuse`다.
- **append-only**: `object_versions`·`artifact_versions`·`source_versions`·`citations`·`version_relations`·`artifact_components`를 UPDATE/DELETE하는 경로가 없다. 새 내용은 `content.append_version`으로만 쌓고 과거 행은 그대로 둔다.
- **현재 포인터**: `objects.current_version_id`는 `content.set_current`로만 옮기며 그 객체 자신의 버전만 가리킨다(다른 객체·다른 프로젝트 버전은 `conflict`/`not_found`). 포인터를 옮겨도 `objects.rev`만 1 증가하고 버전 행은 변하지 않는다.
- **각주**: `citations`는 artifact 버전별 1..n으로 번호를 매기고, 가장 최근 버전(최고 `version_no`)만 새 각주를 받는다. 오래된 버전은 sealed라 `conflict`다. 같은 URL이라도 출처 객체를 합치지 않는다.
- **출처 사실**: `source_versions`에 확인 시점·발췌·위치·방법·판정·확인 행위자를 저장한다. `verified_by_actor_id`는 그 프로젝트 소속이며 비활성화되지 않은(`actors.disabled_at`·`users.disabled_at` NULL) 행위자여야 한다(아니면 `not_found`). `verification_state='unreachable'`인 버전에는 발췌를 붙일 수 없다(`invalid_payload`).
- **연결**: `version_relations`의 from 버전은 그 객체의 최신 버전이어야 하고, 같은 (from,to,kind)는 한 번만 둔다.
- **library**: `content.import_library`는 한 tx에서 항목·출처·각주를 만들고 원본 JSON을 같은 tx의 `content.library_imported` 사건 payload `original`에 보존한다. 같은 library를 다시 가져오면(`library_hash` 동일) 업무 행을 만들지 않고 첫 결과를 돌려준다. 같은 library 정체성(항목 목록을 뺀 메타데이터가 동일) 안에서는 `legacy_id` 기준으로 이미 가져온 항목을 항목별로 건너뛰고 새 항목만 추가한다(부분집합·부분겹침·상위집합 모두). 항목 목록 밖 메타데이터가 다른 library는 별도 가져오기다. `legacy_id`·`kind_original`은 가져오기 고유 필드로 item의 같은 이름 키에 덮이지 않으며, item의 `__proto__` 같은 own 키도 데이터로 보존한다. library의 모든 문자열에 외톨이 서로게이트가 있으면 `invalid_payload`로 아무것도 쓰지 않는다. 파일 바이트 저장은 PR9/11 경계다.
  - **항목 id·비교 키**: 항목 `id`는 0 이상의 안전 정수 또는 비어 있지 않은 문자열이다(실제 library의 id는 정수). 중복·재가져오기 비교는 타입을 붙인 키(`number:5` / `string:5`)로 해서 5와 "5"는 다른 항목이다. `legacy_extra.legacy_id`와 결과 `items`는 원래 값(정수는 정수 그대로)이다.
  - **library 정체성**: 항목 목록과 휘발 키(`imported`·`round`)를 뺀 최상위 메타데이터다. 해시(`shell_hash`)와 항목 비교 키 목록(`item_keys`)을 사건 payload에 따로 두므로 재가져오기 판정은 `original`을 파싱하지 않는다.
  - **건너뛴 가져오기**: 같은 정체성·같은 id지만 내용이 바뀐 파일은 구조 행에 반영하지 않고(옛 내용 유지) 건너뛰되, `content.library_import_skipped` 사건에 그 파일의 `original`과 `library_hash`를 남긴다. 정확히 같은 파일의 반복은 `library_hash`만 남긴다.
  - **제목**: 제목이 없거나 문자열이 아니면 `(제목 없음)`으로 저장하고 원래 값(없었으면 null)을 `legacy_extra.title_original`에 둔다.
  - **`archived_at`**: library 가져오기에서 `status:"removed"`인 항목에만 찍는 가져오기 전용 표시다. `append_version`/`add_artifact`로 status를 바꿔도 `archived_at`은 바뀌지 않는다. 버전 상태가 기준이다.
  - **예정**: library 원본을 사건 payload에 두는 것은 D1 행 2MB 한도 때문에 PR9/11의 blob 경계로 옮길 예정이다.

### 8.5 행위자·토큰·전송 정책(PR10)

`scripts/pes_core/commands/actors.ts`·`commands/policy.ts`가 `token.issue`·`token.revoke`·`policy.set`·`dispatch.prepare`·`dispatch.authorize`·`dispatch.mark_sent`·`dispatch.block` 7개 명령을 정의하고, `scripts/pes_core/actors.ts`·`policy.ts`의 공개 함수는 각각 `CommandService.execute` 한 번만 호출한다. `PolicyChecker.check`는 tx 안의 읽기 전용 `get`/`all` 핸들을 4번째 인자로 받고, 정책 검사는 영수증 재생보다 먼저다. 핸들은 SELECT 또는 최종 문장이 SELECT인 WITH 단일 문장만 받으며(WITH … UPDATE/INSERT/DELETE/REPLACE는 거부, PRAGMA·ATTACH·DETACH·BEGIN/COMMIT/ROLLBACK/SAVEPOINT/RELEASE·여러 문장은 거부), SQLite 연결에서는 검사 동안 `PRAGMA query_only=ON`을 걸었다가 끝나면(예외에도) 원래 값으로 되돌리고, `check`가 끝난 뒤 그 핸들의 `get`/`all`은 예외다. `query_only`를 읽거나 켤 수 없거나 켠 뒤에도 ON이 아니면(어댑터가 무시) 검사기를 실행하지 않고 `policy_denied`로 명령이 실패한다(fail-closed, 영수증·사건 없음).

- **토큰**: `token.issue`는 그 프로젝트의 사람 owner만 실행하고, 대상 행위자는 검증과 같은 자격 규칙(`read_credential_actor`: 활성 행위자·존재하는 활성 사용자)과 그 프로젝트 멤버십을 만족해야 한다(아니면 거부, 행 없음). 원문 비밀은 첫 응답에만 있고, 표·사건·영수증(재생 결과 포함)·오류 메시지에는 SHA-256 해시만 남는다. 범위는 프로젝트, 만료는 생성 시각 + 30일이며 `now >= expires_at`이면 만료다. `token.revoke`는 `revoked_at`만 채우고 행을 지우지 않는다. `verify_agent_token`의 어떤 실패든 원문을 되풀이하지 않는 `forbidden`이다.
- **정책**: `policy.set`은 사람 owner만 실행하고 `project_policy_versions`에 새 행(`policy_rev` + 1)을 append한 뒤 `projects.current_policy_id`를 옮긴다. 이전 정책 행은 바꾸지 않는다. 새 행이 `allow_opencode_go = 0`이면 같은 tx에서 (1) 활성 lease가 mode A(Go) run의 것이면 lease를 `released`로 바꾸고(fence 유지) 그 run이 `running`이면 `interrupted`로 바꾸며 `run.interrupted` 사건(`run_id` 포함, 이유 `policy_off`)을 남긴다. mode B run·끝난 run·이미 해제된 lease는 그대로다. 옛 guard는 OFF 중에도 다시 ON 뒤에도 거부되고, 새 `run.claim`(새 fence) 뒤에만 진행한다. (2) `prepared`·`authorized` 전송을 `blocked`로 바꾸고 `policy.changed` 사건 뒤에 `dispatch.blocked` 사건을 하나씩 남긴다. 단 `authorized`이면서 `sent_at` 또는 `external_request_id`가 있는 행은 이미 나갔을 수 있으므로 `blocked` 대신 `unknown`(증거 보존, `unknown_at`·`unknown_reason` 기록, `dispatch.unknown` 사건)으로 두며 결과의 `blocked_dispatch_ids`·`dispatch.blocked` 사건에 넣지 않는다. `dispatch.block`도 같은 판정이고, 선택과 조건부 UPDATE에 같은 조건을 쓴다. `sent`·`response`·`adopted`·`failed`·`unknown`·`blocked` 이력은 지우거나 고치지 않으며, 다시 허용해도 차단된 전송은 되살아나지 않는다.
- **전송**: `dispatch.prepare`·`authorize`·`mark_sent`는 run 명령과 같은 활성·미만료 lease guard(`run_id`·`lease_id`·`fence`)를 지나고, `dispatch.block`만 guard가 없다. `dispatch.mark_sent`는 `sent`와 `sent_at`만 기록하며 `usage_json`·`cost_json`은 NULL로 둔다(모르는 비용을 0으로 저장하지 않는다). 실제 Go 네트워크 호출은 없다.
- **fail-closed**: 프로젝트 포인터가 NULL이거나 없는 행·다른 프로젝트 행을 가리키거나, 그 프로젝트의 최고 `policy_rev`가 아니거나, `allow_opencode_go`가 정확히 0/1이 아니거나, `mode_a_model`이 `opencode-go/`로 시작하지 않거나, `go_usage_stop_percent`가 50~100 밖이거나, `changed_by_kind`가 `human`이 아니면 정책은 손상이다. `check_go_allowed`는 손상에서도 예외를 던지지 않고 허용하지 않으며, `current_policy`는 `policy_denied`다. Go가 꺼졌거나 정책이 손상되면 `dispatch.prepare`·`authorize`·`mark_sent`는 `policy_denied`이고, `dispatch.block`·`token.*`·`project.*`·`run.*`는 Go 정책에 막히지 않는다. 정상적으로 꺼진 정책에서는 `policy.set`도 실행되지만, **정책이 손상된 경우 `policy.set`도 현재 정책을 먼저 읽기 때문에 `policy_denied`(fail-closed)다.** 손상 복구 절차(사람 전용 복구 명령 등)는 이 PR에 없고 수동 조치·후속 결정으로 남긴다.
- **운영 조립(후속 필수)**: 정책 checker(`DbPolicyChecker`)·토큰 인증(`verify_agent_token`/`resolve_actor`)·scope 집행의 운영 조립은 후속 API/CLI PR에서 필수로 연결한다. 이 PR은 부품과 계약만 제공한다.
- **기본값**: stage-0 7-1 그대로 `policy_rev` 1, `allow_opencode_go` 켜짐, `mode_a_model` `opencode-go/deepseek-v4.1-flash`, `go_usage_stop_percent` 90이다.

### 8.6 결과물·객체 저장(PR9)

`scripts/pes_core/commands/files.ts`가 `file.reserve_upload`·`file.complete_upload`·`file.attach_version`·`file.quarantine`·`file.gc_orphans` 5개 명령을 정의하고, `scripts/pes_core/files.ts`의 공개 함수가 각각 `CommandService.execute` 한 번만 호출한다. `blobs`·`file_policies`·`version_files`의 INSERT/UPDATE/DELETE는 `commands/files.ts`에만 있다.

- **id와 경로**: 공개 결과의 blob 식별자는 서버가 만든 id 하나뿐이다. `storage_key`는 `project_id/sha256`으로 서버가 계산하며, 호출자가 경로·서명 URL·storage_key를 id 대신 넘기면 `invalid_payload`/`not_found`다. 경로는 결과·사건·영수증에 남기지 않는다.
- **정식 저장소 하나**: 저장소는 `CommandServiceOptions.objects_dir`로 생성 때 받은 폴더 하나다. 같은 DB에 다른 폴더로 두 번째 `CommandService`를 만들면 생성이 `conflict`로 실패하고(같은 폴더·같은 경로 표기는 허용), `complete_upload`·`get_blob`·`store_blob`·`gc_orphans`에 넘긴 `store.objects_dir`가 그 폴더와 다르면 아무것도 읽거나 쓰지 않고 `conflict`로 거부한다. `file.gc_orphans` payload는 `{grace_ms}`뿐이며 `objects_dir` 필드는 `invalid_payload`다. 명령은 주입된 저장소만 스캔한다.
- **staging → ready**: `reserve_upload`는 같은 프로젝트에서 `(sha256, size)`가 같은 기존 행을 재사용하고(다른 프로젝트면 별도 행·별도 파일), `complete_upload` 명령은 주입된 저장소에서 그 blob의 실제 바이트를 다시 읽어 sha256·size를 계산해 예약값과 비교한다. 저장소가 주입되지 않았거나 바이트를 읽을 수 없으면 ready가 되지 않고(거부), 예약값과 다르면 `quarantined`다. 호출자가 직접 보낸 `sha256`·`size`는 신뢰하지 않는 주장으로, 예약값과 다를 때만 `quarantined`를 부를 수 있고 ready의 근거가 되지 않는다. 공개 `complete_upload`는 `{blob_id}`만 보낸다. `store_blob`은 `staging` blob에 쓰고, 파일이 없는 `ready` blob은 예약값과 같은 바이트로만 복구하며, 길이·sha256이 예약값과 다르면 쓰기 전에 거부한다. 임시 파일+rename으로 실패 잔여물을 남기지 않는다.
- **계보와 정책**: `attach_version`은 `ready` blob만 받아 `version_files`에 (version, blob, role) 한 행을 만든다. blob마다 `file_policies` 한 행을 만들어 모든 버전·role이 공유하며, 같은 (version, blob, role)은 `conflict`다.
- **격리·gc**: "연결됨"은 `blobs`를 참조하는 모든 FK 표를 뜻한다 — `version_files`, `file_policies`, `snapshots`, `artifact_versions`, `source_versions`, `file_extractions`(blob_id·text_blob_id), `sync_items`, `submissions`, `outbound_dispatches`(manifest·response), `import_batches`(source_manifest·report). 연결된 blob은 격리·삭제하지 않는다. `gc_orphans`는 한 tx에서 참조 없는 `staging`/`quarantined` 행(마지막 예약 시각 기준 grace 초과)을 지우고, 참조 없는 오래된 파일과 그 blob 파일은 tx 커밋 뒤에 지운다. 삭제 직전 같은 동기 구간에서 `storage_key`를 다시 조회해 행이 생겼으면 지우지 않는다(고아 파일도 파일마다 확인). 파일 스캔과 삭제는 objects 루트와 프로젝트 폴더를 삭제 전에 `lstat`해 symlink면 아무것도 지우지 않는다. tx가 실패하면 디스크를 건드리지 않고, 삭제가 실패하면 다음 gc가 DB와 디스크를 맞춘다. 파일이 없는 `ready` blob은 지우지 않고 `missing_file_blob_ids`로 보고한다.
- **경로 안전**: `storage_key`는 objects 폴더 아래 이 프로젝트 폴더로만 풀린다. 절대 경로·`..`·드라이브 문자·역슬래시와 objects 폴더·프로젝트 폴더·대상 파일의 symlink는 읽기·쓰기 모두 거부한다. `EACCES`·`ENOENT` 같은 파일 시스템 오류는 절대 경로나 저장소 폴더를 담지 않는 고정 문구의 `ApiError("conflict")`로 바꾼다.

### 8.7 판·단계·라운드(PR6)

`scripts/pes_core/commands/editions.ts`가 `edition.create`·`round.start`·`round.seal`·`stage.approve`·`stage.reopen`·`edition.release_completion`·`edition.carry_over`·`edition.snapshot` 8개 명령을 정의하고, `scripts/pes_core/editions.ts`의 공개 함수는 각각 `CommandService.execute` 한 번만 호출한다. 예외는 읽기 전용 `open_tasks_for_round(db, project_id, round_id)` 하나이며 쓰지 않는다. 판·단계·라운드·스냅숏·승인·이월 표의 INSERT/UPDATE는 `commands/editions.ts`에만 있다.

- **사람 규칙(PR10)**: `edition.create`·`stage.approve`·`stage.reopen`·`edition.release_completion`·`edition.carry_over`는 `read_credential_actor` 기준 `kind='human'`이면서 `project_members.role='owner'`인 행위자만 실행한다. owner의 user를 공유하는 에이전트도 `forbidden`이다. `round.seal`·`edition.snapshot`은 사람 멤버면 되고, 에이전트는 `run_id`·`lease_id`·`fence`가 그 프로젝트의 활성·미만료 lease와 정확히 같을 때만 된다(없으면 `forbidden`, 낡은 fence·해제된 lease는 `conflict`). 에이전트의 `round.seal`은 guard의 run이 그 라운드에 속할 때만(아직 조준하지 않은 run — `stage_id`·`round_id`가 NULL — 은 첫 봉인 때 같은 tx에서 그 단계·라운드에 묶이고, 이후 다른 단계·라운드 봉인은 `forbidden`이며 아무것도 쓰지 않는다), `edition.snapshot`은 `scope='stage'`면 그 단계, `scope='edition'`이면 그 판에 속할 때만 된다(아니면 `forbidden`). 가드가 있는 호출의 영수증은 `run_id`·`lease_id`·`fence`를, 사건은 `run_id`를 남긴다.
- **판·라운드**: `edition.create`는 `edition_no = max+1`, `status='draft'`, 정확히 6개 `pending` 단계(plan~publish, ordinal 1~6)를 만들고 `current_stage_id`만 plan으로 두며 활성 판을 바꾸지 않는다. `round.start`는 활성 판의 단계만 받고, ordinal이 더 작은 모든 단계가 `approved`이면서 `stale_since_event_seq`가 NULL이어야 하며(하나라도 아니면 `conflict`), 단계당 열린 라운드는 하나다. `round_no = max+1`, `base_snapshot_id`는 그 단계의 최신 봉인 스냅숏(없으면 NULL), 단계는 `active`가 된다. 승인된 단계라도 자기 `stale_since_event_seq`가 있으면 새 라운드를 시작할 수 있고, 신선한 승인은 `conflict`다.
- **봉인**: `round.seal`은 승인 전에도 가능하다. 판이 `active`이고 라운드가 `open`이며 manifest blob이 그 프로젝트의 `ready` blob이고 모든 `(object_id, version_id)`가 그 객체의 실제 버전일 때 한 tx로 `rounds.state='sealed'`·`sealed_snapshot_id`, `snapshots(scope='round')`, `round_contents(position 순서, role='result')`를 쓴다. `versions`는 비어 있을 수 없고(빈 목록은 `invalid_payload`), `content_hash`는 정확한 버전 목록과 순서의 함수라 같은 목록은 같은 해시, 다른 버전은 다른 해시다. 봉인은 승인이 아니다.
- **승인·reopen**: `stage.approve`는 판이 `active`이고 ordinal이 더 작은 모든 단계가 `approved`이면서 stale이 아니며, 그 단계의 현재 라운드가 봉인되었고 `sealed_snapshot_id`가 인자와 같을 때만 `approvals(origin='new', assurance='verified', actor_kind='human', tx_id=영수증)`를 남기고 단계를 `approved`로 만든다. 단계가 reopen되었거나 앞 단계 reopen으로 stale이면, 그 무효화 사건 이후에 봉인된 스냅숏만 승인에 쓸 수 있다(`snapshots.through_event_seq`가 무효화 `event_seq` 이상). 옛 봉인 스냅숏은 `conflict`이고 승인 행도 쓰지 않는다. 다음 단계가 `pending`이면 `asking`으로 열고 `editions.current_stage_id`를 옮기며, 마지막 단계면 판을 `completed`로 끝낸다. `stage.reopen`은 `active` 또는 `completed` 판의 `approved` 단계만 받아 그 단계를 `active`로 되돌리고, 뒤 단계 중 `pending`이 아닌 모든 단계의 `stale_since_event_seq`를 이 명령의 `stage.reopened` 사건 번호로 바꾼다. 승인 행과 뒤 단계의 `approved_snapshot_id`는 유지한다. 뒤 단계의 `queued`·`waiting_human`·`blocked_usage`·`interrupted` run은 `cancelled`(ended_at=now)로 끝내고 run마다 `run.invalidated` 사건을 남긴다. 뒤 단계의 `running` run도 `cancelled`(ended_at=now)로 끝내 `claim({run_id})`로 옛 기반에서 재개할 수 없게 하고, 그 run이 프로젝트의 활성·미만료 lease를 쥐고 있으면 같은 tx에서 lease를 `released`로 놓으며 `run.invalidated` 사건(run_id 포함)을 남긴다. 끝난 run은 그대로 둔다. 완료된 판은 같은 tx에서 `active`로 돌아간다. stale이 자기 사건을 가리키도록 이 tx에서만 `PRAGMA defer_foreign_keys=ON`을 쓰고, 사건은 서비스가 COMMIT 전에 쓴다.
- **완료 해제·스냅숏**: `edition.release_completion`은 `completed` 판만 `active`로 되돌리며, 완료가 아니거나 다른 활성 판이 있으면 `conflict`다. `edition.snapshot`은 `scope='edition'|'stage'` 스냅숏을 만들고, manifest blob·버전 검사와 해시는 봉인과 같다(빈 `versions`는 `invalid_payload`). `through_event_seq`는 그 명령이 실행될 때 존재하던 마지막 사건 번호, `control_rev`는 `projects.control_rev`다. 스냅숏 행은 나중에 새 버전이 생겨도 바뀌지 않는다.
- **이월 두 갈래**: `edition.carry_over`의 `kind='topic'`은 `artifacts(kind='topic')`의 정확한 `source_version_id`에서 새 artifact 객체·버전 1·`artifacts(origin_version_id=source_version_id)`·`version_relations(derived_from)`를 만든다. 원본과 그 뒤 버전은 바뀌지 않는다. `kind='tasks'`는 같은 판 안에서 `from_stage`보다 뒤 단계로만 이월하며(다른 판이면 `conflict`), 현재 버전이 `next_round_task`이고 `target_stage_id=from_stage`이며 상태가 `proposed`·`accepted`·`running`·`deferred`인 follow-up마다 `version_no+1`, `based_on_version_id=옛 버전`, 같은 kind/state/description/base/proposed, `target_stage_id=to_stage`, `target_round_id=NULL`인 새 버전을 붙이고 객체의 현재 포인터를 옮긴다. `applied`·`rejected`·`cancelled`는 이월하지 않고, `followups.origin_*`는 건드리지 않는다. 다음 라운드의 R1 목록은 `open_tasks_for_round`가 읽는다.
- **세 사건의 분리**: `run.complete`는 `run.completed`, `round.seal`은 `round.sealed`, `stage.approve`는 `stage.approved`를 남기며 서로의 상태를 바꾸지 않는다. 거부·검증 실패는 영수증도 사건도 남기지 않고, 모든 성공 명령은 영수증과 사건을 같은 tx에 남긴다.

### 8.8 질문·답(PR8)

`scripts/pes_core/commands/questions.ts`가 `question.publish_set`·`question.revise`·`question.withdraw`·`question.defer`·`question.merge`·`question.comment_add`·`answer.submit` 7개 명령을 정의하고, `scripts/pes_core/questions.ts`의 공개 함수는 각각 `CommandService.execute` 한 번만 호출한다. 읽기 전용 `validate_submission`·`resume_ready`는 직접 SQL을 읽기만 하며 쓰지 않는다. 질문·답 표의 INSERT/UPDATE는 `commands/questions.ts`에만 있다.

- **본 버전 고정**: 제출은 그 폼(`question_sets`)의 구성원과 사람이 실제로 본 질문 버전(`question_set_members.question_version_id`)에 고정된다. 질문이 그 뒤 개정되어 구성원 버전이 현재 버전과 다르면 낡은 폼으로 보고 `conflict`로 거부한다(아무것도 쓰지 않음).
- **개정·재확인**: `question.revise`는 새 질문 버전을 append하고 `objects.current_version_id`만 옮긴다. 옛 버전 행·옛 답·옛 폼 구성은 그대로 두며, 새 버전은 옛 답을 승계하지 않는다. `resume_ready`는 현재 답 버전이 `submitted`이면서 질문의 현재 버전에 고정된 경우에만 충족으로 본다. 옛 버전에만 답이 있으면 `needs_reconfirmation`, 답이 없으면 `unanswered`다.
- **덧붙임**: `other`(레거시 `__other`)는 답 값이 아니다. `allow_comment_as_answer=1`인 질문에서만 덧붙임만으로 답 버전(`value` JSON null)을 만들고, 아니면 답 없이 최소 `threads`/`messages`/`message_versions` 행으로만 보존한다. 새 질문 스펙에서 이 필드를 생략하면 0(덧붙임만으로는 답이 아님)이다. `__other`가 추천 선택지 동의로 바뀌지 않는다.
- **기본값·추천**: 서버는 답 초안을 만들지 않는다. `used_default`는 사람이 기본값을 골랐고 제출 값이 그 기본값과 같을 때만 1이며, 보내지 않으면 0이다. 추천 선택지는 평범한 선택일 뿐 자동 답이 되지 않는다.
- **묶음 원자성**: 한 제출의 제출 행·답 버전·의견 스레드는 한 tx다. 한 항목이라도 잘못되면 제출·답·의견·영수증·사건이 모두 롤백된다. 같은 키의 재요청은 저장된 결과를 재생하고, 실패한 시도는 영수증을 남기지 않아 같은 키로 다시 실행할 수 있다.
- **판·라운드 경계**: 게시는 stage의 판이 `active`이고 프로젝트의 활성 판과 같으며 라운드가 `open`일 때만, 제출은 세트의 판이 `active`이고 세트 라운드가 봉인되지 않았으며 그 `(stage_id, form_key)`의 최신 세트일 때만 된다. 아니면 `conflict`다.
- **필수 답**: `required=1` 질문에 빈 문자열·공백뿐인 문자열·빈 배열을 보내면 `invalid_payload`이고 묶음 전체를 거부한다.
- **읽기 함수 계약**: `resume_ready`·`validate_submission`은 행위자·멤버십을 스스로 확인하지 않는 읽기 함수다. 이들을 노출하는 API/CLI 층이 프로젝트 멤버십과 행위자를 먼저 확인해야 한다.
- **stage_start 세트**: `round_id`가 NULL인 stage_start 세트는 어느 라운드에도 속하지 않으므로 `resume_ready`의 라운드 재개 판정 밖이다.
- **행위자**: `question.publish_set`·`question.revise`·`question.withdraw`·`question.defer`·`question.merge`·`question.comment_add`는 사람 멤버 또는 활성 lease guard(`run_id`·`lease_id`·`fence`)를 가진 에이전트만, `answer.submit`은 사람만 실행한다. 에이전트는 lease가 있어도 답할 수 없다.
- **철회·보류·합치기(SEL-90 U2a)**: `question.withdraw`·`question.defer`·`question.merge`는 질문을 지우거나 고치지 않고 **새 질문 버전**(state `withdrawn`·`deferred`·`merged`, `defer_until`·`merged_into_question_id` 포함)을 append하며 `objects.current_version_id`만 비교 후 교체로 옮긴다. 옛 버전 행·옛 답·옛 세트는 그대로다. 전이표는 `open`→셋 모두, `deferred`→`withdrawn`·`merged`이고 나머지는 `conflict`(`reason=invalid_transition`)이며, 낡은 `base_version_id`는 `rev_conflict`다. merge 대상은 같은 프로젝트의 `open` 다른 질문이다(자기 자신 `invalid_payload`/`self_merge`, 없음·다른 프로젝트 `not_found`, 열려 있지 않음 `conflict`).
- **빠지는 세트**: 그 질문이 폼의 **최신 세트**에 있으면 같은 tx에서 그 질문만 뺀 새 세트(`version_no`+1, 남은 구성원은 폼이 고정한 버전·순서 그대로)를 발행하고 `question.set_published` 사건을 남긴다. 닫힌(봉인된) 라운드의 세트와 활성 판이 아닌 판의 세트는 새 세트를 만들지 않는다. 마지막 질문을 빼면 구성원이 0인 최신 세트가 생긴다 — `publish_set`은 질문 0개를 받지 않지만 이 빈 세트는 허용하는 정상 상태("폼 없음")이며, 읽는 쪽은 빈 `questions`를 처음 만날 수 있다. `answer.submit`은 빈 세트에 `invalid_payload`이고 `publish_set`의 `extend_latest`로 이어 붙이면 `version_no`가 계속 늘어난다.
- **순서: 존재 → 리스(SEL-90 R1)**: `question.revise`·`withdraw`·`defer`·`merge`·`comment_add`는 모두 (1) 본문 모양 검증 → (2) 질문 조회(이 프로젝트에 없으면 `not_found`, 누구에게나 같다) → (3) 행위자·리스 검사(리스 없는 에이전트는 `forbidden`) 순서다. 그래서 같은 토큰이 없는 질문에는 모든 명령이 404, 있는 질문에는 403이다. 프로젝트 밖의 질문 존재는 리스와 상관없이 알려지지 않는다. 본문 모양 검증(필수 필드 누락·`defer_until` 형식·`self_merge`)은 리스 검사보다 앞이라, 리스 없는 에이전트가 틀린 본문을 보내면 403이 아니라 400/422를 받을 수 있다(개정 이전부터의 규칙).
- **사건 이름**: 영수증 `action`과 사건 `type`은 `question.retracted`(`question.withdraw` 명령)·`question.deferred`·`question.merged`·`question.commented`다. 철회만 `withdrawn` 어간을 쓰지 않는 이유는 레지스트리 이름 시험(`test_command_service_hardening`)이 action 이름에 `raw`를 금지하는데 `withd-raw-n`이 걸리기 때문이다. 이 이름 4개는 `test_sel90_review_fixes`가 고정한다. 앱의 `touched` 규칙(`http-client-changes`)은 이 사건을 아직 모르고 `workspace`만 새로고침한다 — U2b에서 다룬다. 폼에서 빠지는 경우 함께 나가는 `question.set_published`가 라운드 보기를 덮는다.
- **의견은 답이 아니다**: `question.comment_add`는 `question_comment` 스레드·메시지만 쓰고 `answers`·`answer_versions`·`submissions`를 만들지 않는다. `resume_ready`는 `answer_versions.state='submitted'`만 본다.
- **묶음·개별 제출과 완료 판정**: `answer.submit`의 닫힌 필드 `mode`는 `bundle`(적용되는 필수 질문이 이번 제출 + 현재 답으로 모두 차야 접수, `show_if`가 거짓인 질문에 대한 답은 거부)과 `single`(정확히 1개 항목)이다. 응답의 `form_complete`·`missing_required`는 제출 뒤 적용되는 필수 질문이 모두 현재 답을 가졌는지의 판정일 뿐 라운드·단계 상태를 바꾸지 않는다. `resume_ready`도 같은 적용 판정을 쓴다 — `show_if`가 거짓인 필수 질문은 요구하지 않아 두 판정이 어긋나지 않는다(R1).
- **이어 붙이기**: `question.publish_set`의 `extend_latest=true`는 `(stage, form_key)`의 최신 세트에서 `open`인 질문을 같은 순서로 앞에 두고 새 질문을 뒤에 붙인 새 세트를 발행한다. 이어받는 대상은 최신 세트의 `round_id`와 상관없이 같은 `(stage, form_key)`의 최신 세트다 — 앞 라운드에서 풀리지 않은 열린 질문이 새 라운드의 폼으로 따라오는 것이 의도이고, 새 라운드의 답은 현재 질문 버전에 묶여 있어 이미 답한 질문을 `resume_ready`가 다시 요구하지 않는다. 철회·보류·합쳐진 질문은 따라오지 않는다.

### 8.9 legacy 이전(PR11)

`scripts/pes_core/commands/legacy.ts`가 `legacy.import_project` 하나를 정의하고, `scripts/pes_core/legacy.ts`의 `scan_project`·`import_project`·`map_legacy`·`report_unknown`이 공개 경계다. 이전 폴더는 **읽기만** 하며, 원본 삭제·수정·잠금 파일 생성 경로가 없다.

- **단일 tx·닫힌 명령**: `legacy.import_project`는 프로젝트가 아직 없는 `owner` 범위 명령이다. 실행자는 존재하는 사람 owner actor여야 하고(아니면 `forbidden`, 행 없음), `via='import'`와 한 tx로 프로젝트·owner 멤버·초기 정책(`policy_rev=1`, `reason='legacy default'`)·1판·6단계·라운드·스냅숏·승인·객체·버전·출처·질문·답·제출·스레드·이월·blob·`import_batches`·`legacy_mappings`·사건·영수증을 남긴다. 그 밖의 업무 표 쓰기 SQL은 이 명령 파일에만 있다(blob·`file_policies`·`version_files`는 아래 파일 항목처럼 PR9 정의를 재사용한다).
- **멱등**: `source_fingerprint`(폴더 manifest의 sha256)가 같으면 기존 배치를 그대로 돌려주고 새 행을 쓰지 않는다. 같은 요청 키의 재실행은 서비스 영수증 재생으로 끝나며, 실패 배치도 `failed`로 재생된다. 원본이 바뀌면 새 지문·새 배치다.
- **활성화 없음**: 배치는 항상 `staging`(또는 `failed`)이고 프로젝트도 `staging`이다. `complete=true`는 1판을 `completed`로 끝내고 활성 판 포인터를 NULL로 둘 뿐, 프로젝트를 활성화하지 않는다. 검증·활성화는 PR12가 맡는다. `complete=true`인데 publish 단계가 `approved`가 아니면 승인 행을 만들지 않고 판만 `completed`로 두며 `edition.settings_json.legacy_extra.legacy_unverified`로 표시한다(시험 4l 해석, map 59행과 차이).
- **정직한 표식**: 옛 승인은 `origin='legacy'`·`assurance='legacy_unverified'`·`actor_kind='legacy_unknown'`·`human_user_id=NULL`이고, 모든 이전 객체 버전은 `legacy_unknown` actor가 쓴다. `feedback.who`에서 가짜 사람을 만들지 않으며, 초기 정책 기본값을 과거 동의(결정·가정·답·`new` 승인)로 기록하지 않는다. 미지 값은 `legacy_extra`/`report_blob_id` 보고서에 남긴다.
- **파일**: blob·`file_policies`·`version_files` 쓰기는 PR9 `commands/files.ts` 명령 정의를 같은 tx 안에서 재사용한다. 예약→저장→완료 순서로 저장소 바이트를 다시 읽어 측정하고, 측정이 예약과 다르면 ready가 아니라 `quarantined`다. `project.json.tmp`는 본 파일과 다르면 격리하고 채택하지 않는다. `.pes-lock`·`.pes-port`·`.pes-server`와 재생성 파일은 manifest의 경로·sha256에만 두고 blob으로 만들지 않으며 fingerprint에서도 제외한다. tx가 늦게 실패해 남은 고아 객체 파일은 `file.gc_orphans`로 정리한다. `map_legacy`·`report_unknown`은 `get`/`all`과 blob 읽기만 하는 읽기 전용이며, 이전 폴더의 절대 경로는 결과·사건·보고서에 남지 않는다.
- **이월**: `carry_over[]`는 `next_round_task`·`state='proposed'`·`target_round_id=NULL`로 보존한다. `target_stage_id`는 `from`이 아니라 **담은 단계의 다음 단계**(plan→research→analyze→write→verify→publish)이고, `base_artifact_version_id`는 담은 단계 항목의 이전 버전이다. `from` 원문은 `stages.settings_json.legacy_extra.carry_over`에 남긴다. publish처럼 다음 단계가 없으면 행을 만들지 않고 원문을 보고서에 남긴다. 다음 R1 조회는 PR6 `open_tasks_for_round`가 읽는다.
- **스냅숏·질문·라운드 파일(최종 리뷰 1/2)**:
  - 정상 스냅숏의 `state.items`는 당시 항목 버전으로 옮기고 그 라운드 `round_contents`가 정확한 버전을 가리킨다. 현재 항목과 canonical record가 같으면 현재 버전을 재사용하고, 다르면 같은 객체의 과거 버전(`version_no` 앞쪽, 현재가 마지막)으로 두며 출처·연결도 그 버전에 붙인다. 깨진 스냅숏은 추측하지 않는다.
  - 질문 내부 키는 폼·발생 위치로 구분한다. 같은 단계·id·record의 질문만 명시 재사용하고, 내용이 다르면 별도 객체다. 세트 구성원과 `legacy_mappings`는 각 폼의 정확한 버전이다. `review.questions`도 폼으로 색인해 `feedback`의 kind·spec·stage·round로 실제 본 세트를 찾아 답·`__other` 덧붙임을 연결하고 제출에 그 세트를 단다. 찾지 못할 때만 import placeholder를 만든다.
  - `items[].path`는 안전한 상대 경로만 읽어 `rendered`로 연결하고, 없거나 안전하지 않으면 `missing_file`과 `legacy_extra.missing_paths`로 남긴다(안전하지 않은 경로는 중립화).
  - `rounds/<stage>-R<n>/qa.json`은 그 라운드 review artifact(`metadata.qa`)다. 결과 JSON은 canonical hash가 항목 record와 같을 때만 `source`로 연결하고, 아니면 원문 blob만 두고 `unmapped_input`으로 보고한다.
  - 출처·`user_links`의 미지 하위 필드는 `locator.legacy_extra`에 보존하고 JSON 포인터로 `unknown_field`를 남긴다.

### 8.10 이전 검증·활성화·되돌리기(PR12)

`scripts/pes_core/migration.ts`가 공개 경계(`validate_import`·`activate_import`·`rollback_before_write`·`restore_project`·읽기 전용 `serving_path`)이고, 쓰기 SQL은 `scripts/pes_core/commands/migration.ts`의 닫힌 명령 4개(`legacy.validate_import`·`legacy.activate_import`·`legacy.rollback_before_write`·`legacy.restore_project`)에만 있다. 모두 `owner` 범위 명령이며 실행자는 **그 프로젝트의 사람 owner**여야 한다(에이전트·옛 작성자·다른 프로젝트의 사람·모르는 actor는 `forbidden`, 행 없음). 한 단계 = `service.execute` 1회 = 한 tx. 호출마다 새 요청 키를 쓰므로(검증은 다시 돌릴 수 있어야 한다) 영수증 재생에 기대지 않고, 상태 전이표가 중복 실행을 `conflict`로 막는다.

- **상태 전이**(스키마 값만 쓴다, `rolled_back` 없음):

  | 명령 | 배치 상태 → | 프로젝트 |
  |---|---|---|
  | validate (문제 없음) | staging·validated → validated | staging |
  | validate (문제 있음) | staging → staging, validated → **staging**(더는 믿을 수 없다) | staging |
  | activate | validated → activated | active |
  | rollback_before_write | staging·validated·activated(새 쓰기 없음) → **failed** | **archived** |
  | restore_project | 번들 시점의 상태로 | 번들 시점의 상태로 |
  | 그 밖 | `conflict`, 아무것도 안 바뀐다 | |

  failed·activated 배치의 validate, staging 배치의 activate, failed 배치의 rollback은 `conflict`다. 같은 원본을 다시 가져오면(PR11) 영수증 재생이 옛 결과(staging)를 돌려주므로, `import_project`가 `CommandService.read`(SELECT 전용 핸들, 내부 전용 — HTTP로 노출하지 않는다)로 **현재 배치 상태**(`staging`·`validated`·`activated`·`failed`)를 읽어 알린다. rollback된 배치는 `failed`이며 되살리지 않는다. 되돌린 프로젝트는 slug를 그대로 쥐고 있어 **같은 slug로는 다시 가져오지 못한다**(새 배치가 `slug_conflict`로 `failed`) — 고친 원본을 다시 가져오는 흐름은 PR22 전에 정한다.
- **validate_import**: `import_batches.source_fingerprint`가 지금 원본 폴더의 지문과 같을 때만 비교한다(다르면 `source_changed` 문제만 나열). 같으면 원본에서 다시 만든 계획(`build_validation_plan`, 읽기 전용)을 DB와 맞춘다. `counts`(표·단계별·역할별 개수, 프로젝트 전체 `blobs`와 `submissions` 개수 — 계획에 없는 blob·제출이 더 있으면 문제)·`bodies`(제목·요약·본문·질문·답·메시지·이월 설명을 hash로, 버전 `content_hash`)·`ids`(계획의 모든 `legacy_mappings`가 같은 자리로 풀리는지, 배치의 모든 mapping 행이 실제 행으로 풀리는지)·`links`(관계·인용·라운드 내용·이월·스레드·세트 구성원이 같은 프로젝트의 행을 가리키는지에 더해, 원본 계획의 연결을 계획 키→실제 ID로 풀어 대조한다 — 답의 질문·질문 버전·제출, 스레드의 대상 객체·버전·맥락, 메시지(와 그 버전)의 스레드·제출, 라운드 내용의 라운드·객체·버전·위치, 세트 구성원, 이월의 대상 단계·기준 버전. 존재만 하는 다른 유효한 대상은 문제다)·`footnotes`(`citation_no`)·`files`(blob 행 ↔ 원본 바이트 sha256/크기, 디스크 파일 바이트, 첨부 행)·`unprocessed_answers`(`processed`에 없는 `feedback/*.json`의 제출·답 개수)·`reports_regeneration`(`reports/<단계>/report.md·html`을 다시 만들어 비교; **보고만, 문제가 아니다**)·`source_changed`. 문제가 있어도 던지지 않고 `ok=false`와 문제 목록(최대 500)을 돌려주며 사건 `legacy.import_validation_failed`를 남긴다. 사건·결과에는 원본의 절대 경로를 넣지 않는다. 보고서 재생성은 PR16 TS 보고서 생성기 전까지 같은 계획에서 만든 구조만 같은 최소 형태라 옛 보고서와는 대개 다르다(`matches=false`). 그래서 결과에 `regeneration_format: "provisional"`을 붙여 임시 형식의 비교임을 알리고, PR16이 실제 생성기로 바꿀 때 불일치를 문제로 올린다.
- **activate_import**: 검증을 통과한(validated) 배치만. 직전 `legacy.validate_import` 영수증 뒤에 `legacy.*`가 아닌 업무 쓰기가 그 프로젝트에 있으면(project 명령은 프로젝트 상태를 보지 않으므로 staging 프로젝트에도 쓰기가 들어갈 수 있다) `conflict`이며 다시 검증하라고 안내한다. 백업 폴더가 PES 홈 안·그 부모, OneDrive 폴더(경로 마디가 `OneDrive…`), 객체 저장소 안이면 `invalid_payload`이고 아무것도 쓰지 않는다. 같은 tx 안에서 **그 프로젝트 하나**를 PR3 번들로 내보내(`export_project_in_tx`, 상태를 바꾸기 전 모습) `verify_bundle`로 확인한 뒤에야 상태를 바꾼다. manifest는 번들이 자기 자신과 맞는지만 보이므로, 내보내기 전에 프로젝트의 모든 객체 파일이 `blobs` 행의 sha256·크기와 같은지 보고(다르면 `conflict`, 백업 폴더도 만들지 않는다) 내보낸 번들의 객체도 번들 안 `blobs` 행과 대조한다(`assert_objects_match_blob_rows`). 번들을 못 쓰면 활성화되지 않는다. 경로는 모두 인자로 받고 환경 변수·`~/`·실제 홈은 읽지 않는다. `pes_home`은 호출 계층(PR14 API·CLI)이 설정값에서 채운다 — 서비스는 `objects_dir`만 알아 그 값이 맞는지 검증할 수 없다.
- **rollback_before_write**: 활성화 뒤 새 쓰기(영수증 `legacy.*`가 아닌 `mutation_commits`)가 하나라도 있으면 `conflict`이며 `restore_project`를 안내한다. 이전 증거(`legacy_mappings`·staging 행)는 지우지 않고 보관한다. 원본 폴더는 건드리지 않는다.
- **restore_project**: 프로젝트 하나를 PR3 번들의 상태로 되돌린다. 번들은 `verify_bundle`·manifest·행·blob 행↔객체 파일 대조(경로뿐 아니라 객체 바이트의 sha256·크기가 번들 안 `blobs` 행과 같은지 — manifest만 고쳐 맞춘 번들은 거부, DB·파일·커서 불변)를 통과해야 하고(다른 프로젝트의 번들·다른 DB의 번들·손상·없는 번들은 거부), 한 tx 안에서 그 프로젝트의 행만 지우고 번들 행을 넣는다(다른 프로젝트는 그대로, `users`·`actors`는 비교도 교체도 하지 않고 지금 행 그대로 둔다 — 이름이 바뀌거나 비활성화돼도 복원이 막히지 않고, 없는 행만 더한다. `database_instance_id` 유지, `cursor_epoch + 1`). 전부 아니면 전무: 외래 키가 깨지면 파일을 만지기 전에 거부한다. 객체 파일은 PR9 helper로 번들 바이트에 맞춘다: ① 다른 파일을 모두 같은 폴더의 임시 파일에 먼저 쓴다(tx 안 — 하나라도 실패하면 임시 파일을 지우고 행도 롤백하므로 원래 파일은 그대로) ② 행이 커밋된 뒤에만 rename으로 바꾸고 번들에 없는 파일을 지운다. 번들에 없는 항목 정리는 gc의 best-effort helper가 아니라 복원 전용 `sweep_project_files_strict`로 한다: 번들에 없는 파일은 지우고, 지우지 못한 파일·읽지 못한 폴더·번들 키로 이어지지 않는 폴더·링크는 이상 상태로 보고 손대지 않은 채(재귀 삭제 없음) 실패 목록에 올린다. 커밋 뒤 rename이나 이 정리가 실패하면 `conflict`로 알리며 `details`에 `rows_restored: true`, `failed_files`와 함께 `lost_writes`·`reverted_steps`·`cursor_epoch_before`·`cursor_epoch_after`를 담는다(사건 `legacy.project_restored`에도 `lost_writes`가 남는다). 같은 번들로 복원을 다시 하면 파일을 마저 맞춘다(그때 결과의 `lost_writes`는 첫 복원에서 이미 사라졌으므로 비어 있다). **전제**: 복원은 `pes stop`(서버·CLI가 DB를 열고 있지 않은 상태) 뒤에 한다. 행 커밋과 파일 교체 사이에 중단되면 행은 번들, 파일은 옛것인 채로 남으므로 같은 복원을 다시 실행한다. 결과는 번들 뒤에 있던 업무 쓰기(`lost_writes`, 오래된 순)와 함께 되돌려진 이전 단계(`reverted_steps`, 예 `legacy.activate_import`), 커서 세대 전후(10진 문자열)를 알린다. 번들 뒤의 감사 기록(영수증·사건)은 번들의 것으로 바뀌므로 복원 사건 `legacy.project_restored`에 손실 목록을 함께 남긴다. 활성화 직전 번들로 돌아가면 파일럿 이후 기록이 사라진다.
- **복원 사전 검사**: 객체 저장소 루트·프로젝트 폴더 검사(`files.ts`의 `project_folder`, gc·blob 삭제·복원 정리와 같은 규칙)는 복원 tx 안, 파일 준비 직전에 한다. 링크·디렉터리 아님·그 밖 lstat 오류면 `conflict`로 거부하고 tx가 롤백되어 DB·커서·파일은 그대로다. 루트나 프로젝트 폴더가 없으면(ENOENT) 거부하지 않는다 — 객체 있는 번들은 쓸 때 루트를 만들고, 빈 번들은 만들지 않는다.
- **TOCTOU 한계**: 검사와 삭제·쓰기 사이에 다른 프로세스가 폴더를 링크로 바꿔치기하는 경우는 막지 못한다(Node에 openat·O_NOFOLLOW 경로가 없다). 단일 사용자·`pes stop` 뒤 복원이라는 전제로 이 경쟁을 배제한다.

### 8.11 API 층이 기대는 보장 (PR14)

- **새 코어 명령 2개**: `project.register`(project token 없는 최초 등록. 프로젝트·owner·초기 정책·첫 판에 더해 기기 actor(`external_agent`, owner의 user)와 첫 토큰을 **한 tx**로 만든다. 영수증은 토큰 원문 없이 저장하고 재생은 토큰을 다시 주지 않는다. 범위는 `project.bootstrap`과 같다)와 `run.cancel`(owner 또는 그 run의 actor만. queued 포함, 끝난 run(`succeeded`·`failed`·`cancelled`·`interrupted`)은 `conflict`). `run.interrupt`·`run.handoff`는 owner가 현재 lease를 대신 풀 수 있게 넓혔다. owner가 남의 run에 쓰는 영수증은 `mutation_commits`의 `(run_id, actor_id) → runs` 외래 키 때문에 `run_id`를 비우고 run은 결과·사건에만 적는다.
- **HTTP 인계는 같은 run 반납이다**: `POST P/runs/{r}/handoffs`는 코어 `run.handoff`로 현재 lease를 풀고 **같은 run을 `queued`로 되돌린다**. child run도, `parent_run_id`도 만들지 않는다. 이어받기는 다음 `claims`가 하고(새 lease·새 fence), `parent_run_id`를 둔 새 run은 코어 claim 경로에만 남는다. 8.3의 parent 사슬과 stage-6 M3의 `parent_relation 'handoff'`는 그 claim 경로의 이야기이고 HTTP 계약은 이 줄이 기준이다. 같은 run이므로 actor·mode가 바뀌지 않는다: `target_actor_id`·`target_mode`는 생략하거나 그 run의 actor·mode와 같아야 하고, 다르면 400 `invalid_payload`(그 필드가 `target`, 쓰기 0)로 거부한다(효력 없는 대상 변경에 200을 주지 않는다). 다른 명령이나 다른 run에 쓴 `Idempotency-Key`를 handoffs·interrupt에 다시 쓰면 409 `idempotency_key_reuse`다.
- **답 제출은 사람만**: `POST P/submissions`는 소유자 사람 세션만 받는다(에이전트는 403 `human_required`, 8.8의 `answer.submit`). 답이 핀한 `question_version_id`가 그 질문의 **현재 버전**이면 세트가 고정한 옛 버전이어도 받는다(폼이 본 버전 기준). 다른 질문의 버전 id를 핀하면 409로 거부하고 아무것도 쓰지 않는다.
- **register 응답을 잃었을 때**: `project-registrations` 재생은 토큰을 다시 주지 않고 `data.token_issued_before: true`를 준다. 복구는 소유자가 같은 기기 actor에 새 토큰을 발급하는 것이다(토큰 발급 HTTP 경로 `agent-tokens`는 2단계에 없으므로 로컬 소유자 도구로 한다).
- **답·질문 버전 읽기 범위**: `GET P/objects/{o}/versions/{v}`로 답·질문 버전을 읽는 것은 같은 프로젝트의 `context:read` 구성원에게 열린다(질문을 낸 run의 actor로 좁히지 않는다). 다른 버전 읽기와 같은 규칙이다 — AI 참조 금지 표지·`internal_ai`의 Go 규칙도 똑같이 적용된다.
- **받기만 하고 저장하지 않는 필드**: `heartbeat`의 `progress`, `submissions`의 `submitted_via`·`client_request_id`는 형식만 검사하고 저장하지 않는다(`via`는 서버가 정하고, 멱등 키는 헤더 `Idempotency-Key`가 진짜다). 반대로 저장하지 않는 값이 결과를 바꾸는 필드 — `questions`의 `direction: "human_to_agent"`, `rounds`의 `purpose`·`question_set_id` — 는 받아 놓고 버리지 않도록 400 `invalid_payload`로 거부한다.
- **세션 비밀·커서 키**: `PES_LOCAL_SESSION_SECRET` → `~/.pes/config.json`의 `local_session_secret` → `~/.pes/local_session_secret`(처음 필요할 때 한 번 만드는 0600 한 줄 파일) 순으로 쓴다. 요청마다 새로 뜨는 브리지 프로세스가 모두 같은 키로 커서를 서명·검증하므로 `next_cursor`를 다음 요청에 그대로 쓸 수 있다. 원문은 응답·로그에 나가지 않는다.
- **서버 요청 예산의 '검증됨' 승격**: `serve.py`는 자격(토큰·세션)이 검증되기 전까지 모든 `/api/v1` 요청을 서버 전체 거친 버킷 하나(에이전트 분당 한도×5)로 센다. 그 자격을 자기 예산으로 옮기는 근거는 Node 브리지가 응답 밖에 붙이는 내부 표지 `credential_verified`(그 요청에서 자격 검증을 통과했을 때만 true) 하나다. 표지는 브리지 출력 JSON의 필드라서 클라이언트 헤더·본문에 나가지 않는다. 인증 전에 나오는 404(라우트 없음)·405·401·자격 확인 전 입력 오류(400)는 표지가 false라 가짜 자격을 승격하지 않고, 401은 승격을 지운다. Node의 429(`rate_limited`)는 자격 확인(`#credential`)을 통과한 뒤 `#spend`에서 나므로 표지가 true다.
- **202 operation은 새 표가 아니다**: 영속 접수는 interrupt·cancel의 **영수증 id**(`mutation_commits.id`)가 operation id다. `GET P/operations/{id}`·`GET P/requests/{key}`는 영수증을 읽으므로 서버를 다시 시작해도 같은 답을 준다. 커밋이 실패하면 영수증이 없어 202도, operation도 없다.
- **변경분 커서**는 서버가 서명한 불투명 값이다: 프로젝트·호출자 종류·`database_instance_id`·`cursor_epoch`·마지막 `event_seq`에 묶인다. 한 tx의 사건은 한 쪽에 모두 나가고, 에이전트에게 숨기는 사건(`token.*`)은 건너뛰되 커서는 끝까지 움직인다. epoch나 DB 인스턴스가 바뀌면 410 `cursor_expired`(쓰기 없음).
- **입력 읽기는 읽는 순간의 자격으로**: `GET P/runs/{r}/inputs`는 입력을 읽는 짧은 read tx마다(대기 전·대기 뒤 각각) 토큰·actor·멤버십·범위, run 소유, run 목적지의 Go 정책(호출자 종류가 아니라 **run의 mode가 A면** Go ON 필요)을 다시 확인하고 커서도 그 tx의 DB 메타데이터로 검사·발급한다. 대기 중 토큰 회수·Go OFF·멤버십 제거가 커밋되면 대기하던 요청도 새 요청과 같은 401·403으로 끝나고 입력은 나가지 않는다. 입력 항목의 `object_id`는 답 object이고, `GET P/objects/{object_id}/versions/{input_version_id}`의 `content`가 답 본문(`question_version_id`·`value`·`state`(답 버전 상태)·`comment`)이다. 질문 버전의 `content`는 `text`·`type`·`state`·`importance`·`required`·`allow_comment_as_answer`·`default_value`·`options`·`show_if`·`help`다. 권한·소속·Go 규칙은 다른 버전 읽기와 같다.
- **입력 영수증 묶음**(`run.record_receipt`의 `receipts` 1~20개)은 전부 아니면 전무이며 영수증 한 줄을 남긴다. `round.start`는 stage의 상태 변화를 별도 사건(`stage.activated`)으로 남긴다.
- **낙관적 확인 필드**(`expected_stage_rev`·`base_stage_rev`·`expected_round_rev`·`expected_policy_rev`·`base_version_id`, 답의 `question_version_id`)는 명령 안에서 비교하므로 읽기와 쓰기 사이에 끼어들 틈이 없다. 요청 한도·poll 간격은 프로세스 메모리의 예산이며 DB에 쓰지 않는다.
- **시험 전용 조이기 변수**: `PES_API_BUDGET_TEST_OVERRIDE`(JSON 객체)가 있으면 `serve.py`가 Node `--limits`로 받은 정책을 예산에 넣기 직전에 덮어쓴다. 받는 키는 요청 개수 한도 4종 `agent_requests_per_minute`·`agent_control_requests_per_minute`·`owner_requests_per_minute`·`coarse_requests_per_minute`뿐이고(`window_ms`·`min_poll_interval_ms`는 줄이면 오히려 한도가 풀리므로 받지 않는다 — 모르는 키와 같이 기동 거부) 값은 **기본값 이하의 양의 정수만**(조이기만 가능, 풀 수 없음)이다. 모르는 키·정수 아님·0 이하·기본값 초과·JSON 아님이면 서버가 뜨지 않고 오류 메시지와 함께 종료한다(조용히 무시하지 않는다). 변수가 없으면 기본값 그대로다. 변수가 있을 때만 시작 때 `--limits`를 한 번 불러 기본값과 견준다.

### 8.12 CLI 쓰기 전환(PR15)

개발 플래그 `PES_DB_CORE=1`일 때만 `scripts/pes.py`의 쓰기 19개와 새 5개(`context`·`claim`·`submit`·`wait`·`complete`)가 DB 경로를 탄다. 플래그가 없으면 v0.15 동작(`project.json`·`.pes-lock` 직접 쓰기, DB를 만들지 않음)이 그대로이고 새 5개는 거부된다. Python은 TypeScript를 import하지 않고, 명령마다 `scripts/pes_core/cli_bridge.ts`를 프로세스로 한 번 실행해 JSON 한 쌍(stdin 요청·stdout 답)으로만 주고받는다(`api_bridge.ts`와 같은 방식). 브리지는 업무 SQL이 없고 공개 함수(`editions.ts`·`content.ts`·`files.ts`·`questions.ts`·`records.ts`·`runs.ts`·`results.ts`)와 `CommandService`만 부른다. 영수증의 `via`는 `cli`다.

- **자격**: `PES_TOKEN` 없음 = 그 프로젝트의 사람 소유자(DB의 사람 owner actor). `PES_TOKEN=<토큰>` = `verify_agent_token`을 통과한 에이전트 actor이며, 새 5개는 각자의 범위(`context:read`·`run:claim`·`run:submit`)를, 그 밖의 쓰기는 `run:submit`을 요구한다. 사람 전용 명령(`approve`·`reopen`)과 `lock --force`는 토큰 보유자에게 거부된다(서비스의 `require_human_owner_actor`, 그리고 `--force`는 브리지에서도). `PES_OWNER`(세션 ID)는 자격이 아니라 잠금 표지다. 엉터리 토큰·만료·다른 프로젝트 토큰은 모두 거부이고 아무것도 쓰지 않는다. `init`은 이 컴퓨터의 사람만 하는 일이라 `PES_TOKEN`이 주어지면(유효한 토큰이라도) 검증 전에 거부하고 프로젝트·사람·판·정책·영수증·폴더를 만들지 않는다 — 프로젝트 범위 토큰에는 프로젝트·소유자 생성 권한이 없다.
- **DB에 없는 프로젝트**: 슬러그가 `projects`에 없으면 모든 쓰기는 거부되고 옛 `project.json`은 바이트·mtime이 그대로다(이전은 PR11·12 몫).
- **잠금 = run lease**: `lock`은 `run.claim`(mode B, runtime `pes-cli`, `runs.external_session_ref`=세션 ID, lease 2시간), 같은 세션의 재`lock`은 `run.heartbeat`(fence 그대로), `unlock`은 `run.complete`다. 다른 세션이 쥔 활성 lease가 있으면 `lock`·`unlock`과 모든 쓰기가 종료 3으로 거부되고 영수증이 없다. `lock --force`는 사람 소유자만, 옛 run을 `run.interrupt`로 끝내고 새 claim(fence +1)을 한다. 같은 세션의 쓰기는 마지막 기록이 30분보다 오래되면 lease를 heartbeat로 늘린다. 세션 ID 없는 `lock`은 종료 2다. 에이전트가 쥔 lease(세션 표지 없음)도 소유 actor가 아닌 쪽의 쓰기를 막는다.
- **내용 쓰기의 lease 규칙**: `round-start`·`render`·`approve`·`reopen`·`merge`·`note`·`chat`·`mark`·`qa`·`qa-brief`·`ask`·`ask-prep`은 (가) 토큰 에이전트(kind가 human이 아닌 actor)이면 **자기 소유의 활성 lease가 있을 때만** 쓸 수 있다 — lease가 없으면 `forbidden`, 남의 lease가 있으면 종료 3이고 둘 다 영수증이 없으며 거부가 lease를 만들지 않는다. 서비스가 에이전트에게 guard를 요구하는 명령(`round.seal`·`question.publish_set`)에는 그 lease의 run·lease·fence를 payload에 실어 서비스의 lease 검사를 지나게 한다. (나) 사람 소유자는 lease 없이도 쓴다(원칙 0). (다) 사람이 `PES_OWNER`를 붙여 쓰면 v0.15의 암묵 잠금처럼 lease가 없을 때 그 쓰기가 lease를 `claim`으로 잡고(`lock`을 따로 부르지 않아도), 같은 세션의 쓰기는 같은 lease를 쓰며(fence 그대로), 다른 세션의 쓰기는 종료 3이다. `PES_OWNER`가 없는 사람 쓰기는 lease를 만들지 않는다. 잠금 확인·암묵 claim·heartbeat와 명령은 한 단위라서 거부된 쓰기가 lease를 남기지 않는다.
- **새 코어 명령 6개**(새 표·마이그레이션 없음, 닫힌 등록표): `commands/records.ts`의 `project.add_note`·`input.record_chat`·`qa.record`·`qa.record_brief`는 `artifacts`(kind `note`/`review`)에 append-only 한 버전을 한 개 쓰고 역할은 `metadata_json.role`(`handoff_note`·`chat_input`·`qa_result`·`qa_brief`)에 둔다. `input.mark_processed`와 `commands/questions.ts`의 `question.prepare_draft`는 영수증과 사건만 남긴다(처리 표시·초안 준비 사실; 질문 초안 본문은 에이전트가 고치는 작업 파일이고 답을 채우지 않는다). 모두 사람 멤버 또는 토큰 actor면 되고, 거부는 영수증도 사건도 남기지 않는다. `render`의 봉인 목록(manifest)은 **활성 판의 그 단계** `artifact`(kind가 `note`·`review`가 아닌 것)의 현재 버전과, 그 현재 버전이 인용하는 `source`의 현재 버전이다. 다른 단계 항목·단계가 지정되지 않은(`stage_id` NULL) 항목·옛 판 항목·메모·검토 기록은 라운드 스냅숏에 들어가지 않는다 — 그 단계 항목이 없으면 봉인할 것이 없다는 `conflict`다. `qa.record`의 `qa` 객체는 버전 메타데이터에 통째로 들어가므로 JSON 길이가 `MAX_TEXT`(10만 자)를 넘으면 `invalid_payload`로 거부한다.
- **승계하지 않은 우회**: 봉인 없는 `approve`, 한 번도 열지 않은 단계의 `reopen`, 이미 승인한 단계의 두 번째 `approve`, 토큰 보유자의 `approve`·`reopen`·`lock --force`는 거부된다(옛 CLI는 모두 통과). `approve`는 현재 라운드의 봉인 스냅숏만 승인한다.
- **`pes home`·`remote`·`serve`·`stop`**: 기계 단위 설정이라 프로젝트 상태 쓰기가 아니다. `home`은 프로젝트 폴더(옛 `project.json` 폴더와 DB에 있는 프로젝트 폴더)와 서버만 옮기고, 다른 세션의 잠금이나 에이전트가 쥔 활성 lease(세션 표지 없음 포함)가 있으면 `--force` 없이는 종료 3으로 거부한다. `~/.pes/pes.db`·객체 폴더·DB 행은 건드리지 않는다. 목록(`list`·`hub`)은 PR16에서 DB 프로젝트를 함께 보이고, 화면(index.html)은 PR18 몫이다.
- **한 CLI 호출 = 한 단위**: `merge`·`approve plan`·`init --import`처럼 코어 명령을 여러 번 부르는 호출은 브리지가 바깥 트랜잭션 하나 안에서 실행한다(코어의 `tx()`는 중첩을 거부하므로, 단위 안에서는 각 명령의 BEGIN/COMMIT/ROLLBACK이 SAVEPOINT/RELEASE/ROLLBACK TO로 바뀐다). 명령마다 영수증은 따로 남지만 어느 하나라도 거부되면 단위 전체가 되돌아가 부분 쓰기가 없다. 항목은 쓰기 전에 모두 검사한다(객체가 아닌 항목, 모르는 `status`·`confidence` 값은 종료 2로 거부하고 아무것도 쓰지 않는다 — 모르는 값을 `done`으로 바꾸지 않는다). `render`는 blob 예약·바이트 저장·완료·봉인을 한 단위로 묶어, 봉인이 거부되면 blob 행과 영수증이 남지 않는다. 이미 디스크에 쓴 manifest 파일은 되돌릴 수 없지만 가리키는 행이 없는 고아 파일이라 다음 `file.gc_orphans`가 지운다. 단위 안에서 명령이 미룬 외래 키(`PRAGMA defer_foreign_keys`)는 바깥 COMMIT에서야 검사되는데, 그 위반은 `internal_error`가 아니라 `conflict`(`ApiError`)로 번역되고 단위 전체가 되돌아간다.
- **merge의 의미(v0.15와 같음)**: 같은 항목의 두 번째 병합은 새 판을 `content.append_version`으로 더한 뒤 `content.set_current`로 항목의 현재 판으로 올린다(render가 봉인하는 것·다음 병합의 기준). `conflicts`·`links`·`shots`도 라운드를 지나며 v0.15처럼 누적한다 — `conflicts`·`shots`는 JSON 같음으로 중복을 빼고 순서를 유지하는 합집합, `links`는 키별 합집합(스칼라 값은 한 개짜리 목록으로 본다)이며 앞 판의 값을 지우지 않는다. 출처는 라운드를 지나며 URL 중복 없이 누적되지만, 집필 단계(`write`)이거나 `kind`가 `section`인 원고에 `sources`를 주면 각주 번호가 출처 순서를 가리키므로 목록을 통째로 바꾼다(중복 제거 없음, 빈 목록이면 비움). `id`가 없는 항목은 그 단계 항목의 최댓값 + 1을 받는다.
- **approve plan = 승인 + 조사 항목 인계**: 인계는 승인하는 봉인 스냅숏(그 라운드의 `round_contents`와 각 행의 `version_id`)을 읽는다 — 봉인 뒤에 병합한 수정·새 항목·삭제 표시 변경은 인계에 쓰지 않는다. 옛 `handoff_plan`처럼 기획 단계에서 `kind`를 `topic`으로 병합한 항목(삭제 표시 제외; `kind`가 없거나 다른 항목은 넘기지 않는다) 중 조사 단계 항목의 `links.plan`에 아직 없는 것마다 조사 단계에 `topic` 항목(상태 `new`, 질문 = 기획 항목의 질문 또는 요약, `links.plan` = [기획 항목 id])을 하나씩 만든다. 승인과 인계가 한 단위라서 어느 쪽이 거부돼도 둘 다 남지 않고, 다시 열었다 승인해도 이미 넘긴 항목은 중복으로 만들지 않는다(`links.plan`이 누적되므로 조사 항목에 다른 기획 링크를 병합해도 풀리지 않는다). `approve plan`은 옛 CLI와 같은 `조사 항목 N개 생성 (기존 조사 재사용 M개)` 줄을 출력한다(M은 위 한계로 항상 0).
- **`lock --force`**: 사람 소유자는 에이전트가 쥔 활성 lease도 가져온다(`run.interrupt` + 새 claim, fence +1). 잠금 조회·interrupt·claim이 한 단위이고 세션 ID 길이(200자 이하)는 바꾸기 전에 검사하므로, 새 claim이 거부되면 옛 run·lease·영수증이 그대로다(`lock`·`unlock` 모두 한 단위). `run.interrupt`는 lease 보유자 본인 또는 사람 프로젝트 소유자만 정확한 run·lease·fence로 부를 수 있고, 남의 run을 끊은 영수증은 run을 칼럼이 아니라 result에 적는다(영수증의 run은 같은 actor의 run이어야 하는 외래 키). 에이전트 토큰의 `--force`는 계속 거부된다.
- **`init --slug`**: DB의 슬러그와 이후 명령이 쓰는 폴더 이름이 같아야 프로젝트를 다시 찾을 수 있으므로 `--slug`가 폴더 이름과 다르면 종료 2로 거부하고 프로젝트도 폴더도 만들지 않는다.
- **`init --import`**: DB 쪽 검사(중복 이름·참고자료 거부 사유)를 먼저 하고, 통과한 뒤에야 프로젝트 폴더와 `library/shots`를 만든다. 거부되면 폴더에 아무것도 남지 않는다. 브리지의 `init`도 프로젝트 생성과 참고자료 가져오기가 한 단위다.
- **출력 인코딩**: `pes.py`는 시작할 때 stdout·stderr를 UTF-8(`errors=replace`)로 바꾼다(Python 3.9 호환, 이미 UTF-8이면 그대로, stdin은 건드리지 않음). Windows 파이프·리디렉션의 기본 cp1252에서 한글 `print`가 죽던 문제(v0.15·DB 경로 모두)를 막는다. `python -I`는 `PYTHONIOENCODING`을 무시하므로 환경 변수에 기대지 않는다.
- **오류 출력**: 브리지가 JSON이 아닌 값·`null`·배열·숫자·`data` 없는 `{ok:true}`를 내거나, `submit`·`merge`·`qa`·`ask`의 입력 파일이 없거나 깨졌거나 객체가 아니면 파이썬 스택 대신 한국어 오류 한 줄과 0이 아닌 종료 코드로 끝나고 아무것도 쓰지 않는다.
- **이번 PR의 알려진 한계**: 기획 항목의 `reuse`(옛 라이브러리 재사용 표시)는 `merge`가 보존하지 않아 인계 때 라이브러리 내용을 복사하지 않는다. 항목의 `open_questions`는 단계 제안(`suggestions`)으로 모으지 않고 메타데이터에만 남긴다.

### 8.13 CLI 읽기·보고서·doctor(PR16)

`PES_DB_CORE=1`일 때만 읽기 명령이 DB 경로를 탄다. 플래그가 없으면(`0`·빈 문자열·`true`도 마찬가지) v0.15와 출력·종료 코드·만든 파일이 같다(`watch`의 경로 따옴표만 예외 — 아래). 새 코어 명령은 없다(등록표 불변): 보고서 쓰기는 기존 `content.*`·`file.*`만 지난다.

- **어느 쪽을 읽나(PR12 `serving_path`)**: 프로젝트가 DB에 있고 `projects.status = active`이면 DB, 그 밖(DB에 없음·staging·failed·archived)은 `project.json`을 읽는 legacy다. legacy 읽기는 v0.15와 바이트가 같고 파일·폴더의 바이트·mtime을 바꾸지 않는다. PES 홈 밖 절대 경로로 부른 폴더는 DB에서 서비스되는 프로젝트가 아니므로 같은 슬러그가 DB에 있어도 읽기는 그 폴더의 `project.json`, 쓰기는 거부다. legacy 프로젝트에 대한 쓰기(`report`·`assemble`·`web` 포함)는 모두 "이전" 안내 한국어 메시지와 0 아닌 종료 코드로 막히고 폴더·DB는 그대로다(아직 active가 아닌 DB 프로젝트의 쓰기도 같다). 브리지의 `route`(`database`/`legacy`/`none`)가 이 판단을 한다.
- **읽기 = 옛 모양으로 다시 만든 프로젝트**: `status`·`pending`·`digest`·`show`·`list`·`hub`는 `legacy_view.ts`가 DB 행에서 `load()`가 돌려주던 딕셔너리를 다시 만들고, 같은 v0.15 출력 코드가 찍는다. 항목 id·kind는 `metadata`(`legacy_id`·`legacy_kind`, 또는 이전해 온 항목의 `legacy_extra`)에서, 출처는 `citations`→`source_versions`(`date`·`note`·`orgId`·`tblId`는 `locator`)에서, 갱신 라운드는 `created_in_round_id`가 있으면 그것, 없으면(CLI `merge`) 그 판의 영수증보다 앞서 시작된 가장 큰 라운드에서 얻는다. `merge`는 이제 출처의 `date`·`note`·`orgId`·`tblId`를 `source_versions.locator`에 남긴다(이전 코드와 같은 자리). `pending`은 이전해 온 답 파일 중 `legacy.processed` 사건이나 `input.marked_processed` 사건에 이름이 없는 것이고, 식별자는 옛 feedback 파일 이름 모양이다. 읽기는 DB에 쓰지 않는다(영수증·사건 0).
- **보고서(`report`·`assemble`·`web`)는 실행마다 새 버전**: 단계마다 `artifact`(kind `report`, `metadata.role = stage_report`) 한 객체, 프로젝트마다 `artifact`(kind `output`, 단계 없음, `role = final_output`) 한 객체를 두고, 실행할 때마다 `content.append_version`(첫 실행만 `content.add_artifact`)과 `content.set_current`로 새 버전을 쌓는다. 내용이 같은 재실행도 새 버전이다(보고서는 "작성 시각 · PES (버전 n)" 줄에 버전을 적어 바이트도 다르다). 렌더 파일(`report.md`·`report.html`·`eli5.html`, 최종은 `report.md`·`sources.json`·`report.html`)은 `file.reserve_upload`→`store_blob`→`file.complete_upload`→`file.attach_version`(role `rendered`)로 붙고, 같은 바이트는 같은 blob을 다시 쓴다. 새 버전은 그때 쓴 항목들의 현재 버전을 `content.link_relation`(`derived_from`)으로 가리킨다(정확한 버전). 각주는 보고서 「출처」 절 번호(처음 나온 순서·중복 제거)와 원고 `[^n]` 다시 매김이다. 전부 한 단위, `via`는 `cli`, 권한·잠금은 다른 쓰기와 같다(`run:submit` 범위, 에이전트는 자기 lease). 프로젝트 폴더의 `reports/`·`out/`에는 쓰지 않는다(`out/cover.json`·`out/appendix.md`·`reports/<단계>/eli5.json`은 있으면 읽기만 한다). 출력에 새 버전 id와 파일 이름·blob id가 나온다. report·output artifact는 `render` 봉인 목록·`qa-data`·`approve plan` 인계·조사 항목 세기에 들어가지 않는다(`metadata.role`로 제외). `render` 출력의 "항목 N개"는 이제 항목만 센다(출처 제외).
- **보고서 생성기(`report.ts`)**: v0.15 `stage_md`·`cmd_assemble`·`cmd_web`(과 `fill`)의 TypeScript 이식이다. 같은 입력이면 v0.15와 바이트가 같다(시각만 다름). 이 생성기를 DB 읽기(위 보고서)와 PR12 `validate_import`가 함께 쓴다.
- **`validate_import`의 보고서 재생성**: `reports/<단계>/report.md`·`report.html`을 프로젝트 원본(`project.json`·`library.json`·`feedback/*.json`)에서 실제 생성기로 다시 만들어 옛 보고서와 비교한다. "작성 <시각> · PES" 줄과 페이지의 `built` 시각은 비교하지 않는다. 줄바꿈은 비교하지 않는다(LF 앞의 CR 묶음과 홀로 있는 CR은 LF 하나로 본다 — 옛 도구가 Windows에서 CRLF로 쓴 보고서, CR·CRLF·LF가 섞인 보고서도 같다고 본다). Python과 JavaScript가 다르게 찍는 실수 토큰(`12.0`·`5e-05`·`1e16`·`-0.0`)은 실수로 표시해 읽는다(`parse_legacy_json`) — Python `str(float)`과 같은 `12.0`·`5e-05`·`1e+16`·`-0.0`으로 찍힌다(`py_float_repr`). 다르면 `reports_regeneration` 문제(`path`=보고서 경로)이고 `ok=false`, 배치는 `validated`가 되지 않는다. `regeneration_format`은 더는 `provisional`이 아니다(`generator`). pdf·eli5·docx 같은 다른 보고서 파일은 비교하지 않는다. 합성 fixture `full`의 `reports/plan/report.md`·`report.html`은 v0.15 생성기의 출력(시각을 고정)으로 다시 만들었다.
- **보고서 파일의 줄바꿈**: 플래그가 없으면(v0.15 경로) `report`·`assemble`·`web`은 v0.15와 똑같이 `write_text`로 써서 같은 플랫폼의 v0.15와 파일 바이트가 같다(Windows는 CRLF). DB 경로의 생성물(객체 파일)은 플랫폼과 무관하게 LF 바이트다(Windows 체크아웃의 CRLF 템플릿도 LF로 읽고, 렌더 파일의 CR은 남기지 않는다). 비교만 줄바꿈을 정규화한다. 설정 표의 라벨은 v0.15처럼 질문 은행에 있는 것만 쓴다(없으면 키 그대로).
- **DB 판정 실패는 오류**: 읽기 명령이 `route`/`active_slugs`로 DB 여부를 묻지 못하면(열기·권한·손상·스키마 미완) 종료 1과 `DB 를 읽지 못했습니다` 메시지로 끝난다. 낡은 `project.json`을 현재 상태처럼 보여 주지 않는다. 'DB 파일 없음'만 코어가 `none`(legacy)으로 답한다. doctor만 실패를 문제 행으로 바꿔 진단을 계속한다.
- **`watch`**: 같은 한 줄 `tail -n0 -F <경로>/feedback.log | grep --line-buffered FEEDBACK`. 공백·따옴표·괄호 등이 든 경로는 작은따옴표로 한 단어로 묶는다(안전 문자 `\w @ % + = : , . / ~ -`만 있으면 v0.15와 같게 그대로 — 역슬래시가 든 Windows 경로도 따옴표로 묶는다). 입력 long-poll은 PR18 몫이다.
- **doctor**: 기본 진단은 아무것도 쓰지 않고(PES 홈도 만들지 않는다), 고칠 수 있는 항목만 `fixable`로 알린다. `--fix`만 고친다(낡은 잠금·포트 파일, 남은 `.tmp`, 대시보드 재생성, 보고서 등록, PES 홈 폴더 만들기). 플래그가 켜져 있을 때 더해지는 것: (가) 홈 전체 진단의 "데이터베이스" 그룹 — 파일이 없으면 참고, 열 수 없거나 무결성 검사에 실패하면 문제(종료 1, `--json`도 마찬가지), 스키마가 낡으면 주의. DB는 읽기 전용으로만 열고(`probe_database`) 마이그레이션·복구 작업은 하지 않으며, `--fix`도 DB를 고치는 일을 하지 않는다(DB 파일 바이트가 그대로다 — 단, 비정상 종료로 남은 저널이 있으면 `--fix`가 DB를 여는 순간 SQLite가 그것을 반영하는 자동 복구는 일어난다. 아래 '남은 저널은 정상 복구, 기본 doctor만 예외'). (나) DB에서 active인 프로젝트는 `project.json`이 없어도 문제가 아니라 자기 그룹의 정상 행으로 진단한다. (다) "서버" 그룹: PES가 아닌 프로그램이 쥔 8760~8764 포트마다 주의 행에 소유 프로세스 pid·이름을 적는다(macOS `lsof`(없으면 `netstat -anv`)·Linux `ss`·Windows `netstat -ano`, 도구가 없거나 못 알아내면 "확인 불가"). 소유자는 소켓에 접속하기 전에 한 번 물어 알아낸다(접속하면 점유 프로그램이 죽을 수 있다). (라) PES 홈 경로에 공백·따옴표·괄호 같은 문자가 있으면 "환경" 그룹에 명령 quoting 경고(`--fix`로 바꾸지 않는다). 프로젝트를 하나 지정한 진단에는 (가)·(라)가 없다. (마) 심볼릭 링크이거나 `resolve()` 결과가 PES 홈 밖인 프로젝트 폴더는 진단만 하고 `--fix` 대상에서 뺀다(그 폴더의 `project.json.tmp`·`.pes-lock`·`.pes-port`를 지우거나 바꾸지 않고, 진단 행에 이유를 적는다).
- **그 밖**: 처리 안 한 답(`pending`·`status`)은 `via`와 무관하게 모든 제출이다(원문 파일이 있으면 그 이름, 없으면 `submission-<id>.json`). `final_output`은 판(edition) 조건과 `display_no` 순서로 하나를 고르고, `web`이 기존 조립본을 다시 쓰면 직전 버전을 `derived_from`으로 건다. 실패한 실행이 쓴 객체 파일은 지운다(다른 blob 행이 가리키지 않는 것만). 플래그가 켜진 뒤의 옛 프로젝트(미전환)에 대한 `doctor --fix`는 그 폴더에 아무것도 쓰지 않는다. 그 행의 `--json`은 legacy 읽기 출력이 v0.15와 같아야 하므로 v0.15처럼 `fixable`이고, 본문은 "이전 후 --fix 로 고칠 수 있음", 요약은 "--fix 로 고칠 수 있는 것"에 세지 않고 "이전 후 고칠 수 있는 것"으로 따로 센다. `created`는 로컬 날짜다.
- **읽기는 디스크를 바꾸지 않는다**: 읽기 작업(`slugs`·`active_slugs`·`route`·`read_project`·`live_locks`·`overview`·`context`·`qa-data`, 그래서 `status`·`list`·`pending`·기본 `doctor` 등)은 질의 전용 연결(`connect_read_only`: `PRAGMA query_only`, 폴더 만들기·저널 모드 바꾸기 없음)로 읽고 객체 폴더를 만들지 않는다(쓰기 작업에서만 만든다). DB 파일·곁가지 파일(-wal·-shm)·폴더가 그대로다.
- **남은 저널은 정상 복구, 기본 doctor만 예외**: `pes.db-wal`(0바이트 초과)이나 `pes.db-journal`이 남아 있으면 SQLite가 연결을 열 때 DB에 반영(복구·checkpoint)한다. `--fix`와 다른 명령은 이 자동 복구를 그대로 쓴다. 기본 doctor만 DB를 열지 않고 "데이터베이스" 그룹에 '다른 PES가 실행 중이거나 비정상 종료 흔적 — 다른 PES를 끈 뒤 다시 실행, 그래도 남으면 doctor --fix' 주의 행을 내며 프로젝트 진단을 건너뛴다(원본 파일 불변). 빈 `-wal`과, 다른 PES가 지금 DB를 열고 있어 생긴 저널(-wal은 `-shm`의 DMS 잠금, -journal은 DB의 RESERVED 잠금을 다른 프로세스가 쥠 — 잠금을 잠깐 시도해 확인, 파일은 안 바꿈)은 복구가 일어나지 않으므로 정상으로 보고 그대로 진단한다.
- **렌더 파일의 이름은 버전이 기록한다**: blob은 프로젝트·sha256·크기로 공유되고 처음 올린 이름만 남으므로, 보고서·조립본 버전은 `metadata.files = [{name, sha256, size}]`로 각 파일의 이 버전 안 이름을 남기고, `web`의 조립본 재사용과 단계 보고서 등록 목록은 그 기록으로 그 버전의 `rendered` 연결에서 파일을 찾는다(기록이 없는 이전해 온 버전만 blob 이름). 새 표·마이그레이션은 없다.
- **숫자 토큰은 길이 제한 없이 읽는다**: `parse_legacy_json`은 JSON 숫자 토큰 전체를 읽고, 끝까지 읽었는지 확인한다.
- **알려진 한계**: DB에 저장된 숫자는 `12.0`이 `12`로 남는다(JSON 정수와 구분하지 않음; 통계 값은 이전 때 남긴 표시로 되살리지만 `-0.0`은 `0.0`으로 보인다). DB 읽기의 `settings`·`history`·`suggestions`는 이전해 온 값과 `merge`의 `open_questions`만 되살린다(AI 점검 질문 `review`는 이전해 온 요약만). `reports` 등록 목록은 보고서 객체의 현재 버전 파일에서 만든다. `hub`·`open`이 띄우는 화면은 PR18 몫이다.

### 8.14 스킬·에이전트·명령 문서의 직접 쓰기 제거(PR17)

스킬(`skills/*/SKILL.md`)·서브에이전트 지침(`agents/*.md`)·명령(`commands/*.md`)은 업무 상태를 바꾸는 방법으로 pes 명령(`merge`·`submit`·`ask`·`note`·`qa`·`round-start`·`render`·`approve`·`mark`·`chat` 등)만 말한다. 문서 변경 외의 코드는 `scripts/pes.py`의 `set` 명령 하나뿐이고 새 코어 명령은 없다(등록표 불변). 문서는 플래그(`PES_DB_CORE`)를 말하지 않는다.

- **`npm run lint:skills`**(`scripts/lint_skills.ts`): 위 문서와 `docs/adapters/*.md`의 **코드 블록·인라인 코드**에서 (가) `project.json` 쓰기(Python `write_text`·`json.dump`·`open(…, "w")`, 셸 리다이렉트·`tee`·`sed -i`·`cp`/`mv` 도착지, PowerShell `Set-Content`·`Out-File`, Node `writeFile*`), (나) 업무 표를 바꾸는 SQL(`INSERT`·`UPDATE … SET`·`DELETE FROM`·`DROP/ALTER TABLE`), (다) 잠금 파일(`.pes-lock`) 만들기·지우기·옮기기를 막는다. 산문 문장·읽기·이름만 적은 언급·자식 제안 파일(`rounds/` 결과 JSON, 질문 명세, `eli5.json`, `cover.json`)은 막지 않는다. 검사 대상 밖(`tests/`·`scripts/`·`docs/plan/`·README)과 신뢰 서비스(`scripts/pes_core`)의 SQL은 보지 않는다. 위반은 `경로:줄: [규칙] 설명`으로 모두 찍고 종료 코드 1이다.
- **Claude 전용 표기**(`anthropic-skills:*`·`AskUserQuestion`·`Agent`/`Task` 도구 표기)는 `docs/adapters/{claude-code,claude-app,opencode}.md`에만 둔다. 어댑터 노트의 예외는 이 표기뿐이고 직접 쓰기 규칙은 어댑터에도 적용된다. `${CLAUDE_PLUGIN_ROOT}`·`mcp__*`·`WebSearch`/`WebFetch`·`pes:*` 이름은 플러그인 동작이라 막지 않는다. 어댑터 노트는 이름의 대응과 **한계**를 적을 뿐 변환 지원을 주장하지 않는다.
- **`pes set`**: 전용 쓰기 명령이 없던 값을 쓰는 허용 필드 화이트리스트 명령이다. 원인: 옛 스킬이 `stages.<단계>.summary`·`changes`·`carry_over`·`settings`·`review`와 최상위 `executive_summary`·`conclusion`을 Python으로 `project.json`에 직접 썼고, v0.15 보고서(단계 요약·남은 일·라운드 경과·최종 요약·결론)가 이 필드를 읽는다 — 이것을 `note`나 section 항목으로 돌리면 실사용 보고서에서 요약·이월·결론이 빠진다. 사용: `set <dir> <단계> <필드> <파일|->`(단계 필드 5개), `set <dir> project <필드> <파일|->`(`executive_summary`·`conclusion`). 값은 필드를 **통째로 바꾼다**(병합·덧붙임 없음, 같은 값을 또 써도 결과가 같다). `summary`·`executive_summary`·`conclusion`은 텍스트(JSON처럼 보여도 문자열), `changes`는 문자열 배열, `carry_over`는 객체 배열, `settings`·`review`는 JSON 객체이며 비었거나 잘못된 JSON·틀린 모양은 거부한다. 허용 밖 필드·점 경로·모르는 단계·없는 프로젝트·없는 값 파일도 한국어 이유와 종료 코드 2로 거부하고 `project.json` 바이트와 폴더 파일 목록이 그대로다. 쓰는 방식은 v0.15 `save()`와 같다(`.pes-lock` 확인, `project.json.tmp`에 쓰고 교체, 다른 세션이 2시간 안에 잠근 프로젝트는 종료 3).
- **`set` 입력 처리와 저장**: 값 파일·표준 입력은 UTF-8로 읽고 앞의 BOM은 값에 남기지 않는다(PowerShell 5.1의 `Set-Content -Encoding UTF8`, 메모장). UTF-8이 아닌 바이트, JSON의 `NaN`·`Infinity`·`1e999`, 너무 깊은 중첩, 짝 없는 서로게이트(`\ud800`)처럼 UTF-8 JSON으로 저장할 수 없는 값은 쓰기 전에 거부하고 `project.json`·폴더는 그대로다. 깨진 `project.json`은 스택 대신 한국어 거부다. `set`은 읽기-수정-쓰기 동안 `.project.json.lock`(아주 짧은 배타 파일, 끝나면 지움, 60초 넘으면 죽은 흔적으로 보고 치움)을 잡아 동시에 도는 `set` 둘이 서로의 갱신을 덮지 않는다. `save()`는 임시 파일을 프로세스별 이름(`project.json.tmp.<pid>`)으로 쓰고 교체한 뒤 옛 이름 `project.json.tmp` 흔적을 치우며, `doctor`는 `project.json.tmp*`를 "저장 중 끊긴 임시 파일"로 알리고 `--fix`가 지운다. 이전(importer)도 이 이름들을 옛 `project.json.tmp`와 같게 본다.
- **알려진 한계(v0.15 공통)**: `set` 말고 `project.json`을 읽고 고쳐 쓰는 다른 명령(`merge`·`round-start`·`note` 등)은 위 짧은 잠금을 쓰지 않는다. 같은 세션(`PES_OWNER`)이 두 프로세스로 동시에 쓰면 읽기-수정-쓰기 사이에 한쪽 갱신이 사라질 수 있다(v0.15 이래 같은 동작). 한 세션은 명령을 차례로 부른다.
- **`PES_DB_CORE=1`에서의 `set`**: 대응하는 코어 명령(단계 요약·설정·점검·최종 요약·결론을 DB에 두는 자리와 영수증)이 아직 없다. 그래서 `set`은 어느 프로젝트에도 쓰지 않고 한국어 이유와 종료 코드 2로 거부하며 DB·`project.json`·폴더는 그대로다(옛 폴더는 다른 쓰기 명령처럼 "이전 후 쓸 수 있다"). 이 경로의 단계 보고서 첫 장은 이 값 없이 만들어진다 — 코어 명령을 더하는 PR의 몫이다(등록표 시험을 함께 바꿔야 한다).
- **`merge`가 옛 직접 편집의 상태를 그대로 만든다**(r1-1 필수 1·2): 옛 스킬이 Python으로 직접 쓰던 항목 값을 `merge` 제안 파일로 넘기므로, `merge`(v0.15 `cmd_merge`와 DB 경로 `cli_bridge` 둘 다)가 다음을 받는다. `request`는 있을 때만 덮어쓰고 빈 문자열이면 비운다. `reuse`(기획 topic의 참고자료 id — v0.15 `approve plan`의 재사용이 읽는다)와 `model`(조사 모델)은 그대로 남긴다. `user_links`는 목록 추가 규칙이다: url이 같은 줄은 준 칸(status·memo·added)만 고치고 새 url은 뒤에 붙이며 status가 없으면 `todo`다 — 조사 문서의 "병합 후 user_links status를 done/failed로" 절차가 이것으로 돌아왔다. `id`와 `status`·`request`·`user_links`만 담은 제안(심화·수정·삭제·원문 확인·링크 지시)은 내용 병합이 아니어서 depth를 올리지 않고, status를 주지 않으면 지금 status를 둔다(옛 직접 편집과 같다; v0.15는 `updated_round`도 그대로). DB 경로에서는 이 값들을 항목 버전의 metadata에 두고 옛 보기(`show`·`status`)가 `reuse`·`model`·`user_links`·`request`를 보여 준다. DB 경로의 기획 승인(`hand_over_plan`)도 v0.15 `handoff_plan`처럼 `reuse`가 가리키는 가져온 참고자료 항목(단계 밖 artifact, `legacy_extra.legacy_id`)의 요약·본문·수치·충돌·신뢰도·출처(인용)를 이어받아 deepen 항목을 만들고 `request`·`links.library`를 단다. 찾지 못하면 새 항목(new)이다. v0.15 파일에서 이전해 온 기획 topic은 번호·종류·연결·재사용을 `legacy_extra`(`legacy_id`·`kind_original`·`links`·`reuse_original`)에 두므로, 승인은 이 값도 읽어 같은 규칙으로 넘긴다(이전된 조사 항목의 번호·`links.plan`도 세어 겹치지 않게 한다). DB 경로 `merge`도 번호로 항목을 찾을 때 `legacy_id`와 `legacy_extra.legacy_id`를 함께 보므로(번호로 찾는 조회 전부 같은 규칙) 이전된 항목에 거는 제어 전용 제안이 "없는 항목"으로 거부되지 않고, 내용 제안이 같은 번호의 새 항목을 만들지 않는다. 첫 `merge`는 이전된 값(`kind_original`·`depth`·`links`·`shots`)을 이어받고, 새 status·confidence를 쓰면 옛 보기가 먼저 읽는 `status_original`·`confidence_original`을 지운다. 상태·요청·`user_links`만 담은 제안이 **없는 항목 번호**를 가리키면 새 항목을 만들지 않고 한국어 이유와 종료 코드 2로 거부한다(두 경로 같음, 그 `merge` 전체가 바뀌지 않는다 — 오타 난 번호가 빈 항목이 되지 않게). `user_links`가 목록이 아니면(null 포함) 같은 방식으로 거부하고, 손으로 고친 파일에서 항목의 `user_links`가 null이면 빈 목록으로 본다.
- **`set <dir> plan settings`는 두 곳에 쓴다**(r1-1 필수 3): `stages.plan.settings`와 최상위 `settings`(옛 문서의 "기획 답은 `p.settings`에도"). 보고서 형식(`report_formats`의 `stage_reports`)·승인 창·`qa-brief`의 「기획 답(사용자)」이 최상위 값을 읽는다. 다른 단계의 `settings`는 그 단계에만 쓴다.
- **덧붙이는 값은 읽고 전체를 다시 쓴다**(r1-1 필수 5): `set`은 통째로 바꾸므로, 변경점에 한 줄 더하기는 `show <dir> <단계> --fields changes`(id 없이 `changes`·`carry_over`·`settings`·`review`만 주면 단계 값을 보여 준다; `summary`는 항목 요약이라 제외)로 지금 값을 읽고 **이미 쓴 줄을 포함한 전체 배열**을 다시 쓴다. 문서(core 「상태 읽기와 검증된 제출」)가 이렇게 지시한다.
- **기본 경로와 DB 경로 명령의 구분**(r1-1 필수 4): `context`·`claim`·`submit`·`wait`·`complete`는 DB 경로(작업 토큰을 받은 작업자) 명령이고 기본 경로에서는 거부된다. 문서는 기본 경로의 답 읽기를 "`pending`이 알려 준 답 파일(`feedback/*.json`)을 읽는다"로 쓰고, core 명령 표에서 이 다섯을 "DB 경로에서 쓰는 명령"으로 구분한다. `ask`는 시작 질문 폼만 만들고 AI 점검 질문은 `set <dir> <단계> review`로 쓴다(core 표를 v0.15 동작에 맞춤).
- **`merge`로 줄일 수 없는 것**(r1-1 권장 5): `conflicts`·`links`·출처(write 단계·section 밖)는 쌓이기만 한다. 옛 직접 편집은 지울 수 있었지만 이 PR은 교체 의미의 필드를 더하지 않는다. 문서는 해소된 충돌을 그 항목의 `request`와 summary·details에 적게 한다. 지우는 길이 필요하면 코어 명령을 더하는 PR의 몫이다.
- **lint 보강**(r1-1 권장 1): pathlib `.open("w")`(모드가 첫 인자), sqlite `.import`, `CREATE TABLE/INDEX/VIEW/TRIGGER`도 막는다. 문자열 이어붙이기 같은 의도적 우회는 막지 않는다.
- **`set` 짧은 잠금의 남은 틈**(r1-1 권장 7, 낮음): 60초 넘은 `.project.json.lock`을 두 프로세스가 동시에 치우면 둘이 함께 들어갈 수 있고, kill -9로 남은 이 파일은 이전(importer)에서 알 수 없는 파일로 분류될 수 있다 — 죽은 프로세스 뒤에만 생기는 일이라 이 PR에서는 고치지 않는다.
- **lint는 쓰기 대상만 본다**(최종 리뷰 1 F2·F3): 문장에 `project.json`·`.pes-lock` 이름과 쓰기 낱말이 함께 있다는 것만으로 막지 않는다. 쓰기 대상만 판정한다 — `write_text`·`write_bytes`·`unlink`·`touch`·pathlib `.open(<쓰기 모드>)`의 수신 객체, `open(경로, <쓰기 모드>)`의 경로, `json.dump`의 파일 인자, `tee`·`sponge`·`sed -i`·`dd of=`·`curl -o`·`>`/`>>`의 대상, Node `writeFile*`·`unlink*`·`rm*`, PowerShell `Set-Content`·`Out-File` 등의 경로(`-Value` 값 제외). 교체·복사·이동(pathlib `.replace`·`.rename`, `os.replace`·`os.rename`, `shutil.copy*`·`shutil.move`, Node `copyFile*`·`cpSync`·`rename*`, .NET `File::Copy/Move/Replace`, `cp`·`mv`·`Copy-Item`·`Move-Item`)은 도착지(이동은 원본도)를 본다. 그래서 상태를 읽어 `rounds/` 제안 파일로 쓰는 한 문장이나 `cat project.json | tee rounds/…` 같은 읽기는 통과하고, `Path(d, "proposal.json").replace(Path(d, "project.json"))`·`copyFileSync("proposal.json", "project.json")`는 막힌다.
- **`submit`은 제안 파일 경로가 아니다**(최종 리뷰 1 F1): `submit`의 결과 파일은 DB 결과 형식(`{"results": [{"op": "append_version", "object_id", "based_on_version_id", 코어 필드…}]}`, 1~20개, 이미 있는 항목만)이고 스킬·서브에이전트의 제안 파일(`id`·`details`·`sources` …)과 계약이 다르다. 그래서 문서·서브에이전트 지침·어댑터는 제안 파일을 메인에 돌려주고 `merge`로만 반영하게 하고, core 명령 표에서 `submit`을 DB 결과 형식 전용으로 구분한다. 제안 파일을 DB 결과 형식으로 바꿔 내는 길은 이 PR 범위 밖이다.
- **참고자료 읽는 길**(최종 리뷰 1 권장 2): `show`·`digest`는 여섯 단계만 받는다. 기획의 참고자료 대조는 `status`(개수·출처), `render` 뒤 대시보드 기획 탭 「참고자료」, 그리고 `--import`에 준 원래 조사 폴더의 `state.json`(PES 상태가 아닌 가져온 자료, 읽기만)으로 한다고 plan·core 문서에 적었다. 이전된 library 재사용은 옛 신뢰도(`legacy_extra.confidence`·`confidence_original` 어느 쪽이든)를 이어받고, DB 경로 `approve plan` 안내 줄도 재사용 개수를 센다.
- **남은 한계 — DB 경로의 「참고자료」 칸**(1차 리뷰 r1-5 권장 3): `PES_DB_CORE=1`에서 대시보드 기획 탭의 「참고자료」 칸은 library 개수만 세어 보여 주고 원래 항목 번호·제목·요약은 채우지 않는다(`legacy_view.ts`의 자리표시자). 그래서 DB 경로에서 `reuse`를 정할 때는 `--import`에 준 원래 폴더의 `state.json`을 읽는다고 plan·core 문서에 적었다. 칸이 제목·요약·원래 번호를 채우게 하는 일은 별도 PR의 몫이다.
- **lint 별칭·이름 인자**(r1-5 권장 1·2): 수신 식이 `fs`·`fsp`·`fsPromises`·`require(...)`이면 Node 호출로 보고(`await fsp.writeFile(...)`, `node -e "require('fs').writeFileSync(...)"`), pathlib `symlink_to`·`hardlink_to`의 수신 객체도 쓰기 대상으로 본다. PowerShell은 `-Value`·두 번째 위치 인자·`(…)` 괄호 식을 값으로 보고, `Copy-Item`·`Move-Item`은 `-Path`/`-Destination` 이름이 있으면 이름으로 도착지를 판정하며, 쉘 조각의 `< 입력파일`은 읽기라서 뺀다. `str.replace`(인자 둘)는 파일 교체로 세지 않는다.
- **연구 절차는 그대로**: 조사 항목·출처 원문 확인·독립 검토(reviewer)·검증(verifier)·승인 전 마무리는 문장만 다듬었고 단계는 바뀌지 않았다(시험이 필수 절차 목록으로 고정).

### 8.15 로컬 화면 DB 전환(PR18)

`PES_DB_CORE=1`일 때만 화면이 DB를 읽고 쓴다. 플래그가 없으면 `render`·`ask`·`hub`가 만드는 파일과 `serve.py`의 응답이 PR16 머지(`36bc6a2`)와 같다(공용 템플릿은 보안 수정 한 가지만 바꿨다 — `dashboard.html`의 항목 `path`·`shots` 링크가 `safeRel`(`javascript:`·`data:` 같은 스킴과 `//` 시작을 막고 http(s)·상대 경로만 링크로)을 거친다. v0.15 화면도 같이 고쳐진다. DB 화면의 보강은 `templates/db/`의 별도 조각을 DB 쪽 페이지 끝에만 붙인다). 새 표·마이그레이션은 없다. 같은 URL·같은 동작이 원칙이다.

- **어느 프로젝트가 DB로 서빙되나**: 서버는 브리지 `route`(PR12 `serving_path`)로 `/<slug>/…`를 판정해 2초 동안 기억한다. `database`이면 폴더에 `project.json`이 없어도(`pes.py init`이 만든 폴더) 서빙한다. DB에 없거나 아직 active가 아닌 프로젝트는 v0.15 길(`project.json` 정적 서빙, 답은 `feedback/*.json`) 그대로다. DB를 판정하지 못하면 503이다(낡은 `project.json`을 현재 상태처럼 보이지 않는다). 서버는 시작할 때 `PES_TOKEN`·`PES_OWNER`를 지운다 — 화면은 늘 이 컴퓨터 DB의 사람 소유자 몫이다.
- **화면은 요청 때 DB에서 짓는다**: 홈 목록(`/`, `/index.html`)과 대시보드(`/<slug>/`, `/<slug>/index.html`)는 요청마다 `pes.py`의 짓기 함수(`fill`)로 DB 값을 담아 내준다. `render`(DB)는 라운드 봉인 뒤 `index.html`(첫 render의 표지 — 이 파일이 있어야 `/<slug>/`가 시작 질문 폼 대신 대시보드를 보인다)과 `.pes-hub`가 있으면 홈 허브 파일을 쓴다. 이 파일들은 화면용이지 상태가 아니고 쓰기에 실패해도 render는 성공이다. 허브 "열기"·질문 폼 안내·보고서 "← 대시보드" 링크가 가리키는 `/<slug>/index.html`과 `/index.html`도 서버는 그 파일이 아니라 DB에서 새로 지어 내준다(`HEAD`도 같은 길이) — 처음 렌더 전 질문 폼으로 보내는 리다이렉트만 `/<slug>/`에 있다. 서버 없이 `pes open`이 파일로 열 때는 여는 순간 DB에서 `index.html`을 다시 쓴다(홈 폴더 자체가 프로젝트인 예전 방식은 이 길을 타지 않는다). `project.json`은 읽지도 쓰지도 않는다. 대시보드 데이터는 브리지 `screen`이 준다: 옛 모양으로 다시 만든 프로젝트(PR16) + 처리 대기/받은 답 + 봉인된 라운드별 스냅샷(타임라인·항목×라운드) + 최종 보고서 파일 목록 + 실행 중 run·전송 중 Go 호출.
- **스냅샷**: 봉인된 라운드마다 그 라운드의 `round_contents`가 가리키는 정확한 항목 판으로 같은 짓기 코드를 돌려 v0.15의 슬림 상태를 만든다. 알려진 차이: v0.15 스냅샷의 `changes`(project.json 목록)는 DB에 없어 빈 목록이고, 스냅샷의 `status`는 늘 `active`다. 같은 라운드에서 상태가 바뀌어 쌓이던 v0.15의 `2.json` 판은 DB에 없다(봉인은 라운드당 하나).
- **AI 점검(`review`)**: `ask`(kind `review`)로 올린 질문 세트 중 단계별 최신 것이 그 단계의 점검 칸이다(질문 id는 DB 질문 id). 조건부 질문의 `show_if.id`도 같은 체계로 바꿔 싣는다: 폼 작성자는 spec의 질문 id로 `show_if`를 쓰는데 DB 질문은 그 id를 갖지 않으므로, `ask`가 가리키는 질문의 폼 안 자리(`show_if.position`)를 함께 저장하고 화면이 그 자리의 DB 질문 id로 바꾼다(v0.15에서 옮겨 온 질문은 spec id가 `bank_key`로 남아 그것으로 찾는다). `position`은 그 질문 판이 처음 게시된 세트 안의 자리라서 그 세트에서만 그대로 쓰고, 같은 판을 다시 담은 다른 세트(API `question_id` 재사용)에서는 그 자리의 질문이 처음 세트에서 가리킨 질문과 같거나 그 질문의 `bank_key`가 참조 id와 같을 때만 쓴다 — 아니면 DB id, 그다음 `bank_key` 순으로 찾는다. 찾을 수 없는 참조는 버린다 — 그 질문은 늘 보이고 필수면 답을 요구한다(가리킬 질문이 없는 조건이 질문을 늘 숨겨 필수 검사를 비켜 가게 두지 않는다). 점검 칸에는 그 질문 세트의 `form_key`·`set_id`도 실리고, 대시보드는 점검 답(kind `review`)에 이 둘(`spec`·`set_id`)을 실어 보낸다 — 그 뒤 같은 폼 키가 개정됐으면 아래 '이전 판 폼의 답'과 같은 검사(명령 안 최신 판 검증)로 409다. 점검의 라운드는 게시 때 열려 있던 라운드, 없으면 폼 id 끝의 `-r<N>`, 그것도 없으면 단계의 최신 라운드다. 시작 질문 폼이 나간 `pending` 단계는 v0.15 `ask`처럼 `asking`으로 보인다(읽기 쪽 표시일 뿐 DB 상태는 그대로).
- **질문 폼(`ask-*.html`)**: v0.15처럼 `ask` 때 폴더에 쓰는 화면 파일이고 정적으로 서빙한다. DB 모드에서는 게시한 질문 세트의 id(`set_id`)가 페이지 데이터에 실려 답에 함께 간다. 알려진 차이: 폼 spec의 출처는 DB의 질문 세트가 아니라 `ask`에 준 spec 파일이다(질문 세트는 `answer.submit`·API용으로 따로 있다).
- **답 보내기 `POST /<slug>/feedback`(DB)**: 검증(허용 안 된 Origin 403 `{error:"origin", hint}`, 잘못된 kind 400 `{error:"kind"}`, 빈 내용 400 `{error:"empty"}`, 깨진 JSON 400, 본문 256KB 초과 413, 없는 프로젝트 404)은 v0.15와 같은 상태·본문이고 실패하면 DB에 아무것도 남기지 않는다. 통과하면 브리지 `web_feedback`이 사람 소유자(lease를 잡지 않는다 — Claude의 잠금이 화면을 막지 않는다)로 코어 명령 `input.record_chat`(`web` 인자)을 정확히 한 번 부른다: v0.15가 `feedback/<이름>.json`에 쓰던 기록(`stage·round·time·kind·text·answers·spec·via·origin·who`, 유일성을 위한 `id`, 질문 세트가 있으면 `set_id`)이 한 submission의 원문 파일(blob, 이름 `<단계>-R<라운드>-<시각>.json`)이 되고 `submissions` 행 하나(`via=web`)가 이를 가리킨다. `pending`·대시보드의 받은 답·보고서의 결정 절이 그 행을 읽는다. 호환 별칭 `POST /feedback`(0.8 이전 화면 — 보낸 페이지 주소 `Referer`의 첫 칸으로 프로젝트를 찾는다)도 서버가 최종 프로젝트를 정한 뒤 같은 한 곳에서 DB 서빙 여부를 보므로, DB 프로젝트면 폴더에 옛 `project.json`이 남아 있어도 같은 `web_feedback`으로 제출되고 `feedback/`에는 쓰지 않는다(거부하지 않고 받는 쪽을 골랐다 — 옛 화면에서 보낸 답이 사라지지 않게). legacy 프로젝트·플래그 없음의 `/feedback`은 v0.15 그대로 `feedback/*.json`이다. 응답은 v0.15처럼 `{ok:true, file:<처리 대기 이름>}`이고 그 이름이 `pes.py pending`의 이름과 같다. DB 방식은 `v`(커밋 뒤 변경 커서)도 싣고, 보낸 화면은 그 값까지를 이미 아는 값으로 보아 자기 제출로 "새 결과가 올라왔습니다" 막대를 띄우지 않는다. `feedback/*.json`·`project.json` 이중 쓰기는 없다. 서버는 `feedback.log`에 `FEEDBACK <단계> R<라운드> <kind> <이름>` 한 줄만 더한다(`pes watch`용 알림 — 답 내용은 싣지 않는다). 폴더에 파일이 없으므로 끝은 경로가 아니라 읽을 이름이고, `pes.py pending`도 같은 이름을 한 줄씩 낸다(`status`의 "처리 안 한 답"도). **답 원문 읽기**: `pes.py pending <프로젝트> --show [<이름>…]`가 두 방식 모두에서 같은 명령이다 — 옛 방식은 `feedback/<이름>` 파일 내용, DB 방식은 그 submission의 원문 파일(blob; API로 낸 답처럼 원문 파일이 없으면 제출 행·답 버전으로 짠 JSON)을 그대로 낸다. 이름을 안 주면 처리 안 한 답 전부(둘 이상이면 `=== 이름 ===` 머리글이 붙는다), 이름은 경로로 줘도 파일 이름만 쓴다. 없는 이름은 종료 코드 2.
- **`input.record_chat` 확장**: 영수증 action 이름은 그대로 `input.chat_recorded`다(`mutation_commits.action`은 사건 이름이 규칙). `web` 인자 `{name, sha256, size, set_id}`가 있으면 노트 artifact 대신 위의 blob(`ready`)+submission을 만든다. 바이트는 브리지가 명령 전에 객체 폴더에 두고 명령이 sha256·크기를 다시 확인한다. 실패하면 그 파일은 지워진다. 두 경로의 영수증 `result`와 사건 `payload`는 공통 필드 `stage`(영수증은 `stage_id`)·`round_no`·`kind`를 갖는다. 일반 경로는 `{object_id, version_id}`(노트 artifact)를, web 경로는 `{submission_id, name, set_id}`(제출)를 더 싣고 web 경로에만 `web: true` 표지가 있다. `web` 인자는 CLI 브리지(`web_feedback`) 전용이고 API(`api.ts`)로는 열려 있지 않다. 질문별 `answers` 표 행은 만들지 않는다 — 화면의 답은 원문 제출로만 보존되고, DB 질문과의 연결(`answer.submit`)은 API 경로(PR14)의 몫이다. 새 API 답 제출 경로는 별도다.
- **kind**: `approve`·`reopen`·`resume`·`feedback`·`review`·`stage_start`는 v0.15처럼 모두 '사람이 한 요청'으로 처리 대기에만 쌓인다. 단계 상태는 `pes.py approve/reopen`이 바꾼다.
- **이전 판 폼의 답(409)**: 답에 `set_id`가 있으면 그 폼 키의 최신 판일 때만 받는다(아니면 409 `{ok:false, error:"conflict"}`, 아무것도 저장하지 않음). `set_id`가 없는 답(옛 화면)은 그 폼의 판이 하나뿐일 때만 받고, 판이 둘 이상이면 409다 — 새 판에 몰래 붙이지 않는다. 폼 키(`spec`)조차 싣지 않은 답(이번 변경 전에 열어 둔 대시보드의 점검 답 같은 구형 화면)은 어느 폼의 답인지 알 수 없으므로 폼 검사 없이 `set_id` 없이 받는다(원문은 그대로 보존 — 사람의 답을 버리지 않는다); 지금 대시보드·질문 폼은 늘 폼 키와 `set_id`를 싣는다. 답이 `spec`과 `set_id`를 실었는데 그 폼 키의 판이 하나도 없으면(폼 키가 잘렸거나 엉뚱함) 조용히 받지 않고 409다. 폼 키는 늘 정규형(소문자 a-z0-9와 `-`, 양끝 `-` 없음)으로 비교한다: `pes.py ask`(DB)는 정규형이 80자를 넘는 폼 id를 종료 코드 2로 거부하고(아무것도 쓰지 않음) 게시한 정규 폼 키를 질문 폼 데이터(`form_key`)에 실어 화면이 그것을 `spec`으로 보낸다. 서버는 받은 `spec`을 1024자까지 브리지에 넘기고 브리지는 자르기 전 전체에서 정규형을 구한다(기록의 `spec` 필드만 v0.15처럼 80자) — 자른 뒤 정규화하면 다른 키가 될 수 있어서다. `set_id`를 실었는데 `spec`이 없거나 정규형이 빈 답은 판 표시 없는 구형 답과 구별해 그 판 id로 판을 찾는다(없으면 404, 옛 판이면 409). 같은 검사를 명령 안에서도 한다(경쟁 방지). 이 '질문이 바뀌었다' 경우만 409이고(브리지 코드 `form_revised`), 그 밖의 충돌을 409로 번역하지 않는다.
- **동시 연결**: 화면 서버의 listen 대기열은 128이다. Python 3.14 이하 `socketserver` 기본값 5로는 같은 순간 6번째부터 연결이 거절돼(Windows `ECONNREFUSED`, macOS `ECONNRESET`) 보낸 답이 서버에 닿지도 않았다.
- **동시 제출과 입구 제한**: 처리 대기 이름의 선택(같은 초면 `-2`, `-3` 접미사)과 삽입은 한 트랜잭션(`BEGIN IMMEDIATE`) 안에서 하므로 같은 순간의 여러 답이 모두 받아지고 이름이 겹치지 않는다. 화면 답의 `text`는 본문 상한(256KiB) 안이면 받는다(v0.15와 같음; API·CLI 경로의 10만 자 상한은 그대로). 중첩 깊이 200을 넘는 JSON과 안전 정수(±2^53−1)를 벗어난 `round`는 서버 입구에서 400이다 — 알림 줄·처리 대기 이름·DB가 같은 round를 말해야 하고, 깊은 JSON이 스택을 터뜨려 503으로 나가면 안 된다. 거절은 흔적이 0이다.
- **버전**: `GET /<slug>/version`은 `{"v": <그 프로젝트의 최신 mutation_commits rowid>}`다. 변경이 없으면 같고, DB 쓰기(화면에서 보낸 답 포함)가 있으면 커진다. 파일 mtime과 무관하다. 홈의 `/version`은 DB 전체의 최신 커밋이다.
- **보고서·eli5·최종 보고서**: 폴더 파일이 아니라 DB의 렌더 파일(`file.attach_version` role `rendered`)을 같은 URL(`/<slug>/reports/<단계>/report.{md,html}`·`eli5.html`, `/<slug>/out/report.{md,html}`·`sources.json`)로 내준다. 대시보드 데이터(`stages.<단계>.reports`, `outputs`)가 같은 경로를 가리킨다. 파일 목록에 없는 이름은 404다(경로 이탈 없음). **이전한 프로젝트의 등록 보고서**: v0.15가 `stages.<단계>.reports`에 등록한 파일(예: PDF)은 PR11 이전이 그 단계의 보고서 객체(`metadata.legacy_extra.report`)와 그 판의 첨부(`version_files` role `rendered`) 하나로 보존한다. 단계 보고서 URL은 먼저 DB가 만든 그 단계 보고서(현재 판)의 파일을 보고, **그 단계에 DB가 만든 보고서가 아직 없을 때만** 현재 판의 `legacy_extra.report.path`가 요청 경로와 정확히 같고 첨부가 정확히 하나인 이전 보고서의 그 파일을 내준다 — 대시보드가 보이는 목록과 같은 규칙이다(DB가 단계 보고서를 만들면 대시보드 목록도 그것으로 바뀐다). 임의 경로·폴더의 정적 파일로는 넘어가지 않는다. 이전 때 다시 만들 수 있다고 보고 옮기지 않은 `.md`·`.html`·`eli5.html`과 원래 없던 파일은 404이고, 이전한 `out/` 파일은 이 경로로 내주지 않는다(최종 보고서는 DB가 다시 만든 것만). **대시보드는 열리는 링크만 싣는다**: `stages.<단계>.reports`와 `outputs`는 서버가 위 규칙으로 실제 파일을 찾는 경로만 남긴다(보고서 URL과 같은 함수로 판정) — 이전한 프로젝트에서 재생성 대상(단계 `report.md`·`report.html`·`eli5.html`, 최종 `out/` 보고서)은 `pes.py report <프로젝트> <단계>`·`pes.py web <프로젝트>`를 돌려 DB가 만든 뒤에 나타난다. 폴더의 `reports/`·`out/`에는 쓰지 않는다.
- **/api/v1은 정적 서빙보다 먼저**다(폴더 이름이 `api`여도). 소유자 세션 비밀(`PES_LOCAL_SESSION_SECRET`)은 어떤 정적 응답·헤더에도 실리지 않고, 화면의 쓰기는 같은 출처 `POST feedback` 한 길이다.
- **브라우저 쪽(DB 화면 보강, `templates/db/overlay-*.html`)**: (가) 성공 표시는 서버 영수증(`{ok:true, file}`) 뒤에만 한다(영수증 없는 200은 실패). 질문 폼도 같다: 보내기를 시작할 때의 초안을 잡아 두고 영수증 뒤에는 저장소의 초안이 그것과 같을 때만 지우며, 보낸 그대로의 내용만 다시 저장하지 않는다 — 응답을 기다리는 동안이나 보낸 뒤에 바꾼 내용은 계속 저장되고 새로 불러오면 복원된다. (나) 보내기 실패(409 충돌·시간 초과 20초·서버 오류)나 `/version` 실패(410 커서 무효)에도 입력 중인 초안은 지워지지 않고 화면을 다시 불러오지 않는다. 409는 "충돌·질문이 바뀌었다·새 판에서 다시 보내라" 안내를 보이고 클립보드로 넘기지 않는다. (다) 초안은 이 탭의 sessionStorage에 두고(질문 폼은 경로별, 대시보드는 경로+단계별) 새로 불러오면 복원한다. 영수증을 받으면 보내기를 시작한 그 단계의 초안만, 그것도 보낸 때와 내용이 같을 때만 지운다 — 응답을 기다리는 동안 다른 단계 탭으로 옮기거나 같은 단계에서 더 입력한 초안은 남는다. (라) 대시보드에 '작업 상태' 상자: 실행 중 run은 '실행 중', 사람 답을 기다리는 run은 '기다리는 중', 전송 중인 Go 호출은 '전송 중', 결과를 모르는(unknown) 호출은 '결과 확인 불가'로 글자로만 보인다. 이 상자는 읽기 전용이다.
- **안전한 Markdown**: 바꾸지 않았다. 템플릿의 `inline()`이 모든 항목·보고서 글을 이스케이프하고 링크는 http(s)만 살리며, 페이지 데이터는 JSON 블록 안에서 `</`를 `<\/`로 바꿔 싣는다. 스크립트·`javascript:` 링크·`onerror` 이미지는 글자로만 보인다(Playwright E7·E8).
- **시험**: `tests/test_web_*.test.ts`(HTTP로 v0.15와 DB를 같은 합성 자료로 비교)와 `tests/e2e/workspace_smoke.spec.ts`(Playwright 1.65.0, Chromium). CI는 `browser` 잡(windows-latest·macos-latest)이 `npm ci && npx playwright install chromium && npx playwright test`를 돌린다 — 브라우저를 받지 못하면 잡이 실패한다.
- **알려진 차이(요약)**: 스냅샷의 `changes`는 빈 목록·`status`는 `active`; 같은 라운드의 여러 스냅샷 판 없음; 화면의 답이 질문별 `answers` 행으로 나뉘지 않음; 폼 spec은 `ask` 때의 파일에서 온다; 홈 `/version`은 DB 전체 커서; 화면 서버는 DB 프로젝트마다 요청 때 Node 브리지를 한 번 이상 띄운다(로컬 사용 규모; 후속: `/<slug>/version` 한 번이 `route`+`version` 프로세스 둘이므로 `version` 답에 판정을 함께 싣거나 `route` 기억 시간을 늘린다, 봉인 라운드가 많은 프로젝트의 `/<slug>/` 시간도 잴 것).

### 8.16 A 내장 실행기·AI 연결(PR19, SEL-52)

방식 A의 AI는 사용자가 등록한 **AI 연결**이다([0019](decisions/0019-ai-connection-registration.md)). 실행기(`scripts/pes_core/a_runtime/`)와 사용 방법은 [docs/adapters/a-builtin.md](../adapters/a-builtin.md)에 있다. **DDL 표가 늘어나므로(마이그레이션 002) PR에 "사람 확인 필요"를 표시한다.**

**0019 "정할 것" 확정(leader 결정, 2026-11-11)**

1. **요청 형식·모델 목록**: `openai_compatible`(Chat Completions; 구독형 API·직접 입력·로컬 모델 포함)과 `anthropic`(Messages)을 구현한다. 모델 목록은 각 형식의 `GET …/models`(`/v1`까지 적은 OpenAI 호환 주소) 또는 `GET …/v1/models`(Anthropic)이다. **Google API는 연결 종류로 등록·저장만 되고 실행은 지원하지 않는다**(`supported: false`, 시험 호출도 하지 않으며 run 시작은 `conflict`). 자세한 주소·헤더·본문은 어댑터 노트에 있다.
2. **구독형 사용량**: 제공사의 사용량 조회 공식 API는 **확인하지 못했다(미확인)**. 그래서 PES가 센 토큰과 사람이 넣은 한도(5시간·주간·월간)로 3구간 이동 창을 추정한다. 멈춤 문턱은 한도의 `stop_percent`(기본 90%)이고 호출 전에 이번 호출의 예약(추정 입력 + 출력 상한)을 더해 본다. 결과를 모르는 호출(unknown)은 사람이 정리할 때까지 계속 센다. **한도를 모르면 등록도 시작도 하지 않는다(fail-closed).**
3. **단가**: 출처는 **사람 입력**(모델별 입력·출력 100만 토큰당 단가와 통화, 입력한 사람·시각)이다. 단가가 바뀌면 **다음 run부터** 적용하고, 진행 중인 run은 시작 때 `ai_run_settings`에 복사한 단가(**스냅샷**)로 계산한다. 단가가 없는 모델로는 시작하지 않는다(0으로 두지 않음). 비용은 정수 연산(토큰 × 마이크로 단가, 올림)이다.
4. **이름**: 아래 표 이름과 명령 이름.

**새 표(마이그레이션 `002_ai_connections.sql`)**

`runs` 표는 CHECK 두 개를 넓히려고 다시 만들었다: `go_block_reason`에 **`cost_cap`**을 더하고, mode A 제약을 "(provider=`opencode-go` 이고 model `opencode-go/%`) **또는 runtime=`pes_builtin`**"으로 바꿨다(기존 행·기존 Go 쌍은 그대로 통과). 데이터는 모두 복사하고 지우는 것이 없다.

- `migrate()`는 마이그레이션 첫 줄의 `-- pes:foreign_keys=off`를 읽으면 그 한 트랜잭션 동안만 외래 키 검사를 끄고(PRAGMA는 트랜잭션 안에서 바뀌지 않는다), 끝내기 전에 `PRAGMA foreign_key_check`를 돌려 어긋난 행이 하나라도 있으면 전부 되돌린다. 끝나면 항상 다시 켠다. 그 밖의 마이그레이션은 이전과 같다.
- **D1(운영)**: 같은 방식이 D1에서는 안 된다(`runs`를 가리키는 RESTRICT 외래 키는 `defer_foreign_keys`로 미룰 수 없다). 5단계의 D1 적용에서 별도 절차가 필요하다. 지금은 로컬 SQLite만 검증했다. `tests/test_d1_smoke.test.ts`는 001만 적용한다.

`dispatch.prepare`(`provider=ai_connection`)는 필수 필드 `reservation{input_tokens,output_tokens}`를 받아 **같은 트랜잭션에서 사용량·비용 문턱을 판정**하고(넘으면 `conflict`, `details.reason`=`usage_limit`|`cost_cap`|`extra_usage_off`·`reset_at`), 예약을 `allowance_json`에 기록한다. 문턱은 완료된 호출뿐 아니라 진행 중(`prepared`·`authorized`·`sent`) 호출의 예약도 센다. 사람이 정리하지 않은 호출(`unknown` 포함)은 시각과 무관하게 모든 창에서 센다. 구독 연결은 연결의 지금 `credential_rev`로 기록된 유효한 추가 요금 꺼짐 확인과 기준점이 없으면, 또는 그 확인 뒤 과금 신호가 기록됐으면(그 호출이 `unknown`이든, 사람이 어떻게 정리했든) `extra_usage_off`다. 비용이 숫자 범위를 넘는 답은 `unknown`으로 정산하고 run을 `usage_unknown`으로 멈춘다.

기존 명령의 변경: `run.create`는 선택 필드 `ai_connection_id`·`stage_id`·`round_id`를 받는다(`runtime=pes_builtin`, mode A일 때만 연결 필드; 프로젝트의 현재 선택과 같은 연결·모델이어야 하고, 연결이 지원 형식·살아 있음·쓴 만큼 과금이면 단가와 같은 통화의 상한이 있어야 한다). `dispatch.prepare`는 provider `opencode-go` 말고 `ai_connection`도 받는다(그 run에 `ai_run_settings`가 있어야 한다).

**mode A run은 internal_ai만 만든다(SEL-68)**: `run.claim`(새 run·`run_id` 이어받기)과 `run.create`는 mode A이거나 Go 라벨(provider `opencode-go` 또는 model `opencode-go/` 접두 — mode를 B로 적어도)이면 대상 actor 종류가 `internal_ai`가 아닐 때(external_agent 토큰·사람 세션) 403 `forbidden`(`retryable=false`)이다. 이 판정은 코어 명령(`commands/shared.ts`의 `require_internal_ai_for_go_run`)과 API 층이 같은 함수로 하므로 CLI·MCP도 같은 규칙을 지나며, run·lease·영수증·사건을 쓰기 전에 거절해 같은 Idempotency-Key를 다시 보내도 같은 거절이고 아무것도 쓰지 않는다. Go 정책(`allow_opencode_go`) 검사는 mode A 경로에서 호출자 종류와 무관하게 돌아, `internal_ai`가 Go OFF에서 요청하면 API는 `policy_blocked`, 코어 명령(CLI)은 닫힌 오류 코드 `policy_denied`다. 코어 명령도 API와 같은 순서(권한 403 → 모양 400 → Go 정책)로 거절하고, 403의 `target`(`$.body.mode`·`provider`·`model`·`run_id`)과 `details.actor_kind`가 거절 이유를 알려 준다. 같은 키의 성공 영수증을 다시 보낼 때도 코어(`CommandService`)는 재전송 전에 같은 트랜잭션에서 읽기 전용으로 현재 대상 actor 종류(403)와 mode A의 Go 정책(`policy_denied`)을 다시 검사하고, 통과하면 원래 결과를 그대로(`replayed:true`, 새 행 없음) 돌려준다(`run.claim`·`run.create`만, 다른 명령은 그대로). Go 라벨은 한 순서로 접은 뒤 비교한다 — NFKC → 서식문자(Cf) 제거 → 앞뒤 공백 제거 → 소문자 → 하이픈류·밑줄·공백을 `-` 하나로, `/` 옆 구분자와 앞 구분자 제거, 바뀌지 않을 때까지 반복(고정점; `fold_go_label`, OpenCode TUI 어댑터도 같은 접기를 쓴다). 이 변경 전에 external_agent·사람 세션으로 만든 mode A run은 `run_id` claim이 403이므로, 있으면 interrupt/cancel로 정리한다.

**보장**

- 키는 표·사건·영수증·명령 입력·로그·DTO·응답 어디에도 없다(표에는 끝 4자리와 저장 위치 이름만). 키 저장소는 인터페이스이고 로컬은 OS 비밀 저장소(구현만; 시험은 가짜 저장소).
- 연결 시험은 PES 서버가 하고, 실패하면 키 저장소도 표도 바뀌지 않는다. 등록·변경·삭제·시험·단가는 요청마다 재인증 코드를 쓴다.
- 모델 호출마다 호출 기록(`prepared→authorized→sent`)이 **요청 전에** 있다. 응답 유실·시간 초과·저장 실패는 `unknown`이고 자동 재호출은 없다. 쓴 비용·토큰은 `response`/`adopted` 행(그리고 정리 안 된 unknown 행)에서 센다.
- 정책 스위치(`allow_opencode_go`)는 AI 연결 전체의 스위치로 호출마다 본다. 꺼지면 다음 호출은 나가지 않고 run은 `interrupted`(사건 `policy_off`)다.
- 공급자 답(모델 목록 포함)에 현재 키(전체 또는 8글자 조각 — `\uXXXX` 여러 겹·`%xx`·base64로 감싼 것, 도구 인자의 두 번째 JSON 해석 결과까지)가 있으면 그 답은 명령·표·DTO·다음 요청에 가지 않고 `unknown`(`key_in_reply`) + `usage_unknown`이다(모델 목록이면 연결 시험 실패 `key_in_reply`). 키 검사는 모든 층을 되짚기 없는 선형 스캔으로 벗기고 작업량 상한을 단계 전에 깎아 정해진 시간 안에 끝난다. 검사가 예외나 작업량 상한으로 끝나지 못하면 닫힌 쪽으로 보아 `unknown`(`key_check_failed`) + `usage_unknown`이다(모델 목록이면 연결 시험 실패 `key_check_failed`). 모양을 읽을 수 없는 답(배열 안 `null` 등)은 예외 대신 `unknown`(`unreadable_reply`) + `usage_unknown`이다. 공급자 오류의 `code`·`type` 원문은 저장하지 않는다. 과금 신호는 HTTP 상태 판정 전에 읽어, 과금됨·읽을 수 없음 신호가 있는 오류 답(429 포함)·끊긴 본문은 `failed`가 아니라 `unknown`(`charged_error`, 신호·예약 보존) + `usage_unknown`이고 구독 연결의 꺼짐 확인을 무효로 한다. 도구 이름은 전송 이름(`context_get` 등)과 고정 표로 매핑한다.
- 정산 저장(`dispatch.settle`)도 같은 요청 키로 `save_retries`번 다시 하고, 끝내 실패하면 `unknown`(답 해시·토큰 보존) + `usage_unknown`이다. 연결 키·주소 변경·삭제는 연결마다 직렬화하고, 실패한 변경의 되돌리기는 저장소에 자기 키가 남아 있을 때만 한다. 실행기와 연결 시험은 주소와 키를 같은 잠금 아래에서 함께 읽고 키 끝 4자리를 표와 대조한다(새 키가 이전 주소로, 이전 키가 새 주소로 가지 않는다).
- 새 사건 type: `ai_connection.reauth_issued|registered|updated|removed|tested|price_set|extra_charge_off_confirmed|usage_baseline_recorded`, `project.ai_connection_set`, `dispatch.response_recorded|failed|adopted|unknown_resolved`, `run.blocked_usage`. (`dispatch.unknown`은 기존 type을 재사용한다.)

**알려진 한계**: 호출 중 실행기가 죽으면 호출이 `sent`로 남아 재개를 막는다 — 사람이 `dispatch.resolve_unknown`으로 정리할 수 있고(정리 전까지 게이트는 예약으로 계속 센다), 재시작 이어가기는 PR21이다. OpenAI 호환 본문은 `max_tokens`만 쓴다(`max_completion_tokens`만 받는 모델은 미지원, 확인 필요). 응답 본문은 8MiB까지만 읽는다. `thread.reply`는 대응 명령이 없어 미연결(allowlist에만 있고 모델에게는 노출하지 않는다 — 명령이 생기면 노출), `followup.propose`만 `project.add_note` 메모다(가정·결정·반영 제안 세 도구는 SEL-93에서 실제 명령 `assumption.propose`·`decision.propose`·`reflection.create`를 부른다). 구독형 사용량 공식 API와 OS 키체인 실동작은 미확인이다.

### 8.17 방식 B 어댑터 — Claude Code·Claude 앱(PR20a)

MCP 서버(`scripts/pes_core/mcp_server.ts`)와 어댑터(`scripts/pes_core/adapters/{claude_code,claude_app,api_client,http_api}.ts`)는 **PES HTTP API 위의 얇은 층**이다. 새 코어 명령도 새 HTTP 경로도 새 표도 없다(명령 등록표·경로표·마이그레이션 불변 — 이 PR20a 시점의 서술이다. 이후 SEL-93이 가정·결정·반영 명령 7개와 `POST /assumptions`·`/decisions`·`/reflections` 경로를 더했고 MCP 도구가 그 경로를 부른다). 공통 계약과 예시는 `docs/adapters/adapter-contract.md`이고, 그 문서의 `json pes-example` 블록은 시험이 그대로 실행한다.

- **MCP 도구는 닫힌 16개**다: `pes_context`·`pes_read`·`pes_claim`·`pes_submit`·`pes_ask`·`pes_wait`·`pes_complete`·`pes_heartbeat`·`pes_release`·`pes_cancel`·`pes_receipt`, 그리고 3단계 U3a(SEL-93)의 `pes_assumption_propose`·`pes_decision_propose`·`pes_reflection_write`(제안·반영 내역 쓰기만, lease 불필요), 3단계 U4a(SEL-99)의 `pes_thread_reply`·`pes_followup_propose`(답글·후속 제안만, lease 필요). 승인·재개방·봉인·정책·등록·토큰 도구는 없고, 가정 확인·결정 채택·대체·폐기, 스레드 해결·후속 채택·앵커 다시 붙이기 도구도 없다. 도구가 할 수 있는 일은 에이전트 토큰의 범위와 API 규칙이 정한다(어댑터는 권한을 판단하지 않는다). PES의 거부는 `isError: true` 도구 결과에 API 오류가 그대로 실린다(프로토콜 오류가 아니다). 토큰은 메모리에만 있고 `Authorization` 헤더에만 쓰이며 어떤 답·파일·DB에도 남지 않는다. 표준 출력에는 JSON-RPC 줄만 나간다.
- **읽기 도구 둘**: `pes_context`와 `pes_read`는 읽기만 하고 멱등 키가 없다. `pes_context`는 `GET /context`에, 아는 실행이 있으면 `GET /runs/{r}/inputs`의 답 목록(`inputs`)을 붙인다. 한 번에 **한 쪽**(최대 50개)만 읽고(`GET /runs/{r}/inputs?limit=`; 서버는 `limit` 1~100을 받는다), 더 있으면 `inputs_has_more: true`와 `inputs_next_cursor`를 싣는다(둘은 응답 객체 맨 앞). 그 값을 `inputs_cursor`로 다시 주면 이어 읽는다(커서를 버리지 않는다. 더 없으면 `inputs_has_more: false`, `inputs_next_cursor: null`). 도구 결과는 같은 JSON이 text와 structuredContent로 두 번 나가므로 `inputs`는 JSON 16KB 이하로 제한한다 — 넘으면 같은 커서에서 `limit`을 절반으로 줄여 덜 담는다(빠지거나 겹치는 답 없음). `pes_read`는 `{object_id, version_id?}`로 이미 있는 버전 읽기 `GET /objects/{o}/versions/{v}`(PR14)를 그대로 부른다. 사람의 답은 `inputs`의 `object_id`·`input_version_id`로 읽어 `content.value`·`content.comment`·`content.question_version_id`를, 질문은 `inputs`의 `question_id`와 그 `question_version_id`로 읽어 질문 글·선택지를 얻는다. `version_id`를 생략하면 `GET /context` 자료 목록의 현재 버전이다(목록에 없으면 `not_found`). 권한·Go·AI 참조 금지 파일 숨김은 API 규칙 그대로다(도구가 판단하지 않는다).
- **멱등 키**: `pes_context`·`pes_read`를 뺀 모든 도구가 `idempotency_key`를 받아 API의 `Idempotency-Key`로 보낸다. 같은 키·같은 인자는 처음 답을 되돌려 주고(행 0개), 같은 키·다른 인자는 `idempotency_key_reuse`다. 키가 없으면 `invalid_payload`(`$.arguments.idempotency_key`)이지만, **자격·범위 거부와 모르는 실행(`not_found`)이 도구의 입력 검사보다 먼저** 답한다: 입력이 모자란 도구(키 없음, lease 묶음 없음)는 쓸 수 없는 형태의 요청(빈 본문·키 없음)으로 PES에 먼저 물어 본다. 그 요청은 반드시 실패하므로 아무것도 쓰지 않는다. 이 순서를 위해 `POST /claims`는 `run_id`가 PES에 없는 실행이면 키가 없어도 `not_found`로 답한다(키 검사보다 대상 확인이 앞선다).
- **lease 묶음**: 서버는 마지막 claim의 `{run_id, lease_id, fence}`를 기억해 쓰고, 직접 준 값이 우선한다(새 연결이 이어받는 길). 없으면 `claim_required`. `pes_wait`·`pes_complete`·`pes_release`·`pes_cancel`은 기억한 lease를 잊는다. 다만 성공한 그 호출이 보낸 묶음(취소는 `run_id`)을 **도구·키별로** 기억한다(최근 256개): 답을 잃은 클라이언트가 같은 키·같은 인자로 다시 보내면 서버는 그 묶음으로 PES에 다시 보내고, PES가 자격·정책을 검사한 뒤 처음 답을 재생한다(`claim_required`가 아니다). 같은 키에 다른 인자는 `idempotency_key_reuse`다. 이 기억은 같은 키의 재전송에만 쓰이고 잊은 lease를 되살리지 않는다 — 새 키의 lease 작업은 계속 `claim_required`다. 재생(`replayed: true`)은 기억한 현재 묶음을 바꾸지 않는다 — 지우는 것은 재생이 아닌 실제 성공이면서 `run_id`·`lease_id`·`fence`가 모두 같을 때뿐이다(취소는 `run_id`만). 같은 run을 새 fence로 이어받은 뒤 옛 종료 키를 다시 보내도 새 묶음은 남는다. 이어받기는 새 fence라 옛 fence의 다른 연결은 `conflict`/`lease_lost`다.
- **진행 알림(heartbeat `progress`)**: `run.heartbeat` 명령이 선택 인자 `progress = {phase, observed_at?}`를 받는다. `observed_at`을 생략하면 명령 시각이 채워지고, 영수증 `result`와 사건 `payload`에 `progress`가 실린다(재전송은 영수증 그대로 되돌려 사건을 더하지 않는다). HTTP 답은 저장된 `progress`를 `run_id`·`lease`·`server_time`과 함께 싣는다(재전송이면 처음 저장된 값이다). MCP 도구는 그 답을 그대로 돌려주므로 `observed_at`은 저장값·사건과 늘 같다. `progress`는 요청 해시에 들어가므로 같은 키로 다른 단계를 보내면 `idempotency_key_reuse`다. 시작·단계 전환·완료·실패·대기·예정(`started`·`stage`·`completed`·`failed`·`waiting`·`scheduled`)은 같은 도구·같은 사건 종류·같은 멱등 규칙이다. 닫힌 `phase` 목록은 어댑터가 검사한다(API는 비어 있지 않은 문자열이면 받는다). heartbeat는 업무 revision(`control_rev` 등)을 바꾸지 않는다.
- **일반 결과 제출은 에이전트 토큰 전용**이다: `POST /runs/{r}/results`에 소유자 세션을 보내면 본문을 보기 전에 `403 forbidden`(`next_action: use_agent_token`)이다. 소유자가 남의 실행에 결과를 쓰는 길은 없다.
- **명시적 전달 가져오기(앱이 PES에 접속하지 못하는 경우)**는 `POST /runs`의 본문 `import`(소유자 세션 전용; 다른 필드와 함께 쓸 수 없다)로 한다 — **`run.create` 명령의 `import` 분기**이고 새 명령 이름이 아니다. 이 분기는 `via = import`일 때만, 사람 소유자 행위자에게만 열린다(그 밖은 `forbidden`). 한 트랜잭션에서:
  - 소유자 자신의 실행을 만든다: `mode B`, `runtime = claude_app_handoff`, `provider = anthropic`(`app`이 없을 때. 앱별 값은 8.19), `model = unknown`, 상태 `succeeded`(시작·끝 시각은 명령 시각), `actor_id`는 소유자. 에이전트 claim·lease·fence는 없다(`run.claimed` 사건 없음, `project_leases` 불변). 소유자는 **이 명령이 만든 자기 실행에만** 결과를 낼 수 있다.
  - 결과(`append_version` 1~20개)를 소유자 이름으로 쓴다. 판 검사는 `result.submit`과 같은 코드(`parse_result_items`·`plan_result_items`·`write_append_plan`)를 쓴다.
  - 영수증은 하나이고 행위자는 소유자, `via = import`, `run_id`를 싣는다(행위자와 실행의 행위자가 같아 `mutation_commits`의 `(project_id, run_id, actor_id)` 외래키를 지킨다). action 이름은 `run.created`라 `GET /requests/{key}`가 원래 상태 201을 그대로 말한다. 사건은 `run.created`·`result.submitted`(판마다)·`run.completed`이고 `result.submitted`의 `payload`에 `via: "import"`와 `provenance = {source: "manual_import", claimed_tool, claimed_model, verified: false}`가 실린다. 붙여 넣은 글이 말한 도구·모델은 주장이며 `runs.model`은 늘 `unknown`이다.
  - `expected_control_rev`가 있으면 같은 트랜잭션에서 `control_rev`와 비교한다(복사한 뒤 바뀐 프로젝트는 `rev_conflict`). `expected_heads = [{object_id, version_id}]`(묶음의 `base_versions` 전체, 최대 1000개 — 항목 약 105바이트라 약 105KB로, 본문 한도 256KB 안에 결과 자리를 남긴다. 넘으면 `invalid_payload`)가 있으면 **같은 트랜잭션에서** 각 자료의 현재 버전과 비교한다 — 머리 바꾸기(`content.set_current`)는 `control_rev`를 바꾸지 않으므로 `control_rev` 비교만으로는 못 잡는다. 하나라도 다르거나(보관된 자료 포함) 없으면 `rev_conflict`(`details.object_id`)이고 아무것도 쓰지 않는다. 어댑터는 이것을 `bundle_stale`로 바꾼다. 일반 결과 제출(`/runs/{r}/results`)의 기반 버전 규칙은 바뀌지 않는다(과거 버전을 기반으로 한 제안은 그대로 된다). 단계·라운드 id를 주면 현재 판에 있는지 확인한 뒤 실행 행에 싣는다.
  - **가져오기는 사람의 결정을 우회하지 못한다.** 승인된 단계에는 쓰지 않는다 — 단계가 `approved`이면 `conflict`(사람이 단계를 다시 열어야 한다). 봉인된 라운드에도 쓰지 않는다 — 지정한 라운드가 봉인이거나, 라운드를 안 줬을 때 단계의 현재 라운드가 봉인이면 `conflict`(새 라운드에서 다시 복사한다). 한 가져오기가 같은 자료(object)를 둘 이상 말하면 `invalid_payload`다(같은 자료의 버전이 서로 이어지는 갈래를 만들지 않는다. 서로 다른 자료 여러 개, 또는 자료 하나에 한 번은 허용). 거부는 모두 아무것도 쓰지 않는다(실행·영수증·버전·사건 0).
  - 멱등 키는 `import-<묶음 요청 ID>`이고 **서버가 강제한다**: `request_id`와 맞지 않는 키는 `invalid_payload`(`$.headers.idempotency-key`)이며 아무것도 쓰지 않는다. 그래서 다른 키로 같은 묶음을 두 번 가져올 수 없다. 어댑터는 먼저 `GET /requests/{key}`로 이미 가져왔는지 보고(있으면 `duplicate_import`), 그래도 동시에 두 번 온 요청은 키 재사용/재생을 `duplicate_import`로 바꾼다. 거부는 흔적이 0이라 거부된 묶음은 소모되지 않는다.
- **전달 묶음**(`export_bundle`)은 읽기뿐이다(실행·lease·행 0개). 승인된 단계는 복사할 수 없다(`conflict`, 사람이 단계를 다시 연 뒤 복사). 묶음의 `base_versions`(최대 1000개 — 어댑터가 복사 단계에서 넘으면 `payload_too_large`로 거부하고 묶음을 만들지 않는다. 쓰지 않는 자료를 보관해 줄이거나 MCP 연결로 처리한다. 붙여 넣은 묶음이 1000개를 넘거나 같은 자료를 두 번 말하면 `bundle_invalid`)는 **프로젝트 전체의 보조(artifact·source) 자료 머리 버전**이다 — 자료는 단계에 묶여 있지 않아 단계·라운드로 좁히지 못한다(PR20c 전에 다시 정한다). 그래서 단계와 무관한 자료 하나만 바뀌어도 `bundle_stale`이 된다. 가져올 때 어댑터는 같은 판(`edition_id`)·같은 단계(`stage_id`·`stage_key`)인지 다시 본다(아니면 `bundle_stale`/`not_found`). 봉인된 라운드는 복사 때가 아니라 가져올 때 서버가 `conflict`로 거른다. 필드는 `format_version`·`kind = pes.handoff`·`project_id`·`edition_id`·`stage_id`·`stage_key`·`round_id`·`base_control_rev`·`base_versions`·`request_id`·`manifest_hash`·`instructions`이고 토큰·세션 비밀·lease/fence는 없다. `manifest_hash`는 나머지 필드의 정규 JSON의 SHA-256이다 — **복사 뒤 일부가 바뀐 사고를 잡을 뿐 인증이 아니다**(권한은 소유자 세션이 준다). 가져오기 검사 순서는 어댑터에서 형식(`bundle_invalid`) → hash(`bundle_hash_mismatch`) → 프로젝트(`bundle_wrong_project`) → 중복(`duplicate_import`) → 붙여 넣은 글(`bundle_invalid`) → 범위(`result_out_of_scope`) → 첨부(`attachment_missing`/`attachment_unsupported`) → 같은 판(`bundle_stale`) → 같은 단계(`not_found`) → `control_rev`(`bundle_stale`) → 자료 머리 버전(`bundle_stale`) → 승인된 단계(`conflict`)이고, 그다음 서버가 쓰기 트랜잭션 안에서 키(`import-<request_id>`) → 같은 자료 중복(`invalid_payload`) → `control_rev`·자료 머리 버전(`rev_conflict` → 어댑터 `bundle_stale`) → 승인된 단계·봉인 라운드(`conflict`) → 쓰기 순으로 다시 본다. 어댑터의 앞선 확인은 빠른 안내일 뿐이고, 경합을 막는 것은 트랜잭션 안의 비교다. 중복이 최신성보다 앞인 것은 첫 가져오기가 판을 바꿔 두 번째가 `bundle_stale`로 보이지 않게 하려는 것이다.
- **연결 항목**: `claude_code_mcp_entry`는 MCP 설정에 넣을 `{command, args, env}`만 만들고 파일을 읽지도 쓰지도 않는다. 토큰은 값이 아니라 참조(`${PES_AGENT_TOKEN}`)다. MCP 서버 프로세스는 `PES_API_BASE_URL`이 루프백 `http`일 때만 시작한다(토큰이 이 컴퓨터를 떠나지 않는다).
- **시험**: `tests/test_adapter_b_claude_*.test.ts`(가짜 MCP 클라이언트, 합성 프로젝트; 실제 Claude·앱·MCP 설정은 읽지도 쓰지도 않는다).
- **한계**: 실제 Claude Code·Claude 앱 연결은 시험하지 않았다(문서에 「미확인」). 가져오기는 첨부 파일을 저장하지 않는다. `pes link`·`pes sync` CLI는 만들지 않았고 계약은 초안으로 문서에만 있다. `pes_receipt`의 `applied`는 **같은 실행의 `pes_submit` 키**만 증거로 받는다(다른 도구의 키, 다른 실행의 제출 키는 `not_found`). MCP 서버의 `POST /claims` 키 없는 호출은 PES를 한 번 더 부른다(요청 예산은 입력 오류라 돌려받는다).

### 8.18 방식 B 어댑터 — Codex CLI·OpenCode TUI(PR20b)

20a의 MCP 서버(`scripts/pes_core/mcp_server.ts`)와 계약(`docs/adapters/adapter-contract.md`)을 **그대로** 쓴다. 새 코어 명령·HTTP 경로·표·마이그레이션이 없고, MCP 서버 코드도 바뀌지 않는다. 어댑터(`scripts/pes_core/adapters/{codex_cli,opencode_tui,cli_common}.ts`)는 도구의 MCP 설정에 넣을 연결 항목을 만들 뿐 파일을 읽지도 쓰지도 않고 프로세스도 띄우지 않는다. 도구별 노트는 `docs/adapters/{codex,opencode-tui}.md`이고, 그 문서의 `toml/json pes-config` 예시는 시험이 임시 폴더에 써서 읽고 `pes-example` 흐름은 그대로 실행한다.

- **실행 표시**: `runs.mode = B`, `actors.kind = external_agent`. Codex CLI는 `runtime = codex_cli`, `provider = openai`(도구를 만든 쪽), OpenCode TUI는 `runtime = opencode_tui`, `provider = unknown`(여러 제공자). 모델은 도구가 PES에 알려 주지 않으므로 연결 항목에 사람이 적지 않으면 `unknown`이다. 사용량은 B 실행에 기록하지 않는다(숫자를 지어내지 않는다).
- **토큰은 값이 아니라 이름/참조**: Codex 항목은 `env_vars = ["PES_AGENT_TOKEN"]`(Codex가 시작한 환경에서 넘긴다), OpenCode 항목은 `"{env:PES_AGENT_TOKEN}"`(OpenCode가 확장한다)이다. 어떤 설정 파일·`env`에도 값이 없다. 값은 도구를 켜는 쪽이 `codex_cli_launch_env`·`opencode_tui_launch_env`로 키 저장소에서 **한 번 읽어(`get(ref)`, `ref = pes-agent-token-<runtime>-<project_id>`)** 메모리로만 받아 프로세스 환경에 넣는다. 키 저장소에는 쓰지도 지우지도 않는다. 없으면 `token_missing`(한국어)이다. 다른 도구의 ref만 있는 경우도 없는 것이다. 어댑터의 키 저장소 타입은 PR19 `KeyStore`(`a_runtime/keystore.ts`)의 `Pick<KeyStore, "get">`이며 타입만 가져오므로 실행 시 의존은 없다(`project_id`가 키 저장소 이름 문자 집합 `[A-Za-z0-9._:-]` 밖이면 `field_invalid`). **지금 `pes-agent-token-*` 항목을 키 저장소에 넣는 PES 명령은 없다** — 현재 절차는 사람이 `PES_AGENT_TOKEN` 환경변수로 직접 두는 것뿐이다.
- **OpenCode 설정 형식**: 공식 문서(2026-11-11 확인)의 현행 형식 `mcp.servers.<이름>`(`enabled` 없음, 끄려면 `disabled`)으로 항목을 만든다. 옛 형식 `mcp.<이름>` + `enabled`는 스키마에서 `deprecated`라 쓰지 않는다. 호출 제한은 `pes_wait`(최대 25초)보다 길어야 한다: Codex `tool_timeout_sec` 기본 60초, OpenCode 현행 `execution` 기본 12시간(옛 형식 `timeout` 기본 5초는 부족).
- **입력 규칙**: `api_base_url`은 정규 루프백 origin(`http://127.0.0.1[:포트]`·`localhost`·`[::1]`)만 받고(사용자 정보·경로·쿼리·조각·역슬래시·앞뒤 공백 거부), 항목에는 정규화한 origin을 적는다(토큰이 컴퓨터를 떠나지 않는다). `command`·`server_script`·`project_id`·`model`은 제어 문자(줄바꿈·CR·탭·NUL·DEL·U+2028/2029)와 `{env:…}`·`{file:…}` 치환 표기를 거부한다(공백·따옴표는 경로 데이터로 허용; 두 도구 공용. 모델의 공백·서식 문자 거부와 Go 차단은 OpenCode 항목에만 있고, Codex 항목은 모델을 라벨로만 적는다). 거부는 고정 `code`(`field_invalid`·`substitution_blocked`·`api_base_url_invalid`)·한국어 설명의 `TypeError`이며 값을 되풀이하지 않는다.
- **내장 실행기(방식 A)와의 구분**(결정 0019): 방식 A 실행(`pes_builtin`, `opencode-go`)과 B 실행은 프로젝트의 lease 하나를 나눠 쓴다. 한쪽이 잡고 있으면 다른 쪽의 claim은 `conflict`이고 아무것도 쓰지 않는다. B 라운드는 A 쪽 표(디스패치·사용량·Go 계량·연결)를 바꾸지 않고, B 연결은 A 실행을 만들 수 없다.
- **Go 경로**: OpenCode TUI 연결 항목은 모델 이름을 NFKC로 접고 서식 문자(너비 0·소프트 하이픈·BOM·방향 바꿈)를 지우고 하이픈류·밑줄·공백을 한 구분자로 본 뒤 `opencode-go`로 시작하면 `go_route_blocked`로 거부한다(공백·서식 문자가 든 모델은 Go가 아니어도 거부). 한계: 키릴 호모글리프 같은 다른 문자 체계의 흉내는 풀지 못하고, 사람이 OpenCode 안에서 Go 모델을 고르는 것은 PES가 보지도 막지도 못하고 Go 계량에 잡히지 않는다 — Go는 방식 A 전용이다. Codex CLI는 Go 경로와 무관하다.
- **닫힌 도구**: 도구는 20a의 11개 그대로다. 승인·재개방·봉인·정책·등록·토큰·삭제·export 도구는 없고, 에이전트 토큰으로 그 API를 불러도 거부된다.
- **시험**: `tests/test_adapter_b_codex.test.ts`, `tests/test_adapter_b_opencode_tui.test.ts`(공용 `tests/helpers/adapter_b_cli_suite.ts`; 가짜 MCP 클라이언트·합성 프로젝트·가짜 키 저장소). 실제 `codex`·`opencode`를 실행하지 않고 사용자의 `~/.codex`·OpenCode 설정 폴더를 읽거나 쓰지 않는다.
- **한계**: 실제 Codex CLI·OpenCode TUI 연결은 시험하지 않았다(두 노트에 「미확인」). 도구 버전별 `env_vars`·`{env:VAR}` 처리와 긴 대기 중 연결 끊김은 확인하지 않았다. 서버 시작·호출 제한 시간은 공식 문서의 기본값만 노트에 적었고 실제 동작은 미확인이다. 두 도구의 모델·사용량은 PES가 알 수 없다. 토큰을 키 저장소에 넣는 명령은 후속이다(PR19에는 AI 연결 키용 저장소만 있다).

### 8.19 방식 B 어댑터 — Codex 앱·OpenCode 앱(PR20c)

앱은 길이 둘이다. **직접 연결**은 20b의 연결 항목과 같은 MCP 서버(`scripts/pes_core/mcp_server.ts`)·같은 11개 도구를 쓰고(코드·도구·경로표 불변), **명시적 전달**은 20a의 가져오기(8.17)를 그대로 쓴다. 직접 연결이 되는지는 확인하지 못했으므로 **보장하는 길은 명시적 전달**이다. 어댑터(`scripts/pes_core/adapters/{codex_app,opencode_app}.ts`)는 파일을 읽지도 쓰지도 않고 프로세스도 띄우지 않으며, 앱의 설정(`~/.codex`·OpenCode 설정 폴더)을 보지 않는다. 노트는 `docs/adapters/{codex-app,opencode-app}.md`이고, 그 문서의 `toml/json pes-config` 예시는 시험이 임시 폴더에 써서 읽고 `pes-example` 흐름은 그대로 실행한다.

- **직접 연결의 표시**: `codex_app_mcp_entry`·`opencode_app_mcp_entry`는 CLI·TUI 항목과 같은 모양이고 `PES_RUNTIME = codex_app | opencode_app`(`provider`는 `openai` | `unknown`, 모델은 `unknown`)이다. 행위자는 에이전트 토큰의 `external_agent`, 영수증의 `via`는 `import`가 아니다. 토큰은 값이 아니라 이름/참조(`env_vars` / `{env:PES_AGENT_TOKEN}`)이고, `codex_app_launch_env`·`opencode_app_launch_env`가 키 저장소에서 `pes-agent-token-<runtime>-<project_id>`를 한 번 읽는다. 터미널판의 ref는 읽지 않는다. 토큰이 없으면 `token_missing`이고 설명이 **명시적 전달**을 항상 쓸 수 있는 길로 알린다. OpenCode 앱 항목은 TUI와 같은 규칙(`on_go_route`를 TUI 모듈에서 가져와 쓴다)으로 Go 경로 모델을 `go_route_blocked`로 거부한다. Codex 앱은 Go 경로와 무관하다.
- **명시적 전달의 표시**: `CodexAppAdapter`·`OpencodeAppAdapter`는 `ClaudeAppAdapter`를 확장해 같은 생성자(`{api, project_id, owner_session}`)·같은 `export_bundle`·`import_result`·같은 거부 코드와 검사 순서를 쓴다. 다른 점은 `handoff_app()`(보호된 메서드, 기본 `claude_app`)를 바꿔 가져오기 요청이 앱을 이름으로 말하는 것뿐이다(Claude 앱은 `app`을 보내지 않는다). 가져온 실행은 소유자의 것(사람 행위자, `mode B`, 영수증 `via = import`, 에이전트 claim·lease·fence 없음, 출처 표지 `verified: false`)이고 `runtime = codex_app_handoff`(`provider = openai`) 또는 `opencode_app_handoff`(`provider = unknown`), 모델은 늘 `unknown`이다.
- **서버 변경(좁다)**: `POST /runs`의 `import`가 닫힌 목록 필드 `app`(`claude_app`·`codex_app`·`opencode_app`)을 받는다. 서버는 `commands/handoff_import.ts`의 표 `HANDOFF_APPS`에서 실행의 `runtime`·`provider`를 정한다 — 붙여 넣은 글이 아니라 서버의 목록이 정한다. 필드가 없으면 전과 같이 `claude_app_handoff`/`anthropic`이다(20a의 시험·픽스처 회귀 0). 목록 밖의 값(빈 문자열·숫자·null·배열·`constructor` 같은 객체 속성 이름 포함)은 HTTP 층에서 `400 invalid_payload`(`$.body.import.app`)이고 명령도 같은 검사를 한 번 더 하며, 거부는 실행·영수증·버전·사건 0이다. `app`은 요청 해시에 들어가므로 같은 키에 다른 앱이면 `idempotency_key_reuse`다. 새 명령·경로·표·마이그레이션은 없다. `api.ts`의 claim·Go 검사와 `commands/runs.ts`는 건드리지 않았다.
- **Codex 앱·OpenCode 앱·터미널판의 구분**: 네 연결(`codex_cli`·`codex_app`·`opencode_tui`·`opencode_app`)은 각자의 runtime·ref를 쓰고, 프로젝트의 lease 하나를 나눠 쓴다(한쪽이 잡으면 다른 쪽 claim은 `conflict`, 쓰기 0). 명시적 전달은 lease를 쓰지 않는다. 앱 연결과 전달 모두 방식 A 표(디스패치·사용량·Go 계량·연결)와 A 실행 행을 바꾸지 않고, 어댑터는 `a_runtime`에서 타입만 가져온다. 방식 A 내장 실행기의 프로필·서버는 재사용도 중단도 하지 않는다. `external_agent`의 방식 A claim 거부는 SEL-68이 구현했고, 이 PR은 공용 시험(`adapter_b_cli_suite.ts`)으로 두 앱의 직접 연결에서도 그 거부(403·상태 변화 0)를 확인한다.
- **설정 공유는 미확인**: Codex 앱이 Codex CLI와 `config.toml`을, OpenCode 앱이 TUI와 MCP 설정을 나눠 쓰는지는 확인하지 않았다. 두 노트가 「미확인」과 「시험 결과」로만 적고 보장으로 쓰지 않는다. 확인되면 시험 결과로 노트에 적는다.
- **변하지 않은 것(8.17)**: 전달 묶음의 `base_versions`는 여전히 프로젝트 전체의 보조 자료 머리 버전이고 최대 1000개다. 단계·라운드로 좁히는 일은 이 PR이 하지 않았다(한계로 남는다). 첨부 파일은 저장하지 않는다.
- **시험**: `tests/test_adapter_b_codex_app.test.ts`, `tests/test_adapter_b_opencode_app.test.ts`(공용 `tests/helpers/adapter_b_app_suite.ts`·`adapter_b_cli_suite.ts`; 가짜 MCP 클라이언트·합성 프로젝트·가짜 키 저장소·임시 HOME). 실제 Codex 앱·OpenCode 앱·`codex`·`opencode`를 실행하지 않고 사용자의 앱 설정을 읽거나 쓰지 않는다.
- **한계**: 실제 앱의 직접 연결은 시험하지 않았다(두 노트에 「미확인」). 앱 버전별 MCP 설정 형식·`env_vars`/`{env:VAR}` 처리·긴 대기 중 연결 끊김은 확인하지 않았다. 앱의 모델·사용량은 PES가 알 수 없다. 사람이 앱 안에서 Go 모델을 고르는 것은 PES가 보지도 막지도 못한다. 토큰을 키 저장소에 넣는 명령은 후속이다.

### 8.20 A·B 교차 계약(PR21, SEL-56)

A(내장 실행기, `internal_ai`)와 B(MCP·HTTP, `external_agent` — 직접 연결 다섯 길과 앱 세 개의 전달 경로)가 **같은 시작 상태에서 같은 의미·권한·오류**를 내고, 인계·중복·충돌에서 유실이 없음을 가짜 AI 서버·가짜 MCP 클라이언트·합성 자료로 시험한다. 결정은 [0020](decisions/0020-cross-contract.md).

- **오류는 code·효과로 같다(해석 1).** 같은 code·같은 target·쓰기 0. 문장은 같게 하지 않는다 — A는 영어 `code: message`, B는 code마다 고정된 한국어 문장(B의 여섯 도구는 byte 단위로 같다). SQL·표 이름·스택은 둘 다 보이지 않는다.
- **옛 guard 거부 code(해석 3).** `heartbeat`·`release`는 `lease_lost`, `submit`·`wait`·`complete`는 `conflict`로 갈린다. `input-receipts`는 이번 이슈에서 시험하지 않았다(guard 시험에는 보이는 입력이 필요하다) — 계약에 넣지 않는다. 현재 동작을 계약으로 고정하고(둘 다 거부·쓰기 0), 통일은 후속이다.
- **인계(해석 9~12).** 인계 = lease를 내려놓음(release·만료·interrupt) 뒤 다른 쪽의 새 claim. B는 A run을 `run_id`로 이어받지 못하고(SEL-68) 새 run·새 lease가 선다. fence는 프로젝트 lease 한 줄에서 claim마다 정확히 +1. 같은 키의 재전송은 lease가 넘어간 뒤에도 처음 답 재생. 경합에서 진 claim은 `conflict`이고 흔적 0(A 쪽은 owner가 먼저 만든 `queued` run 1개가 남을 수 있다).
- **제출은 승인이 아니다(해석 13).** 채택 전 제출 버전은 DB에 남지만 다음 context에는 보이지 않는다 — 유실이 아니다.
- **지연·종료·Go OFF·사용량 문턱.** 늦게 온 답은 채택하지 않고 run은 `blocked_usage`·lease 해제. 프로세스 종료는 run이 `running`·lease `active`·호출 `sent`로 남고(해석 14·15), lease TTL 뒤 B의 새 claim이 그 run을 `interrupted`(`lease_expired` 사건)로 끝낸다. Go OFF·비용 상한·구독 문턱은 A만 막고 B는 영향이 없다(해석 5·16).
- **`unknown` 예약 보존(해석 17·18).** 호출 행은 B 인계·Go OFF/ON·재시작·한 달 시계 뒤에도 한 글자도 안 바뀌고, 사람이 정리하기 전에는 재개가 막히며 예약이 한도에 계속 잡힌다. 정리는 사람만, 행 옆에 한 줄 기록. B는 `unknown`을 만들 수도 정리할 수도 없다.
- **F1 수정(죽은 run 이어받기).** `running` + 프로젝트에 살아 있는 lease 없음(만료)인 run은 **같은 행위자**가 이어받는다: B `run.claim {run_id}`(`commands/runs.ts`), A `resume`(`a_runtime/loop.ts`). 새 lease는 fence +1, 옛 lease는 `run.interrupted`(`reason: lease_expired`, 옛 `lease_id`·`fence`) 사건을 남기고 교체된다. 활성 lease가 살아 있으면 `conflict`, 다른 행위자 run·SEL-68·`PRE_REPLAY_TABLE`은 그대로다. A는 정산 안 된 dispatch(`prepared`·`authorized`·`sent`·`unknown`)가 있으면 `conflict` — 사람이 정리한 뒤에만 이어받는다. 옛 guard는 계속 거부된다.
- **B의 외부 비용은 집행했다고 표시하지 않는다.** B run에는 dispatch·사용량·단가·A 설정이 없고 API·MCP 답·사건·영수증에 비용 필드가 없다(프로젝트 `policy` 묶음 제외, 해석 8).
- **D1(해석 19·20).** SQLite와 로컬 D1(miniflare)이 같은 성공·충돌·부분 실패를 내는지 같은 문장 표로 본다. **001 스키마 한정** — 002의 D1 적용은 검증하지 않았다. 표의 SQL은 서비스 코드를 import하지 않고 다시 쓴 것이다. **release·heartbeat는 `commands/runs.ts`와 같은 모양이고, claim은 D1에서 쓸 CAS 변형(`fence`·만료 조건 추가)이며 `runs.ts`의 claim UPDATE와 다르다.** 따라서 이 표는 서비스 SQL의 D1 등가 증명이 아니라 "D1에서 claim을 CAS로 쓰면 SQLite와 같은 결과를 낸다"는 시험이다. 5단계에서 D1 claim을 CAS로 바꿀 때 이 표를 기준으로 삼고, `runs.ts`의 release·heartbeat UPDATE 모양이 바뀌면 이 표도 같이 고친다.
- **시험**: `tests/test_cross_contract.test.ts`(같은 시작 상태 표), `test_cross_handoff.test.ts`(인계·옛 fence), `test_cross_scenarios.test.ts`(지연·종료·Go OFF·사용량·F1), `test_cross_unknown.test.ts`(예약 보존), `test_cross_d1.test.ts`(SQLite/D1); 도우미 `tests/helpers/cross_{env,driver}.ts`; 표 `tests/fixtures/contracts/cross/{same_outcome,b_tools,d1_scenarios}.json`.
- **D1 로컬 smoke 조건**: `PES_D1_SMOKE=1` 또는 `tests/d1/node_modules`(miniflare)가 있으면 D1 부분을 돌리고, 꺼져 있으면 사유와 함께 skip한다(`PES_D1_SMOKE=1`인데 도구가 없으면 실패). CI는 `d1-smoke` 워크플로가 돌린다(paths에 `tests/test_cross_d1.test.ts`·`tests/fixtures/contracts/cross/**` 포함).
- **한계**: 해석 3의 code 통일은 후속. D1 교차는 001뿐. 실제 모델·실제 B 에이전트는 호출하지 않았다.

### 8.21 TypeScript CLI `scripts/pes.ts` — 0.15 동작을 DB 위에서 (PR26b-1, SEL-71)

`node scripts/pes.ts <명령>`은 Node 26이 타입을 지워 바로 돌린다(tsx·ts-node·빌드·로더 없음). 진입 파일은 얇고(`scripts/pes.ts`), 본문은 `scripts/pes_core/cli_main.ts`와 `cli_*.ts` 모듈이다. 쓰기는 모두 코어 한 번 호출(`cli_bridge.handle_request`, Python 이 자식 프로세스로 부르던 그 코드 — 이제 같은 프로세스 안에서)이고, `project.json`·`.pes-lock`·업무 SQL 은 이 파일들에 없다. 이 PR 이 옮긴 명령: init·ask-prep·ask·round-start·merge·render·approve·reopen·status·mark·chat·note·set·qa-brief·qa·lock·unlock·home·remote·stop. 읽기·보고서 명령(pending·digest·show·report·assemble·web·list·hub·open·which·doctor·serve·watch)은 이 PR 에서는 이름만 알고 "아직 없다"는 한국어 한 줄과 종료 1로 답했다(SEL-77 에서 들어옴 — 8.22). DB 로 옮기지 않은 옛 `project.json` 폴더에 쓰기 명령을 내리면 거절한다 — 이 PR 에서는 종료 2 였고 SEL-77 부터 종료 1 + 한국어 한 줄이며 폴더는 그대로다(D14, 읽기 명령은 0.15 처럼 읽는다).

사용법 글은 `pes.py` 의 `__doc__` 그대로이고 첫 줄의 실행 명령만 `node scripts/pes.ts`다. 인자 오류·종료 코드·stdout/stderr 는 0.15 와 같다. 0.15 가 Python 스택 추적으로 죽던 곳(없는 결과·질문 파일, 깨진 JSON, 모자란 인자, `merge` 결과의 잘못된 `sources`)은 같은 종료 코드와 스택 없는 한국어 한 줄이다(D11). 사용자에게 나가는 CLI 경로의 영어 `code: message` 두 줄(아래 D13)도 한국어 한 줄로 바꿨다. 문서가 만든 파일은 어느 OS 에서나 UTF-8·LF 이고 저장 경로는 `/`다(D10, W1·W2) — 생성 파일은 한 쓰기 도우미 `cli_support.write_text` 가 LF 로 맞춰 쓰고, `.gitattributes` 가 `templates/`·`questions/`·`tests/fixtures/` 를 Windows checkout 에서도 LF 로 둔다.

0.15 는 어느 단계든 언제든 쓸 수 있었고 DB 는 단계 순서·라운드·봉인을 지킨다. 그 틈을 CLI 가 메우는 방식(모두 `scripts/pes.ts` 가 켜는 선택 항목이다 — 기본 동작과 `pes.py` 경로, 기존 코어 시험은 바뀌지 않는다):

- **`round.start { any_order }`**: 앞 단계가 승인되지 않아도 그 단계의 라운드를 열고, 그 단계가 프로젝트의 `current` 가 된다(0.15 `round-start`). **이미 승인된(낡지 않은) 단계는 열지 않는다** — 의도된 차이 D13: exit 1, stdout 비움, stderr `round-start: 기획은 이미 승인됐습니다 — 먼저 reopen 하세요`(단계 이름은 해당 단계). 0.15 는 승인된 단계에서도 라운드를 더하고 status 를 active 로 돌렸다.
- **`approve` = `compat_approve`**: 열린 라운드가 있으면 봉인하고, 없거나 낡았으면(reopen 뒤) 라운드를 하나 열어 CLI 가 스스로 봉인한 뒤 승인한다. **앞 단계가 승인되지 않았으면 승인하지 않는다**(DB 의 "승인은 승인된 일 위에서" 보장을 풀지 않는다) — 의도된 차이 D13: exit 1, stdout 비움, stderr `approve: 앞 단계(기획)가 아직 승인되지 않았습니다`(괄호는 아직 승인되지 않은 가장 앞 단계). 0.15 는 순서 없이 승인했다. CLI 가 스스로 연 라운드는 **서버가 정하는 표지**로 알아본다: `round.start` 의 `implicit`(CLI 전송 `via = cli` 만 받는다. 다른 전송은 `invalid_payload`)이 라운드 시작 영수증(`mutation_commits.result_json.implicit`)에 남고, 읽기 모델은 이것을 **라운드로 세지 않는다**(`stages.<단계>.round` 는 사람이 연 라운드 수, 승인 기록 "(R0)"도 그 번호). 항목이 하나도 없는 단계는 보이지 않는 "승인 표지" 노트 하나를 봉인에 담는다(`kind note`, 어느 항목 목록·매니페스트에도 안 나온다). 이미 승인된(낡지 않은) 단계를 다시 승인하면 먼저 조용히 다시 열었다가 승인한다 — 이 reopen 은 `stage.reopen` 의 `quiet`(역시 `via = cli` 만)이 reopen 영수증에 남아 읽기 모델의 history 에 한 줄도 남지 않는다. 매니페스트 이름 `implicit-approval.json`·reopen 이유 `pes-cli:re-approve` 는 읽는 사람을 위한 이름일 뿐 읽기 모델은 믿지 않는다(업로드 이름·reopen 이유는 클라이언트가 고른다).
- **history 줄**: `stage.approved`(origin `new`)·`stage.reopened` 사건에서 `승인 <시각> (R<n>)`·`다시 열기 <시각>`을 읽기 모델이 만든다(importer 가 남긴 `legacy.history` 와 겹치지 않게 origin `new` 만).
- **`render` = `compat_render`**: 열린 라운드에 내용이 있으면 봉인하고, 이미 봉인된 라운드를 다시 `render` 해도 거절하지 않는다. `snapshots/<단계>-R<n>.json`(같은 라운드의 다른 상태는 `<단계>-R<n>/<k>.json`)은 0.15 처럼 폴더에 쓴다 — 읽기 모델의 그 단계 상태를 그대로.
- **`merge { v015 }`**: 같은 결과를 다시 보내면 `depth` 를 올리지 않는다(0.15 결함 ②, D06). 바뀐 내용이 있을 때만 새 판이다. `sources` 가 출처 객체 목록이 아니면(글자·숫자·글자 목록) 0.15 는 병합 도중 스택 추적으로 죽었다 — 지금은 첫 쓰기 전에 묶음 전체를 거절한다(exit 1, 한국어 한 줄, 아무것도 쓰지 않음; D11).
- **`note { allow_blank, stage_optional }`**: 글 없는 `note <dir>` 은 0.15 처럼 빈 메모를 남긴다. 현재 단계가 없는 손으로 쓴 옛 파일의 프로젝트는 메모를 단계 없이(`stage: null`) 둔다 — 이 완화는 `stage_optional`(CLI 전송만 받는다)이 켜졌을 때만이다. A 실행기·API 는 전처럼 `not_found` 를 받는다.
- **`chat { allow_blank }`**: 빈 글·공백만 있는 글도 0.15 처럼 답으로 기록하고 exit 0 이다(`input.record_chat` 의 `allow_blank`, CLI 전송만; API·화면 답은 전처럼 거절). `cli_bridge` 의 `chat` 은 `scripts/pes.ts` 가 `allow_blank` 를 보낼 때만 이것을 켠다 — `pes.py` DB 경로(`PES_DB_CORE=1`)의 `chat` 빈 답은 SEL-71 전처럼 거절이다.
- **`init { any_name }`**: 프로젝트 이름은 폴더 이름 그대로다(한글·공백 가능, 0.15 `pdir` 규칙). `pes.py` 경로는 소문자·숫자·하이픈 규칙을 그대로 둔다. `plan_asking` 이면 기획 단계가 처음부터 `asking`(0.15 init). 폴더를 먼저 만든다 — 못 만들면(파일이 길을 막음·권한·긴 경로) DB 에 프로젝트가 남지 않아 같은 이름으로 다시 `init` 할 수 있고, DB 가 거절하면 방금 만든 폴더를 지운다.
- **`set` = `set_field`**: 허용 필드 7개 값은 각각 눈에 안 띄는 `review` 종류 artifact 의 최신 판(`metadata.role` = `stage_field`/`project_field`, `field`, `value`)에 둔다. 읽기 모델이 값을 0.15 가 두던 자리(`stages.<단계>.summary`·`changes`·`carry_over`·`settings`·`review`, 최상위 `executive_summary`·`conclusion`, `plan settings` 는 최상위 `settings` 도)에 되돌려 놓는다. 같은 값을 또 쓰면 아무것도 바뀌지 않는다. 새 코어 명령은 없다(등록표 불변). 현재 값을 읽는 일과 쓰는 일은 한 `unit`(BEGIN IMMEDIATE) 안이라 폴더가 달라 잠금이 다른 같은 이름 프로젝트의 두 `set` 도 서로 결과를 본다(필드는 늘 객체 하나). 그 위에 읽고 고쳐 쓰는 동안 `<프로젝트 폴더>/.project.json.lock`(배타 생성·60초 묵은 잠금 정리·30초 기다림 후 종료 3·권한 오류는 Windows 이거나 잠금을 본 경우만 재시도, 아니면 종료 2 "권한", 끝나면 지우기 50번 재시도 뒤 조용히 포기 — SEL-75)을 잡는다. 이 파일은 사람·AI 가 직접 쓰는 상태 파일이 아니라 `scripts/pes.ts` 가 만들고 곧 지우는 **SEL-75 계약의 짧은 배타 잠금**이라 AGENTS.md 원칙 0 의 "잠금 파일을 직접 쓰지 않는다"의 예외다(DB 보장은 위 `unit` 이 지킨다).
- **lock·unlock**: `.pes-lock` 의 owner 는 lease 의 `runs.external_session_ref`(= `PES_OWNER`)다(D04). 거절 문구는 0.15 처럼 `<시작 시각>부터`를 넣고 `lock <폴더> --force` 안내에 사용자가 쓴 폴더를 보인다. 이 문구는 `cli_bridge` 공용 핸들러라 `pes.py` DB 경로 문구도 바뀐다(0.15 에 더 가까움).
- **읽기 모델 보강**: 가져온 참고자료 항목을 빈 껍데기가 아니라 옛 state.json 항목 모양으로(`id·title·summary·details·confidence·status·sources·stats·shots·conflicts`), `pes init --import` 의 참고자료 머리(`source·imported·round·topic…`)는 사건에서, 채팅 입력은 "처리 끝난 답"으로 보인다. `notes` 키는 아무것도 저장하지 않은 프로젝트에는 없다(0.15 는 첫 저장 때 만들었다). 현재 단계를 모르는 손으로 쓴 옛 프로젝트는 `current` 가 없다. `set` 값은 위 7개 필드만 받는다(다른 이름을 담은 review artifact 는 아무것도 바꾸지 못한다). **이 읽기 모델 변경은 `pes.py` DB 경로의 `status`·대시보드 출력도 바꾼다**(`notes` 키 생략, `current` 없음, 참고자료 항목 본문 채움, 라운드 수는 사람이 연 라운드만) — "기본 동작은 안 바뀐다"는 이 줄에는 해당하지 않는 의도된 변경이다(기존 시험은 모두 통과).
- **`via = cli` 의 뜻**: 위 선택 항목(`implicit`·`quiet`·`stage_optional`·`allow_blank`·`any_order`·`plan_asking`)의 "CLI 전송만"은 사람 CLI 만이 아니다 — A 실행기(내장 AI)도 `via = cli` 이며, A 실행기에서 CLI 전용 항목을 막는 것은 A 실행기의 고정 payload 다(도구가 payload 를 코드로 만든다). `any_order`·`plan_asking` 은 `implicit` 처럼 코어도 `via` 가 `cli` 가 아니면 `invalid_payload` 로 거절한다(API 의 고정 payload 와 두 겹).
- **W1(옛 Windows 데이터)**: importer 는 `reports[].path` 의 역슬래시를 `/`로 읽는다.
- **서버 꺼짐 판단**: `whoami` 를 허브 포트(8760~8764, 옛 8765~8775)에 `fetch` 로 물어 연결 거부(ECONNREFUSED)·시간 초과를 "서버 꺼짐"으로 본다(시험 가드가 막은 포트도 같다).

알려진 한계: 같은 폴더 이름의 프로젝트는 PES 홈 밖에서도 하나로 본다(slug = 폴더 이름). 승인되지 않은 단계의 `reopen` 은 0.15 와 달리 "승인된 단계가 아니라 다시 열 수 없다"로 거절한다. 앞 단계가 승인되지 않은 `approve` 와 이미 승인된 단계의 `round-start` 도 0.15 와 달리 거절한다(D13, 위 두 줄 — 계약 사례 X08·X09 가 0.15 기준값과 ts 기대값을 함께 고정한다). 영어 `code: message` 로 나가는 코어 거절은 위에 적은 경로(approve·round-start·merge `sources`)만 한국어로 바꿨고, 나머지 코어 거절(예: 이미 있는 이름)은 이전처럼 코어 문구다. `init` 이 DB 에 프로젝트를 만든 뒤 하위 폴더 만들기·라이브러리 복사·`feedback.log` 쓰기에 실패하면 프로젝트는 DB 에 남는다(다시 `init` 하면 "이미 프로젝트가 있습니다"). Windows 의 읽기 권한 오류(EPERM)는 EACCES 와 같은 `[Errno 13] Permission denied` 한 줄이다. `qa-brief` 는 읽기 명령 `digest` 가 아직 없어 DB 방식 지시문(`pes.py` DB 경로와 같은 글)을 쓴다.

### 8.22 TypeScript CLI — 읽기·보고서·서버·doctor 명령 (PR26b-2, SEL-77)

`scripts/pes.ts` 에 남아 있던 명령(`pending`·`digest`·`show`·`report`·`assemble`·`web`·`serve`·`hub`·`open`·`list`·`watch`·`which`·`doctor`)이 들어와 `pes.py` 의 모든 명령 이름이 있다. 상태는 코어에서만 읽고 쓰며(8.21 과 같은 호출), 사람이 보는 파일만 폴더에 쓴다.

- **보고서 파일**: `report`·`assemble`·`web` 은 코어에 새 버전을 쌓은 뒤 그 버전의 바이트를 `report_file` 로 읽어 `reports/<단계>/…`·`out/…` 에 UTF-8·LF 로 쓴다(폴더와 DB 가 같은 바이트). `report` 는 코어에 `plain: true` 를 보내 0.15 와 같은 보고서(버전 표시 줄 없음)를 받는다 — `pes.py` DB 경로는 그대로 버전 줄을 단다. `eli5.json`·`out/cover.json`·`out/appendix.md` 는 읽기만 한다. 0.15 처럼 `report` 는 `index.html` 을 다시 만들고 `assemble`·`web` 은 만들지 않는다. `report` 는 `reports/<단계>/` 의 `.docx`·`.hwpx`·`.pdf`·`.pptx` 를 0.15(`pes.py` cmd_report)처럼 단계 보고서로 등록한다 — 바이트를 코어 `report` 에 `attachments` 로 넘겨 같은 보고서 버전에 붙이고(기존 파일 등록 명령 `reserve_upload`·`attach_version`, 새 업무 SQL 없음) 폴더의 그 파일은 다시 쓰지 않는다. 읽기 모델 `reports`(대시보드·허브 링크)에 `/` 경로로 나온다(migration-ts-equivalence 2절 31번).
- **서버**: `serve.ts` 를 떼어 낸 자식으로 띄운다(현재 node 옵션을 그대로 넘긴다 — 시험의 권한 목록·가드도 따라간다). 허브 포트 범위는 `PES_HUB_PORTS`(migration-ts-equivalence 13절의 I1~I3), `PES_NO_BROWSER=1` 이면 `open` 은 아무것도 띄우지 않는다. `pkill` 은 `serve.py`·`serve.ts` 두 이름을 모두 찾는다. 기록 파일(`.pes-hub-server`·옛 `.pes-server`)의 pid 는 기록된 포트(옛 기록은 `.pes-port` 도)의 `/whoami`(127.0.0.1)가 이 PES 홈(옛 서버는 그 프로젝트 폴더)으로 답할 때만 신호를 보낸다 — 답이 없거나 다른 root 면 신호 없이 묵은 기록만 지운다(재부팅·충돌 뒤 그 pid 를 받은 남의 프로세스 보호, Windows 도 같은 규칙; 출력 문구는 0.15 그대로). 0.15 는 기록의 pid 를 확인 없이 죽였다. `ensure_server` 는 띄운 자식이 `/whoami` 에 답하기 전에 실패하면 방금 쓴 기록을 지우고 끝낸다. 명령에 PES 홈 밖 경로를 직접 주면 폴더 이름만으로 DB 프로젝트로 보는 규칙(`doctor`·`serve`)의 정리는 SEL-74 로 넘긴다.
- **doctor**: 0.15 의 행을 같은 순서로 낸다. DB 프로젝트는 `project.json` 대신 코어의 읽기 모델(`read_project` 의 `updated_ms`)로 "대시보드가 최신 상태보다 오래됨" 을 판단한다(index.html 이 없거나 마지막 변경보다 1초 넘게 오래됨). 이전하지 않은 옛 `project.json` 프로젝트는 읽기만 하고 `--fix` 가 건드리지 않는다.
- **읽기 모델**(`legacy_view.ts`)은 0.15 의 project.json 모양에 더 가깝다. 이 PR 의 변경은 보고서 파일 `label`(0.15 의 이름)·단계 `reports_built`·`slug` 는 만들 때의 이름, 이 셋뿐이고 다른 키는 그대로다. `reports_built` 가 채워져 DB 프로젝트의 대시보드 "만든 시각" 칸에 처음으로 값이 보인다(보이는 변화). `report` 가 보내는 `plain` 은 버전 표시 줄만 뺀다(`pes.ts report` 만 보내며, `pes.py` DB 경로·API 는 그대로). `pes.py` DB 경로도 같은 읽기 모델(`read_project`)을 쓰므로 `label`·`reports_built`·`slug` 세 변경은 `pes.py` DB 경로의 status·대시보드에도 같이 보인다.

### 8.23 전환 — 스킬·설치를 TS 로, 0.15 폴더 이전 (PR26e, SEL-74)

스킬·명령·에이전트 문서와 설치 스크립트가 `node …/scripts/pes.ts`·`setup.ts` 를 부른다(제품에 Python 이 필요 없다). 이 PR 의 1~4단계가 만든 보장은 다음과 같다(5단계 Python 제거는 이어서).

- **서버 안전**: `serve.ts` 의 `/whoami` 는 `{root, single, pid}` 로 답한다(`pid` 는 서버 프로세스 자신). `stop` 은 기록(`.pes-hub-server`)의 pid 를 **그 포트의 `/whoami` 가 같은 pid 로 답할 때만** 끈다 — 다른 pid·pid 없음(옛 서버)·정수 아님이면 아무 신호도 보내지 않는다. 옛 프로젝트별 서버 기록(`.pes-server`)은 옛 서버가 pid 를 말하지 않으므로 root 로만 확인한다. `ensure_server` 는 20초 안에 답하지 않은 서버 자식을 끝내고 기록을 지운다.
- **DB 전용 5명령**: `context`·`claim`·`submit`·`wait`·`complete` 가 플래그 없이 `pes.ts` 에 있다(`cli_agent.ts`) — 0.15 `pes.py` 의 `PES_DB_CORE=1` 길과 같은 인자·한 줄 JSON·종료 코드(인자 오류 2). 자격은 `PES_TOKEN` 없음 = 이 컴퓨터 DB 의 사람 소유자, 있음 = 그 에이전트.
- **`migrate <폴더|이름>` · `migrate --all`**(`cli_migrate.ts` + 브리지 `migrate`): PES 홈 안의 0.15 `project.json` 폴더를 PR11 import → PR12 validate → 백업 번들(`~/.pes/backups/migrate-<이름>-<배치>`, PES 홈 밖) → activate 로 옮긴다. 폴더는 읽기만 해서 바이트·mtime 이 그대로다. 실패하면 아무것도 켜지 않고(`active` 가 아닌 채) 한 줄로 알린다. DB 에 이미 그 이름의 active 프로젝트가 있으면 `이미 이전됨`(exit 0, 아무것도 바뀌지 않음). 깨진 `project.json`·slug 가 폴더 이름과 다른 폴더는 DB 를 건드리기 전에 거절한다. import 는 사람 owner actor 가 필요하므로 DB 가 비어 있으면 owner 만 담은 프로젝트 `pes-local-owner` 하나를 먼저 만든다(`list` 에는 나오지 않는다).
- **D14 거절**: 안 옮긴 폴더에 쓰는 명령은 exit 1 + `…먼저 이전하세요 — pes migrate <이름>` 한 줄로 거절하고 폴더를 건드리지 않는다. `doctor` 는 `이전 필요` 줄(주의, 고칠 수 없음 — `--fix` 도 옮기지 않는다)을 낸다. 스킬은 이 거절을 받으면 사용자에게 먼저 묻고 동의 뒤에만 `migrate` 한다.
- **설치 이음매**: `PES_INSTALL_MIRROR=<폴더>`(네트워크·git clone 대신 이 폴더가 저장소), `PES_INSTALL_PATH_ONLY=1`(PATH 그대로), `PES_SKIP_TOOLS=1`(조사 도구 설치·업그레이드 건너뜀). `bootstrap.*` 의 마지막 줄은 `NODE <명령>`(Node.js 26 이상이 없으면 `NODE none`). 설치는 0.15 설치 위에 그대로 덮는다(CI 가 macOS·Windows 에서 설치 → 0.15 흔적 → 업그레이드를 돌린다).

- **Python 제거 + 읽기 모델이 0.15 가 `project.json` 에 두던 것을 되돌린 7가지(SEL-74 `ai/SEL-74-py`)**: `scripts/*.py`·`check_ddl.py`·pytest 시험·`requirements-dev.txt`·CI 의 Python 잡을 지웠다(역사 기록인 `docs/plan`·`docs/archive` 의 `.py` 는 남김). 새 코어 명령은 없다. (G7) `set changes` 값은 그 단계의 다음 `round-start` 부터 안 보이고(읽기 모델이 값의 커밋과 라운드 시작 커밋 순서를 비교), 그 라운드가 끝날 때 있던 값은 `R<n> (시각): 라벨 · 라벨 [/ 독립 검토 판정] — 상세 snapshots/<단계>-R<n>.json` 한 줄로 단계 이력에 들어간다. `round-start` 는 `render` 가 봉인할 게 없어 열린 채 남은 **빈 라운드**를 보이지 않는 표지로 봉인하고 새 라운드를 연다(내용 있는 열린 라운드는 전처럼 conflict). (G8·G16) `qa-brief` 는 `rounds/<단계>-R<n>/self-review.json` 에 `set review` 값 그대로를 쓰고 지시문에 「기획 답(사용자)」(`stage_reports` 제외)·「<단계> 시작 답(사용자)」·「이번 라운드 변경점(메인)」을 싣는다. (G9) `set` 은 짝 없는 서로게이트가 든 값(키 포함)을 거절한다. (G10) 승인된(무효화되지 않은) 단계의 두 번째 `approve` 는 새 승인 기록 없이 첫 번째와 같은 답을 내고, 0.15 처럼 단계 이력에 `승인 …` 줄이 한 줄 더 생기도록 보이지 않는 review artifact(`role: reapproval`)만 남긴다. (G17) `show`·`digest` 는 단계를 스스로 말하므로 `current` 없는 옛 `project.json` 도 0.15 처럼 읽는다(`status`·`pending` 등은 전처럼 한 줄 오류). (G18) `reopen`(조용한 재승인이 아닌 것)은 그 전에 `set review` 로 쓴 `review` 를 비운다.
