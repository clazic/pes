# 0단계 기반 다지기 — Codex 논의안

작성일: 2026-11-04. 이 문서는 결정을 위한 제안이며, 코드·테스트·설정을 구현했다는 보고가 아니다. 근거는 현재 PES 저장소에서 읽은 파일이다. OpenCode Go의 실제 접속·동작과 별도 research-loop 저장소의 내용은 검증하지 않았다.

0단계의 목표는 **현재 프로젝트를 잃지 않고, A·B 어느 쪽에서 작업하더라도 같은 PES로 발전시킬 수 있는 개발 기반**을 만드는 것이다. DB·API·화면을 여기서 완성하지 않는다. 브리프에서 그 설계 확정은 1단계, 구현·기존 프로젝트 이전은 2단계로 나뉘어 있다. hwpx 변환 확인과 기존 카드 디자인 개선은 이번 범위에서 제외한다.

## 2. 주제별 결정 사항·선택지·판단 기준·추천

### 1) 범위와 현행 기준선

- **무엇을 정할까:** 지금 반드시 보존할 동작, 알려진 결함, 바꿔도 되는 구현 세부사항을 구분한다. 재설계 전에 기준으로 삼을 커밋·플러그인 버전도 기록한다.
- **선택지:** ① 현행 화면·파일 전체를 그대로 동결한다. ② 사용자에게 중요한 결과·상태 전이를 보존한다. ③ 새 요구만 기준으로 삼고 현행을 버린다.
- **어떻게 정할까:** 실제 연구를 이어갈 수 있는지, 자료·결정·승인이 남는지, 새 구현을 불필요하게 제약하지 않는지로 판단한다. 기능마다 「보존 / 의도적 변경 / 결함 / 미확인」을 붙인다.
- **추천과 이유:** ②. 여섯 단계와 라운드, 시작 질문, 질문별 답·첨언, 승인, 재개, 앞 단계 다시 열기와 뒤 단계 stale, 출처 연결, 단계·최종 보고서를 보존 대상으로 잡는다. 포트 번호·HTML 배치·파일 수정 시각을 사용하는 알림 방식까지 새 구현의 필수 조건으로 삼지는 않는다.
- **현행과 요구의 차이:** 브리프는 질문별 의견 입력이 안 된다고 설명하지만, 현재 공용 질문 모듈에는 모든 질문의 덧붙임 입력과 `answers[질문ID + '__other']` 수집이 있다. 이미 있는 기능을 회귀 기준에 넣고, 질문 문구 자체 수정·양방향 대화는 새 요구로 구분해야 한다. 반대로 현재 `approve` 명령은 상태를 바로 바꾸며, 독립 검토·남은 일 정리는 스킬이 지시한다. 지침의 의도와 코드의 보장을 같은 것으로 적으면 안 된다.
- **근거:** [00-brief.md:19–29](../00-brief.md#L19-L29), [templates/_questions.html:33–47, 77–93](../../../templates/_questions.html#L33-L93), [scripts/pes.py:442–467](../../../scripts/pes.py#L442-L467), [skills/core/SKILL.md:120–135](../../../skills/core/SKILL.md#L120-L135). 현재 플러그인 버전은 [.claude-plugin/plugin.json:1–6](../../../.claude-plugin/plugin.json#L1-L6).

### 2) 테스트 범위와 우선순위

- **무엇을 정할까:** 처음 지킬 기능, 검사의 층위, 테스트 도구, 실패 시 개발을 멈출 기준을 정한다. 연구 결과에 대한 QC/QA와 소프트웨어 회귀 테스트도 구분한다.
- **선택지:** ① CLI 명령이 실행되는지만 확인한다. ② 핵심 함수·CLI 흐름·HTTP·질문 화면을 위험도에 따라 함께 확인한다. ③ 모든 화면·도구·실제 모델까지 자동화한다. 도구는 표준 `unittest` 또는 개발용 `pytest`가 가능하다.
- **어떻게 정할까:** 데이터 손실과 사용자 의사 누락의 영향, 변경 가능성, 재현성, 유지 비용을 비교한다. 줄 커버리지 수치보다 중요한 상태 변화와 실패 경로가 확인되는지를 본다.
- **추천과 이유:** ②와 개발용 `pytest`. 임시 디렉터리·입력 조합·외부 호출 대역을 다루기 쉬워 초기 안전망에 맞는다. 제품 실행에 테스트 의존성이 필요하지 않도록 분리한다. 도구 설치를 최소화해야 한다면 `unittest`도 가능하지만, 선택 후 실행 명령은 하나로 통일한다. 전체 HTML 문자열이나 LLM 답변 문장 일치는 합격 기준으로 삼지 않는다.
- **0단계 필수 검사 묶음:**

| 범위 | 최소 확인 내용 | 근거 |

| 생성·읽기·저장 | 초기 단계·필드, 이미 있는 프로젝트 생성 거부, 누락 필드 보완, 참고자료 분리·재로딩 | `scripts/pes.py:96–114, 147–158, 186–216` |

- **보완 근거:** `cmd_reopen`에는 `complete` 갱신이 보이지 않고(`scripts/pes.py:496–510`), 병합은 매번 depth를 올리며(`360–362`), 스냅샷은 같은 이름에 쓴다(`405–408`). HTTP 서버는 다중 스레드이며 파일명 존재 확인 후 저장한다(`scripts/serve.py:140–154`). 연구 QC/QA의 대상은 주장·근거·목적 적합성이다([agents/reviewer.md:14–33](../../../agents/reviewer.md#L14-L33)).

### 3) 테스트 자료·격리·재현성

- **무엇을 정할까:** 표본 프로젝트의 범위, 실제 자료 사용 여부, 홈·설정·서버·시간·외부 도구의 격리 방법을 정한다.
- **선택지:** ① 실사용 PES 홈을 검사한다. ② 합성 표본과 임시 홈으로 검사한다. ③ 실제 프로젝트를 통째로 저장소에 넣는다.
- **어떻게 정할까:** 실자료와 키가 노출되지 않는지, 다른 개발자의 컴퓨터에서도 같은 결과인지, 실패해도 사용 중인 프로젝트·설정·서버에 영향이 없는지로 판단한다.
- **추천과 이유:** ②. 작은 기본 프로젝트, 여러 라운드·승인·reopen 표본, research-loop 가져오기 표본, 원고·각주 표본, 손상된 입력 표본을 만든다. 이름·도시·통계·경로·키는 합성한다. `PES_HOME`뿐 아니라 `Path.home()`에서 읽는 `~/.pes/config.json`과 도구 설정 접근도 격리한다. 홈을 덮어쓰는 검사나 실제 설치·종료 명령은 자동 검사에 섞지 않는다.
- **구체적 기준:** 한글·공백이 있는 경로, Windows 형식 경로가 기록된 로그, 같은 시각의 제출, 빠진 필드·깨진 JSON을 포함한다. 서버 검사는 임시 루트와 충돌하지 않는 포트를 사용하고 자신이 띄운 프로세스만 정리한다. 시간·소유자 ID를 제어하고, KOSIS·법령·브라우저·모델 호출은 대역을 기본으로 한다. 실제 외부 연결은 별도 수동 검사로 남긴다.
- **근거:** 홈 우선순위와 설정 접근은 [scripts/pes.py:73–93](../../../scripts/pes.py#L73-L93), 시각 의존은 `scripts/pes.py:181–182`와 `scripts/serve.py:140–145`, 외부 환경의 Claude 설정 의존은 [scripts/setup.py:32–64](../../../scripts/setup.py#L32-L64). OS 경로 혼재는 [README.md:495–512](../../../README.md#L495-L512).

### 4) AGENTS.md와 지침의 역할 분담

- **무엇을 정할까:** 개발 에이전트가 먼저 읽을 파일, 공통 규칙의 원본, 도구별 지침과 PES 연구 스킬의 경계를 정한다. 현재 확인한 저장소에는 `AGENTS.md`가 없다.
- **선택지:** ① 기존 연구용 `skills/core`에 개발 규칙까지 넣는다. ② 루트 `AGENTS.md`를 개발 규칙의 원본으로 두고 상세 문서·기존 스킬로 연결한다. ③ Claude·Codex·OpenCode별로 같은 규칙을 복사한다.
- **어떻게 정할까:** 처음 들어온 에이전트가 작업 위치·검사 명령·금지할 실자료 조작을 찾을 수 있는지, 같은 규칙이 여러 곳에서 어긋나지 않는지로 판단한다.
- **추천과 이유:** ②. 루트 문서에는 저장소 지도, 계획 문서 우선순위, 개발·연구 데이터 위치 구분, 검사 명령, 변경·검토·결정 기록 규칙, 자격정보 처리, A·B 공통 원칙을 짧게 적는다. 도구별 파일이 필요하면 원본으로 연결하는 최소 안내만 둔다. 각 도구가 실제로 어떤 지침을 읽었는지는 시작 체크로 확인한다. 파일 이름만 같다고 자동 적용된다고 가정하지 않는다.
- **특히 정할 점:** `AGENTS.md`는 PES를 **개발**하는 규칙이고, `skills/core`는 PES를 이용해 **연구 프로젝트를 수행**하는 규칙이다. 개발 문서 논의에 연구 라운드·웹 승인·매 라운드 QA 절차를 기계적으로 적용하지 않는다. 현재의 직접 `project.json` 편집은 현행 운영 설명으로 남기되, 새 구조에서는 공통 인터페이스를 통해 변경한다는 전환 원칙을 명시한다.
- **근거:** 연구용 지침의 목적·파일 편집 방식은 [skills/core/SKILL.md:3–18, 62–83](../../../skills/core/SKILL.md#L3-L83), Claude 전용 경로는 `23–25행`, 연구 라운드 절차는 `114–135행`. 개발 문서·소스를 한 저장소에 두는 요구는 [00-brief.md:32](../00-brief.md#L32).

### 5) research-loop 저장소와 자료 재사용

- **무엇을 정할까:** 브리프가 말하는 research-loop 저장소의 정확한 위치·소유·공개 범위·보존할 버전, 앞으로 유지·보관·이관할 범위를 정한다. **저장소를 어떻게 다룰지와 조사 결과를 PES에 가져오는 것은 별개 결정**이다.
- **선택지:** ① 별도 저장소를 계속 개발한다. ② 별도로 보존하고 PES는 필요한 아이디어·가져오기 호환성만 유지한다. ③ PES에 소스 전체를 합친다(직접 복사·이력 병합·서브모듈 포함).
- **어떻게 정할까:** 현재도 독립 사용자가 있는지, PES에 없는 기능이 무엇인지, 보존할 이력·권한·라이선스가 무엇인지, 결합이 설치·개발을 복잡하게 만드는지 확인한다. 이름만으로 폐기·통합을 결정하지 않는다.
- **추천과 이유:** 현황 확인을 먼저 하고, 기본안은 ②. 코드와 문서는 읽기 가능한 기준 커밋·태그를 기록하고 보존한다. PES에는 재사용할 기능 목록과 출처를 적고, 가져오기용 합성 `state.json`·이미지 경로 표본만 둔다. 별도 저장소를 보관 전용으로 전환하는 작업은 그곳의 사용 여부와 책임자가 정해진 뒤 한다. 이번 논의에서 저장소를 삭제·이동·보관 처리하지 않는다.
- **호환성 확인:** 현재 가져오기는 `state.json`의 항목 중 removed를 제외하고, `shots/`를 복사하며 경로에 `library/`를 붙인다. 이 결과가 기획의 reuse→조사 항목·출처·연결로 이어지는지 검사한다. 누락 이미지·중복 ID·예전 형식은 예외 목록에 넣는다. 이는 **research-loop→현행 PES 가져오기**이고, **현행 PES→새 DB 이전**과 구분해 추적한다.

### 7) 개발 환경·의존성·OS·자동 검사

- **무엇을 정할까:** 지원 Python·Node 범위, 개발용 의존성 고정 방식, 로컬 검사 명령, CI의 OS 조합, 수동 확인 범위를 정한다.

- **추천과 이유:** ②. 현재 안내인 Python 3.9 이상을 무심코 바꾸지 말고, 실제 사용할 최소 버전과 기준 버전을 합의해 명시한다. 선택한 테스트 도구의 호환성도 함께 확인한다. 테스트 의존성은 버전을 고정하며, 자동 검사 중 설치 스크립트의 전역 업그레이드를 실행하지 않는다. 이후 웹 의존성은 실제 도입 시 패키지·잠금 파일을 정한다.

### 9) A·B 공통 경계와 입력·출력 약속의 준비

- **무엇을 정할까:** PES가 책임지는 일과 실행기가 책임지는 일, 같은 작업으로 식별할 정보, 두 방식의 공통 성공·실패 의미를 정한다.
- **선택지:** ① A·B별 데이터와 API를 따로 만든다. ② 공통 업무 모델과 입력·출력을 두고 실행기만 바꾼다. ③ OpenCode 세션·메시지 형식을 PES의 기본 모델로 삼는다.
- **어떻게 정할까:** 같은 프로젝트를 A→B 또는 B→A로 이어갈 수 있는지, 공급자 변경이 자료 형식까지 바꾸지 않는지, 특정 TUI의 명령·메모리·감시에 의존하지 않는지로 판단한다.
- **추천과 이유:** ②. PES는 자료·질문·답·승인·결정·작업 상태·권한 검사를 맡고, 실행기는 조사·집필 등의 작업과 결과 제출을 맡는다. **OpenCode 서버 API(PES→실행기)**와 **PES API(실행기↔PES)**를 구분한다. A도 결과를 PES 공통 입력 형식으로 제출하고, B도 같은 규칙을 따른다.
- **0단계 결과:** 프로젝트·판·단계·라운드·항목·질문·답·작업·실행·산출물·사용자 승인의 용어표와 관계 초안, 「맥락 읽기 / 일 받기 / 결과 제출 / 질문 올리기 / 답 읽기 / 처리 확인 / 중단·인계」 동작 목록, 정상·오류 JSON 예제를 준비한다. 프로젝트 식별자·판 범위·작업 ID·기준 리비전·제출 ID·형식 버전·수행자·근거·파일 참조가 왜 필요한지 적는다. 최종 필드명·URI·DB 테이블은 확정하지 않는다.
- **이유의 보강:** 지금도 외부 결과 JSON을 병합하는 경계가 있다. 다만 필드 검사·동시 수정·권한·중복 제출을 충분히 보장하는 새 API 계약으로 간주할 수는 없다. 그 병합 규칙을 표본으로 삼아 공통 동작을 먼저 설명한다.
- **근거:** A·B 동일 모델·API 요구는 [00-brief.md:35–39](../00-brief.md#L35-L39), API 의미는 `17행`, 판 요구는 `16행`, 현행 결과 병합은 [scripts/pes.py:315–365](../../../scripts/pes.py#L315-L365). 직접 파일 편집 의존은 `skills/core/SKILL.md:62–72`, TUI 재개는 [commands/run.md:10–15](../../../commands/run.md#L10-L15).

### 10) 실행 소유권·중복·중단·재개

- **무엇을 정할까:** 누가 같은 프로젝트를 고칠 수 있는지, 오래된 결과·재전송·중단 중 도착한 답을 어떻게 처리할지, A·B 인계 시 무엇을 이어받을지 정한다.
- **선택지:** ① 에이전트에게 조심하라고 지시한다. ② 초기에는 한 프로젝트의 활성 실행 담당을 하나로 제한하고, 버전·제출 ID·처리 확인을 설계 조건으로 둔다. ③ 처음부터 여러 실행기가 동시에 같은 항목을 수정한다.
- **어떻게 정할까:** 자료 유실·중복 반영·사용자 승인 오인 가능성, 재시작 이후 복구 가능성, 6단계의 다중 에이전트 확장과 현재 개발량을 비교한다.
- **추천과 이유:** ②. A·B를 둘 다 지원한다는 말이 같은 항목을 동시에 고치게 해야 한다는 뜻은 아니다. 초기에는 한 프로젝트의 실행 담당 하나와 명시적 인계를 기본으로 하고, 읽기·사람의 답 제출은 계속 가능하게 한다. 승인 권한은 사람에게 두고 에이전트 작업 완료와 구분한다.
- **미리 적을 요구:** 같은 제출 ID 재전송은 중복 반영하지 않기, 기준 리비전이 지난 결과는 자동 덮어쓰기하지 않기, 답 저장과 처리 완료를 구분하기, 중단된 실행의 늦은 결과는 격리하기, 인계 시 미처리 답·진행 작업·파일 참조·마지막 반영 지점을 넘기기. A의 자동 재시도는 무한 반복하지 않고 한도·대기·사용자 알림을 둔다. 정확한 트랜잭션·작업 대여 방식은 1단계에서 정한다.
- **근거와 현재 한계:** 현행 잠금은 TTL과 소유자 파일 확인 방식이고([scripts/pes.py:117–158](../../../scripts/pes.py#L117-L158)), 직접 편집은 이 경로를 우회할 수 있다(`skills/core/SKILL.md:64–72`). 답 처리 표시는 파일명 목록이며(`scripts/pes.py:516–518, 556–563`), 웹 수신 파일 저장과 로그 추가도 별도 동작이다(`scripts/serve.py:149–151`). 따라서 현재 구조가 동시 실행·정확히 한 번 반영을 보장한다고 주장하면 안 된다. 다중 운영 확장은 `00-brief.md:51`의 후속 범위다.

## 3. A·B를 함께 개발하기 위해 0단계에 미리 준비할 것

### 공통으로 준비할 것

1. **같은 표본과 같은 기대 결과:** 사람이 질문에 답함→작업 실행→결과·질문 게시→추가 의견 반영→사람 승인→재개를 하나의 합성 시나리오로 만든다. 실행기가 A인지 B인지에 따라 프로젝트 결과의 의미가 바뀌면 안 된다.
2. **공통 입력·출력 예제:** 맥락, 작업 요청, 항목 결과, 질문, 답, 처리 확인, 오류를 파일 예제로 준비한다. 실행기별 세션 식별자는 부가 정보로 두고 프로젝트의 기본 ID로 쓰지 않는다.
3. **보존할 업무 규칙:** 사람 승인, 근거 연결, 질문별 덧붙임, 검토 결과와 미해결 사항, 이전 단계 변경 영향은 특정 스킬 프롬프트에만 맡기지 않는다. 어떤 규칙을 PES가 검사해야 할지 목록으로 정리한다.
4. **이력·판·파일의 경계:** 현재 프로젝트에는 판 모델이 없지만 향후 결과를 특정 판·리비전에 연결할 수 있어야 한다. 큰 파일을 JSON 본문에 넣기보다 파일 참조로 다룰 준비를 하고, 로컬 절대경로를 웹 자산 식별자로 굳히지 않는다.
5. **모의 실행기와 오류 표본의 설계:** 실제 모델 없이 공통 흐름을 검증할 수 있게, 두 실행기가 같은 요청을 받아 같은 형식으로 제출하는 시험 방법을 정한다. 새 API 구현은 2단계에서 이 표본을 실제 계약 검사로 연결한다.

완료 판정은 테스트 개수나 문서 존재만으로 하지 않는다. **다른 개발 에이전트가 지침만 읽고 검사를 재현하며, 현재 프로젝트의 복사본을 복구하고, A·B를 같은 PES 모델로 설계할 근거가 갖춰졌는지**를 본다. 이후 1단계에서는 이 증거와 미결정 목록을 입력으로 DB·API·화면 설계를 확정한다.
