작성: 2026-11-04. 상태: **화면 설계 토론안**. 이 문서의 추천은 사용자 확정 사항과 구분한다.
목표는 질문에 답하고, 결과 글을 읽고, 의견이 반영됐는지 확인하는 일을 **프로젝트 작업 공간 하나에서 이어 가는 것**이다. AI 질문 폼을 가장 중요한 검토 입구로 유지한다.

## 0. 설계의 전제

- 확정된 stage-0 7절과 합의된 stage-1-db 2절의 **17개 결정 전부를 전제**로 한다. 재결정 안건으로 올리지 않는다.

- **전송 허용 / 실행 / 사람의 답 제출 / 단계 승인 / 반영 완료는 각각 다른 사실**이다. 버튼 이름과 상태 문구도 나눈다.

## 2. 추천 화면과 동작

### 2.1 하나의 주소, 세 영역

넓은 화면에서는 다음 구조를 추천한다. 질문이 길어지면 질문 영역을 넓히는 ‘질문에 집중’을 제공한다. 결과 원문은 언제든 같은 자리에서 확인한다.

```text
프로젝트 / 1판     조사 · R2     방식 A · 답변 기다림
Go 전송 허용 [켜짐] [전송 내역]       [결정 기록] [명령 찾기] [인쇄]
─────────────────────────────────────────────────────────────────
단계·라운드       결과 글 + 첨언                 질문 | 가정 | 대화
기획 · 승인       이번 라운드 반영 내역           답할 질문 2 / 전체 5
조사 · 현재       결과 제목 · 버전 · 작성자       Q-12 중요 · 필수
  R1             본문·표·근거                    질문 문구 [고치기]
  R2             선택 → 첨언 / AI에게 묻기 / 할 일로
분석·종합        여백의 첨언 번호                선택지 / 질문별 의견
집필             [글 집중 / 질문에 집중]         [기본값 사용]
검증                                            [답 검토 후 보내기]
산출·공유                                       [AI에게 질문 추가]
```

- 헤더는 프로젝트·판·현재 보는 단계/라운드·실행 담당·Go 정책을 알려 준다. 과거 라운드를 볼 때 ‘현재 진행: 조사 R2’를 따로 표시한다.
- 왼쪽은 6단계와 그 안의 라운드 목록. 가운데는 결과 글·근거·첨언, 오른쪽은 기본 ‘질문’ 탭과 가정·대화 탭이다. 질문이 있는데 대화가 기본으로 열리지 않는다.
- 미응답·재확인 질문 수는 탭 밖에도 남긴다. 단순 KPI보다 ‘지금 확인할 질문’이 먼저 보인다. 새 AI 글은 읽는 위치를 갑자기 옮기지 않는다.
- 단계 시작 질문은 `round_id=NULL`일 수 있다. ‘단계 시작’으로 표시하고 가짜 R0을 만들지 않는다. 결과가 없으면 결과 영역에 목적·선행 결정·참고 자료를 둔다.
- 유효 화면 폭 약 1280px 이상은 3영역(탐색 약 160px, 질문 약 400px, 나머지 결과), 960~1279px는 탐색 접기+2영역을 출발점으로 검증한다.
- 그보다 좁거나 200% 확대하면 결과/질문을 한 열로 전환한다. 같은 작업 공간 안의 탭으로 오가며 각 초안·스크롤을 보존한다. 미리보기는 전체 폭으로 열린다.
- 결과·질문은 영역 안에서 스크롤할 수 있지만 스크롤 영역을 중첩하지 않는다. 좁은 화면은 문서 스크롤 하나다. 고정 헤더·버튼이 입력과 초점을 가리지 않게 한다.

### 2.2 탐색, 단계 전환, 승인

- 단계 클릭은 열람이다. ‘승인하고 다음 단계로’, ‘다음 라운드 시작’, ‘앞 단계 다시 열기’는 각각 별도 동작이다. 마지막 질문의 ‘다음’이 승인을 실행하지 않는다.
- 단계 상태는 대기/질문 중/진행 중/승인, 라운드는 열림/봉인, 실행은 별도 상태로 표시한다. 하나의 녹색 완료 표시로 합치지 않는다.
- stale은 ‘승인됨 · 재확인 필요’처럼 병기하고 원인 사건·다시 열린 단계를 링크한다. 이미 받은 승인의 이력을 지우거나 자동 재승인하지 않는다.
- 봉인 라운드·과거 판은 고정 버전으로 연다. 그 화면에서의 ‘의견 남기기’는 원본 기록을 바꾸지 않고 활성 판/열린 라운드에 새 후속을 만들며 출발 버전을 가리키게 제안한다. API에서 허용 범위를 확정한다.
- 승인 화면은 대상 판·단계·고정본, 미응답 필수 질문·재확인 항목·미처리 제안을 보여 준다. 차단 사유와 참고 경고를 구분한다. 모든 첨언을 닫아야 승인할 수 있게 만들지는 않는다.
- 새 승인은 사람이 직접 확정한다. 과거 이전 자료의 `legacy_unverified`는 ‘이전 승인 · 승인자 확인 불가’로 표시하며 새 인증 승인처럼 꾸미지 않는다.

### 2.3 AI 질문 폼: 답하면서 질문 자체도 고친다

질문 머리에는 `Q-12`, 방향(AI→사람/사람→AI), 중요도, 필수 여부, 응답 상태를 같은 순서로 놓는다. 중요도와 필수 여부는 독립이다.

| 동작 | 추천 화면 동작 | 저장·검토 의미 |
|---|---|---|
| 고치기 | 문구·선택지·도움말·중요도·필수·기본값 편집, 저장 전 변경 대조 | 새 질문 버전+그 버전을 참조하는 새 폼. 원문 보기 유지 |
| 더하기 | ‘내가 답할 질문’ / ‘AI에게 물을 질문’을 구분, 현재 단계·라운드 기본 | 작성자는 실제 사람으로 남김. AI가 쓴 것으로 꾸미지 않음 |
| 빼기 | ‘이번 질문에서 제외’와 사유, 되돌려 포함 가능 | 물리 삭제 안 함. 새 폼에서 제외·철회 이력 보존 |
| 미루기 | 대상 라운드 또는 ‘다음 검토’ 표시 | deferred. required를 몰래 해제하지 않음 |
| 합치기 | 원 질문 두 개와 새 질문을 대조 | 원본은 merged·연결 유지. 답을 새 질문에 자동 이식하지 않음 |
| 순서 바꾸기 | 위로/아래로 버튼, 드래그는 보조 | 새 폼의 position 변경. 질문 버전이 같으면 답 재확인 불필요 |
| 계속 더하기 | 저장 뒤 창 유지 선택 | 질문을 연달아 만들되 매번 접수 결과 표시 |

- 질문 버전이 달라지면 옛 답은 ‘이전 질문에 대한 답’으로 접어 보여 주고 현재는 ‘재확인 필요’다. 문구뿐 아니라 기본값·중요도 등을 새 버전으로 저장한 경우에도 임의 예외를 두지 않는다.
- ‘이전 답으로 다시 제출’은 변경 전후 질문과 답을 보여 준 뒤 사람이 누른다. 새 버전에 대한 새 답 기록을 만든다. 삭제된 선택지는 새 값으로 임의 치환하지 않는다.
- 편집 중 닫기는 초안 유지, 저장은 버전 확정이다. 매 키 입력을 업무 버전으로 만들지 않는다. 질문 여러 개의 편집은 변경 요약을 한 번 검토해 새 폼으로 발행할 수 있다.
- 질문별 ‘의견’에는 짧은 덧붙임과 이어지는 대화가 있다. 답 없이 의견만 먼저 보낼 수 있다. 대화가 존재한다는 이유만으로 필수 응답 완료로 세지 않는다.
- `allow_comment_as_answer=1`이면 제출 때 ‘선택 없이 이 의견으로 응답’을 제공한다. 이때 의견만 응답으로 인정하며 추천 선택지 동의로 바꾸지 않는다. 0이면 의견 전송은 가능하지만 필수 응답은 남는다.
- 기본값은 ‘제안 기본값’으로 표시하고 처음부터 제출된 답처럼 선택하지 않는다. ‘기본값 사용’을 눌러 초안에 넣고 최종 제출해야 `used_default`가 된다. 추천 이유와 기본값도 구분한다.
- 조건부 질문은 노출 이유를 볼 수 있다. 숨겨진 질문을 미응답 분모에 넣지 않고 기존 답은 보존한다. 미제출 초안의 조건부 질문은 상위 입력이 바뀌면 제출 대상에서 제외됐음을 안내한다.
- 진행 수는 ‘현재 표시 대상 중 제출 3/5 · 재확인 1’처럼 정의한다. 의견만 응답은 별도 표기한다. 사람→AI 질문은 사람의 미응답 수에 섞지 않는다.

### 2.4 초안, 제출, 동시 변경

추천은 **질문별 초안 유지+여러 답을 검토해 한 번에 제출**이다. 질문별 의견은 독립 전송할 수 있고, 개별 답도 별도 제출 동작을 제공한다. 저장된 초안과 제출된 답을 같은 표시로 부르지 않는다.

- 초안은 작업 공간 메모리와 현재 탭의 sessionStorage에 보관하는 안을 권한다. 키는 프로젝트·사용자·판·폼·질문 버전을 포함한다. 새로고침 복원 시 대상 버전을 확인하고 제출 성공 뒤 해당 초안만 지운다.
- 이는 같은 탭의 새로고침 복구 범위다. 탭 종료·다른 기기까지의 초안 보장은 약속하지 않는다. 더 넓은 복구가 필요하면 별도 서버 초안 계약이 필요하며 현 DDL에 있다고 가정하지 않는다.
- 임시 저장소를 쓸 수 없으면 ‘이 탭에서만 임시 보관 중’으로 표시한다. 토큰·첨부 원문을 넣지 않고 사용자가 초안을 지울 수 있게 한다. 첨부는 검증된 임시 업로드 참조만 다룬다.
- 입력 중 부분 갱신은 포커스·선택 범위·스크롤·IME 조합을 보존한다. 편집 중인 객체는 즉시 교체하지 않고 ‘새 버전 도착’으로 알린다. 한글 조합 중 Enter로 제출하지 않는다.
- 제출 실패는 초안을 그대로 두고 필드 옆 오류와 첫 오류 링크를 보여 준다. 타임아웃은 ‘접수 확인 중’이며 같은 요청 키로 영수증을 확인한다. 새 키로 무조건 재전송하지 않는다.
- rev 충돌은 ‘내 초안 / 서버의 새 버전 / 당시 버전’ 대조로 해결한다. 사용자가 다시 제출할 때 새 기반과 새 요청을 만든다. 질문이 바뀌면 새 질문을 먼저 확인한다.
- 실행 담당이 있어도 사람은 답·첨언을 쓸 수 있다. 실행 담당 lease는 사람의 입력 잠금 표시로 쓰지 않는다.

### 2.5 가정: ‘맞다/틀리다’ 뒤 무엇이 바뀌는지도 보인다

가정 탭은 `번호 | 가정 | 상태 | 확인자·시각 | 관련 질문·글 | 동작` 표다. 기본 필터는 미확인·재검토이며 전체 목록도 바로 연다.

- ‘맞다’→confirmed, ‘틀리다’→rejected, ‘고침’→revised와 대체 가정 버전이다. 틀리다/고침은 이유나 수정 문장을 받는다. ‘아직 판단 못 함’은 proposed를 유지한다.
- 확인한 가정도 `needs_review`면 ‘맞다고 확인한 이력 있음 · 재검토 필요’를 함께 표시한다. 새 판 복사만으로 현행성을 확인하지 않는다.
- 가정을 틀리다고 표시해도 결과 글은 즉시 고쳐졌다고 하지 않는다. 영향받는 글·질문과 ‘수정 제안 만들기’를 보여 주고 후속 작업·반영 내역으로 잇는다.
- 첫 구현은 의미 판단이 필요한 일괄 ‘모두 맞다’를 제공하지 않는 편을 권한다. 개별 판단을 남겨야 무엇을 확인했는지 분명하다.

### 2.6 반영 내역과 결정 기록

새 라운드 결과 첫머리에 ‘지난 의견 반영 내역’을 둔다. `내 답·첨언·가정 | 처리(반영/일부/미반영/다음으로) | 이유 | 바뀐 글·후속` 네 열을 추천한다.

- applied/partial은 결과 버전 또는 실제 적용된 후속과 연결한다. ‘검토했습니다’ 같은 AI 문장만으로 반영 완료를 표시하지 않는다. 증거 없는 입력은 ‘처리 확인 전’이라는 조회 상태로 남긴다.
- 입력의 ‘PES 접수’, ‘에이전트가 읽음’, ‘반영’은 각각 제출 영수증, run_input_receipts, reflection_entries의 근거를 쓴다. 읽음은 반영이 아니다.
- ‘일부/미반영’은 기본 펼침, ‘반영’은 요약과 변경 위치로 이동할 수 있게 한다. 해당 라운드의 내역이 없으면 0건으로 단정하지 않고 ‘반영 내역 미제출’을 구분한다.
- 결정 기록은 헤더에서 언제든 여는 목록이다. `D-번호 | 결정 | 프로젝트 공통/판 | 상태 | 결정자 | 이유·근거`를 정렬하고 채택된 결정을 기본 표시한다.
- AI 제안은 proposed, 사람의 채택 동작은 adopted다. 바꾸거나 철회하면 새 버전을 만들고 앞 결정을 링크한다. 단순 의견을 사용자 확정 결정으로 승격하지 않는다.
- 각 라운드는 당시 적용된 결정 버전을 보여 준다. 현재 결정이 바뀌었으면 ‘현재 결정 보기’로 따로 비교한다. 과거 화면에 현재 값만 끼워 넣지 않는다.
- 새 판의 공통 결정 참조·판 범위 복사와 유지/수정/제외 검토는 4단계 판 화면으로 넘기며, 현재 화면은 범위·계보를 표시할 자리만 정한다.

### 2.7 결과 글·첨언·대화의 연결

결과 제목 옆에는 버전·라운드·실제 작성자·근거 확인 상태를 표시한다. 본문은 읽기 중심이고 ‘수정 제안’은 변경 전후 미리보기를 거친다. 토큰 스트림은 ‘작성 중 미리보기’이며 저장 결과 버전과 구분한다.

| 위치 판정 | 사용자 문구 | 가능한 동작 |
|---|---|---|
| exact | 원위치 확인 | 인용문으로 이동 |
| moved | 위치 이동 확인 | 새 위치·원래 글 비교 |
| ambiguous | 위치 후보 여러 곳 · 확인 필요 | 후보 문맥 비교 후 사람이 선택 |
| lost | 현재 글에서 위치 못 찾음 | 원래 버전 보기 / 다시 위치 지정 / 미연결로 유지 |

- ambiguous/lost 첨언은 목록과 건수에 계속 남긴다. 틀린 위치에 붙이거나 일반 대화 속으로 숨기지 않는다. 후보를 고르기 전 본문 하이라이트로 확정하지 않는다.
- 같은 인용문을 새 버전에서 재지정하면 확인자·시점이 있는 새 판정을 덧붙인다. 인용 대상 자체를 바꾸면 새 anchor와 supersedes 관계가 필요하다. 원본 인용문·문맥은 불변이다.
- 현 DDL의 thread는 원래 anchor를 가리킨다. 새 anchor 계보에서 ‘현재 사람이 확인한 위치’를 어떻게 조회할지 API에서 명시해야 한다. thread_versions에 anchor 열이 있다고 가정하지 않는다.
- 긴 인용은 펼쳐 볼 수 있고 출발 버전 링크를 항상 남긴다. 표의 글을 선택해도 행·열 문맥을 함께 보여 준다. 이미지에는 이미지/문서 단위 의견 입구를 두고 텍스트 앵커로 위장하지 않는다.
- 스레드 머리는 대상 글·인용, 본문은 메시지, 끝에는 결론과 후속이다. 특정 답글을 ‘이 답이 결론’으로 지정하고 요약을 고칠 수 있다.
- ‘대화 해결’은 스레드를 resolved로 한다. 후속은 글 수정/다음 라운드 할 일/앞 단계 다시 열기/후속 없음으로 구분하고 제안→수락→진행→적용 상태를 별도로 표시한다.
- reopen 제안을 수락했어도 실제 사람용 reopen 명령을 거쳐야 적용이다. 글 수정도 결과 버전·적용 기록이 있어야 완료다. 오래된 기반이면 변경 대조를 다시 한다.
- 질문별 의견은 question_comment, 프로젝트 대화는 general이다. 현재 DDL의 텍스트 anchor 대상은 artifact이므로 모든 객체에 글 조각 첨언이 된다고 약속하지 않는다.

### 2.8 선택 글: ‘첨언 / AI에게 묻기 / 할 일로’

세 동작은 선택 막대와 본문 동작 메뉴에 같이 둔다. 키보드로 선택한 글에도 적용하고, 선택이 없으면 현재 문단/글 전체가 대상임을 표시한다. 선택을 바꾸어도 작성 중인 인용은 고정된다.

| 동작 | 작성 화면 | 완료의 의미 |
|---|---|---|
| 첨언 | 인용+의견+답글 스레드 | PES에 의견 접수. AI 실행·글 수정은 별도 |
| AI에게 묻기 | 인용+질문+대상 단계·라운드 | 사람→AI 질문 등록. A 실행 또는 B 전달은 별도 |
| 할 일로 | 인용+제목+설명, ‘PES 후속 / Linear 이슈’ 목적지 | PES 후속 등록 또는 Linear 외부 이슈 생성 영수증 |

- 사용자 요청에 따라 **Linear 이슈 만들기까지의 흐름을 설계**한다. 연구의 후속 일과 PES 개발 이슈를 구분하고 기본 목적지는 PES 후속을 권한다. Linear를 고르면 외부 전송임을 명시한다.
- Linear 초안은 팀·프로젝트·제목·설명·원문 포함 범위를 보여 준다. 추천 기본은 제목+사용자가 쓴 요약이며, 연구 인용·첨부·전체 대화는 자동 포함하지 않는다. ‘Linear에 만들기’가 실제 전송 버튼이다.
- 로컬 PES 링크는 다른 사람이 열 수 없을 수 있음을 초안에서 표시한다. 로컬 경로·토큰은 본문에 넣지 않는다. 연결이 없으면 초안을 보존하고 ‘Linear용으로 복사’를 제공한다.
- 외부 생성 성공이면 이슈 번호·URL과 PES 원본 링크를 함께 기록한다. 생성 응답이 유실되면 ‘생성 확인 필요’로 두고 같은 이슈가 있는지 확인한다. 새 이슈를 무조건 재생성하지 않는다.
- Linear 이슈 생성·외부 완료 상태는 PES 글 반영·단계 승인과 별개다. 왕복 동기화는 넣지 않는다. 실제 연동의 시점·전송 자료 범위는 5절의 사용자 결정 안건이다.
- 현 DB의 outbound_dispatches는 Go 전송 증거다. 이를 Linear 내보내기에 재사용하지 않는다. 외부 이슈 참조·중복 방지·미확인 결과의 영속 계약은 DB/API 추가 검토 사항이다.

### 2.9 명령 팔레트, AI 전환, 맥락 동작

- Windows 기본은 **Ctrl+K**, macOS는 Cmd+K다. 눈에 보이는 ‘명령 찾기’ 버튼과 단축키 도움말도 둔다. 앱이 활성화된 범위에서만 처리하고 브라우저·보조기기와 충돌하면 버튼으로 같은 일을 한다.
- 팔레트 위에 `명령 찾기 / AI에게 묻기`를 탭 순서에 드는 버튼으로 둔다. 명령 입력에 초점이 있고 한글 조합 중이 아닐 때 Tab 전환을 보조로 제공하되 반복 Tab을 가두지 않는다. 전환 규칙을 안내하고 일반 초점 이동을 보장한다.
- 명령 모드 Enter는 선택한 명령 실행, AI 모드 Enter는 질문 초안 검토다. 검색 결과가 없다고 자동으로 AI에 보내지 않는다. AI 전송은 별도 버튼이다.
- `프로젝트·판·단계·라운드·선택 객체/버전` 맥락을 칩으로 보여 주고 사용자가 제외할 수 있게 한다. ‘프로젝트 전체’가 기본 전송 범위가 되지 않는다.
- 하나의 동작 정의를 버튼·팔레트·문맥 메뉴·단축키가 공유한다. 정의에는 ID, 한국어 이름·검색어, 대상, 사용 조건, 비활성 이유, 초점 복귀점, 외부 전송 여부를 둔다.
- 예: 질문에서는 고치기·미루기·원문 보기, 첨언에서는 결론 지정·위치 재지정·후속 만들기, 결과에서는 프롬프트 복사·인쇄가 먼저 나온다. 적용 불가 이유를 설명한다.
- 화면의 사용 조건은 편의일 뿐 권한 검사가 아니다. 승인·reopen·판 시작·전송 재허용을 에이전트가 부를 수 있게 하는 공통 execute 통로를 만들지 않는다.
- 두 글자 이동·한 글자 처리 키는 3단계 후반 선택 기능으로 권한다. 입력 칸·contenteditable·IME 조합 중에는 무효이며 기본 기능은 Tab과 명시적 버튼으로 모두 가능해야 한다.

### 2.10 ‘프롬프트로 복사’, 미리보기, 순서대로 넘기기

- 프롬프트 복사 전 구성 미리보기를 연다. 기본 내용은 요청 목적, 선택 인용/질문, 판·단계·라운드·객체/버전 번호, 필요한 결정, PES 복귀 링크, 기대 응답이다. 첨부·전체 프로젝트는 명시적으로 추가한다.
- 미제출 답을 포함하면 ‘미제출 초안’이라고 표시한다. 접속 토큰·실제 로컬 파일 경로·비밀 설정은 제외한다. 인용된 외부 글은 참고 자료이며 실행 지시와 분리한다.
- ‘복사됨’은 제출·외부 에이전트 수신·반영이 아니다. Clipboard API 실패 시 읽기 전용 텍스트와 직접 선택·Ctrl+C를 제공한다. 복사만으로 run을 시작하거나 lease를 획득하지 않는다.
- 미리보기는 출처·질문·첨언·결정을 목록 옆의 패널 하나로 연다. 패널을 계속 쌓지 않는다. 초안을 가진 질문 영역이 밀리면 돌아올 수 있는 상태와 초안 표시를 유지한다.
- 주소 예: `/p/<id>/e/<id>/s/research/r/2?peek=<object-id>#q-<id>`. 버전 고정이 필요하면 version 식별자를 별도로 넣는다. 시작 질문은 라운드 경로 없이 stage 범위다. URL에 질문·인용 본문은 넣지 않는다.
- 짧은 번호 Q/C/D/A는 화면·대화용이고 프로젝트 내부 ID와 함께 쓴다. Enter는 해당 항목 전체 보기, Esc는 닫고 원래 항목에 초점 복귀, 브라우저 뒤로 가기는 이전 작업 상태로 돌아간다.
- ‘3 / 12 이전·다음’은 진입할 때의 필터·정렬·대상 ID 목록을 고정한다. 처리 후 필터에서 빠져도 다음 항목이 건너뛰어지지 않는다. 새 항목은 ‘새 항목 2개’로 알리고 명시적으로 목록을 갱신한다.

### 2.11 전송 허용과 실제 전송

- 프로젝트 생성 화면은 ‘OpenCode Go 전송 허용: 켜짐’을 보이고 끌 수 있게 한다. 기존 프로젝트도 헤더에 항상 상태와 끄기 스위치를 둔다. 허용은 자동 실행 동의가 아니다.
- 현재 합의상 정책 변경은 소유자 동작이다. 다른 사용자에게는 상태와 권한 이유를 보여 준다. 에이전트·브라우저 에이전트는 재허용하지 못한다. 정책 누락·손상은 ‘허용 확인 불가 · 차단 중’이다.
- 스위치 변경은 서버가 확정하기 전 ‘변경 중’이며, 실패하면 실제 정책 상태와 실패 이유를 표시한다. 화면에서 꺼져 보이는 것만으로 차단 완료라고 하지 않는다.
- OFF 확정 뒤 준비된 전송·재시도·요약·첨부도 차단한다. 이미 전송 중인 것은 취소 시도 결과를 별도로 보여 주며 ‘이미 나간 자료의 회수는 보장되지 않음’을 해당 상황에서 안내한다.
- ‘전송 내역’에는 시각·대상·자료 범위·정책 버전·준비/허가/전송/차단/실패/결과 불명 상태를 표시한다. `unknown`을 미전송으로 바꾸지 않는다.
- OFF여도 열람·사람의 입력·방식 B는 계속 쓸 수 있다. Go가 필요한 실행 버튼에는 차단 이유와 B로 이어가기 입구를 둔다. 재허용해도 자동 재시작하지 않는다.

### 2.13 범위를 골라 인쇄

추천 흐름은 **범위 선택 → 포함 항목·분량 확인 → 고정본 미리보기 → 브라우저 인쇄/PDF**다. 현재 DOM의 접힌 상태를 인쇄 결과로 삼지 않는다.

| 범위 | 선택 항목 | 추천 기본 |
|---|---|---|
| 라운드 | 현재/지정 라운드, 결과·질문/답·가정·첨언·반영·결정 | 현재 라운드의 결과+질문/답+반영 |
| 단계 | 특정 단계, 최신 결과 요약 / 라운드별 기록 | 최신 결과 요약, 기록 포함은 선택 |
| 전체 | 현재 판의 6단계, 다른 판 추가 여부 | 현재 판 전체. 다른 판은 명시 선택 |

### 2.14 한국어·Windows·접근성

- 본문 16px 안팎, 표·질문 14~16px, 보조 글자 13px 이상을 시작값으로 검증한다. 글꼴은 시스템 한글 글꼴과 Malgun Gothic을 포함한다. 긴 한글 제목·공백·숫자 0·긴 URL로 확인한다.
- 요약 카드·선택지는 같은 행에서 같은 폭·높이, 공통 여백·정렬선을 쓴다. 본문·대화는 내용에 맞춰 늘리고 고정 높이로 잘라 내지 않는다. 목록의 표는 열 제목과 값 대응을 유지한다.
- 건수는 분자/분모와 범위를 표시한다. 출처가 없으면 ‘확인 대상 없음’, 읽지 못한 출처는 ‘확인 못 함’이다. 숫자 없는 퍼센트·근거 없는 ‘완료’를 피한다.
- 기본은 밝은 배경·짙은 본문·절제된 강조색이다. 이모지는 기능 이름을 대신하지 않는다. 밝은/어두운 모드 모두 일반 글자 대비 4.5:1, 큰 글자·조작 경계·초점 표시 3:1 이상을 제품 검증 목표로 제안한다.
- 상태는 글자+테두리/아이콘으로 구분한다. hover만으로 나타나는 버튼을 필수 입구로 쓰지 않는다. 표·선택지는 의미에 맞는 table/fieldset/label과 네이티브 입력을 우선한다.
- 키보드 순서는 헤더→탐색→결과→질문이다. ‘결과로/질문으로 건너뛰기’를 제공하고 대화창·미리보기는 열린 곳으로 초점 이동, Esc로 닫고 호출 위치 복귀를 지킨다.
- 드래그 대체 버튼, 키보드 글 선택, 선택 없이 문단에서 첨언하기를 제공한다. 툴팁만 있는 아이콘·포인터로만 쓰는 리사이즈 손잡이를 피한다.
- 200% 확대·320px 폭에서 주요 동작이 한 열로 이어져야 한다. 넓은 데이터 표만 별도 가로 스크롤을 허용한다. 조작 영역은 최소 24px, 자주 쓰는 단추는 약 36px 이상을 목표로 한다.
- 접수·오류·새 결과는 상태 영역으로 알리고 매 토큰을 읽어 주지 않는다. Windows Edge+NVDA, 키보드만, 고대비 모드·확대, macOS 브라우저에서 합성 자료로 확인한다.

### 2.15 기술 선택: 서버 렌더를 기본으로, 상호작용만 클라이언트에

| 선택지 | 장점 | 부담·판단 |
|---|---|---|
| 서버 렌더+전체 이동 | Python 로컬 서버·출력 문서와 연결하기 쉬움 | 매 이동 시 초안·선택·미리보기 복구 부담. 이것만으로 새 작업 공간을 만들기는 부족 |
| SPA | 패널·입력·검토 이동 상태를 한곳에서 관리 | 라우팅·서버/클라이언트 상태 복제·빌드·인쇄 화면 등 초기 운영 부담 |
| 서버 렌더+부분 상호작용 | 읽기·고정본은 서버, 질문/첨언/팔레트만 부분 갱신 | 경계와 초점 보존 규칙을 명확히 해야 함. **현재 규모에 추천** |

- 초기 HTML과 깊은 링크는 서버가 읽기 모델에서 만든다. TypeScript 모듈이 질문 편집·초안·선택 막대·미리보기·팔레트만 맡는다. 결과 원고를 곧바로 범용 블록 편집기로 만들지 않는다.
- 화면 데이터·명령 계약은 렌더러와 분리한다. 브라우저는 DB를 직접 읽거나 쓰지 않는다. 로컬 Python과 향후 Workers는 같은 API·검증 규칙을 구현하고, 서버 템플릿 코드를 그대로 이식할 수 있다고 가정하지 않는다.
- 패키지·템플릿 엔진·번들러는 여기서 고정하지 않는다. 실행에 Node를 필수로 더하지 않고 배포 정적 자산을 쓸 수 있는지, Windows 설치·오프라인 열람·향후 웹 재사용을 2단계에서 확인한다. 개발 빌드 의존성과 사용자 실행 의존성은 구분한다.
- 초기 변경 알림은 **번호 커서 기반 폴링**을 권한다. 활성 화면 약 3초를 출발점으로 하되 비활성·오류 시 늦춘다. SSE는 실행 스트림 등 필요가 검증되면 추가한다. 전체 페이지 새로고침을 변경 동기화로 쓰지 않는다.
- 커서는 DB instance/epoch·프로젝트 범위를 포함하는 불투명 값으로 API가 정한다. 사건 번호의 빈틈은 오류가 아니다. tx_index/tx_size를 고려해 한 명령의 화면 변경을 완성된 묶음으로 반영한다. 복원으로 커서가 무효면 초안을 보존하고 읽기 모델을 다시 받는다.
- 제출·승인·정책 변경·외부 전송은 서버 영수증 뒤 성공으로 표시한다. 패널 펼침·로컬 초안 같은 되돌릴 수 있는 화면 조작만 즉시 반영한다. 범용 오프라인 쓰기 큐·CRDT는 넣지 않는다.
- 저장 Markdown/외부 인용은 안전하게 렌더하고 임의 스크립트·이벤트 속성·위험 URL을 허용하지 않는다. 로컬 쓰기는 출처·요청 위조 방어와 사람/에이전트 구분을 서버에서 검증한다. 로그인 UI를 2단계에 새로 요구하는 것은 아니다.
- 한글 입력 보존·선택 앵커·검토 이동 시나리오에서 부분 갱신 방식이 복잡해지면 3단계 착수 전 작은 SPA와 비교한다. 이 경우 API·출력 고정본·DB 합의는 바꾸지 않고 렌더러만 재선택한다.

## 3. 방식 A·B의 화면 차이

질문 폼·답·가정·반영・결정·첨언·인쇄는 같은 데이터와 같은 화면이다. 차이는 **누가 실행하고, 전달·중단·재개를 어디까지 확인할 수 있는가**에만 둔다.

| 상황 | 방식 A: PES 안 OpenCode Go | 방식 B: Claude Code·Claude 앱 |
|---|---|---|
| 담당 표시 | 내부 AI, DeepSeek 모델, 연결 상태 | 외부 에이전트, 실제 runtime·알려진 모델. 모르면 확인 불가 |
| 시작 | 사람이 ‘이번 작업 실행’, 정책·실행 담당 확인 | 연결된 에이전트가 가져갈 일 등록. PES가 앱을 자동 깨운다고 가정 안 함 |
| 질문 답 제출 | PES 접수→재개 가능/실행 중. 자동 재개 정책은 SEL-24 | PES 접수→외부 에이전트 수신 대기→읽음/반영. 꺼진 앱에도 접수는 유지 |
| AI에게 묻기 | 질문 등록 후 명시적 실행. 기존 실행이 있으면 후속 대기 | 질문 등록+전달 대기. ‘프롬프트로 복사’를 함께 제공 |
| 권한 요청 | PES의 실행 권한 영역에서 중계 | 해당 도구에서 처리. PES 연구 질문과 분리 |
| 중단 | 중단 요청 후 어댑터가 확인한 상태 표시 | 확인 가능한 취소/담당 회수 범위만 표시. 외부 프로세스 종료와 동일시 안 함 |
| 재접속 | 세션·run 상태 확인, 새 실행과 재개 구별 | 마지막 입력 영수증 확인, 읽지 않은 질문·답 제시. 지속 heartbeat 가정 안 함 |
| Go OFF | Go 호출·요약·첨부·재시도 차단, B로 인계 가능 | 작업 공간 사용 가능. 실제 Go 목적지 호출은 같은 정책 검사 |
| 실행 담당 교체 | 기존 담당 중단/만료 확인 후 새 담당 획득 | 똑같음. 질문·첨언·답·후속은 담당을 바꾸어도 남음 |
| 완료 | run 완료와 사람의 단계 승인은 별도 | 동일. 복사·앱의 답 문장만으로 PES 결과 채택 안 됨 |

Claude 앱의 실제 연결 방법은 SEL-24/2단계 PR 20의 확인 대상이다. 연결되기 전에는 ‘앱 연결 미확인’과 복사 대안을 표시한다. WebMCP가 Claude 앱 연결을 대신한다고 쓰지 않는다. Codex·OpenCode TUI 추가 지원은 별도 어댑터 검토다.

근거: `docs/plan/stage-0.md:87–90`, `docs/plan/stage-1-db.md:136–144`, `docs/plan/stage-1-db.md:214–214`, `docs/plan/discussion/stage-0-opencode.md:678–715`, `docs/plan/discussion/stage-0-opencode.md:719–756`.

## 5. 사용자 결정이 필요한 것 (추천 포함)

합의된 DB 17개 결정과 A/B 지원 범위는 이 표에 넣지 않는다. 아래는 새 화면을 종합할 때 받을 선택이다.

| 첫 배치 | 결과+질문 병렬 / 질문만 크게 / 대화 중심 | 병렬+질문 기본 열림. ‘질문에 집중’ 전환 제공 |

| 답 제출 단위 | 질문마다만 / 묶음만 / 둘 다 | 묶음 검토를 주 버튼으로, 개별 답·의견 전송도 제공 |

새 이슈는 아래 기능 묶음만 제안한다. UI 번호는 이 문서 안의 제안 식별자다. 기능별 API·서비스·검증을 같은 PR에 포함하고 화면만 먼저 붙이지 않는다.

UI-3의 ‘할 일로’는 UI-7 전에도 PES 후속과 Linear용 초안·복사까지 동작한다. 실제 Linear 생성은 연결 구현 뒤 활성화하며 자동 완료·가짜 외부 이슈 번호를 만들지 않는다. 접근성·보안·초안·A/B 검증은 각 기능의 완료 조건이며 별도 마지막 정리 이슈로 미루지 않는다.
