## 3. 무료 요금제 설계 점검

**요금제 방향은 맞게 바뀌었다.** 2절 표·2.1·2.9·5절·6절이 모두 Workers Free·D1 Free·R2 무료 구간을 전제로 하고, 유료 계정·결제 주체·월 예산은 9절의 전환 신호가 나올 때만 묻는다(7·223·230·339·381줄).

### 3.2 문제·확인 필요

| 항목 | 판정 | 위치 | 고칠 것 |
|---|---|---|---|
| 단일 DB 권장 vs 500 MB 추정 | 틀림 | 2.1.2 "D1 저장" 행, 2.8 "단일 DB" | 추정 가정(텍스트 3프로젝트 500 MB)이 이미 **DB당 500 MB의 100%**인데, 2.8은 모든 프로젝트를 DB 하나에 둔다. 처음부터 **프로젝트(또는 묶음)별 D1 분리(무료 10개 안)** 를 기본으로 하거나, 추정 가정을 실측 전 "상한 시나리오"로 낮추고 단일 DB의 분리 기준(예: 350 MB)을 WEB10에 넣는다. 둘 중 하나로 맞춘다 |
| 폴링 값 변경의 경계 | 틀림 | 2.1.2 2번, WEB6 | 1단계 UI 결정 14(활성 약 3초 커서 폴링)를 웹에서 25–30초 long poll/SSE로 바꾼다. 변경 자체는 무료 한도 때문에 타당하지만 "**UI 결정 14의 웹 조정, 로컬 모드는 그대로**"라고 명시하고 U1 계약(커서 갱신)과 같은 의미를 유지한다고 적는다 |
| Workers에서 25초 long poll 구현 | 확인 필요 | 2.4·2.5·2.1.2 | Durable Objects 없이 Worker 안에서 D1을 반복 조회하면 **호출당 쿼리 50·subrequest 50**에 걸리고 행 읽기가 늘어난다. Free에서 SQLite Durable Objects가 제공되는 것은 확인했다(가격 문서, 요청 10만/일·행 읽기 500만/일). WEB1에서 "DO로 대기 / 짧은 폴 + ETag / SSE" 중 무엇을 쓸지 정하고 한도를 계측하도록 적는다 |
| R2 활성화에 결제 수단 등록이 필요한가 | 확인 필요 | 2.1·6절 | r2/pricing에는 언급이 없다. 무료 구간이라도 대시보드에서 R2를 켤 때 결제 수단을 요구할 수 있다. WEB1 전에 확인하고, 필요하면 "요금 0원이어도 결제 수단 등록"은 사용자에게 묻는 항목(6절)으로 올린다 |
| Cron 호출당 wall time 15분 | 확인 필요 | 2.1.1 Cron 행 | cron-triggers 페이지에는 Free 수치가 없다. limits 페이지의 Free는 Cron CPU 10 ms·5개만 확인됨. 15분은 "미확인"으로 표시 |
| "요청당 평균 2.2 ms(공식), 인증·SSR 10–20 ms(공식)" | 확인 필요 | 2.1.2 CPU 행 | 출처가 없다. "(공식)"을 빼고 추정치로 표시하거나 출처 URL을 붙인다. WEB0·WEB2에서 p95를 실측한다는 기존 문장은 유지 |
| D1 import 5 GB, 9.2의 Queues·Workflows Paid 포함량 | 확인 필요 | 2.1.1 D1 기타, 9.2 | 이번에 직접 확인하지 못했다. 유료는 9절 전환 때 다시 확인한다고 적으면 충분 |
| Python Workers의 Free 포함 여부 | 확인 필요(초안도 미확인 표시) | 2.1·WEB0 | 초안이 이미 미확인으로 두고 WEB0에서 확인한다. 그대로 둔다 |
