## 0. 한 장 요약

1. **질문 폼 페이지를 없애는 것이 아니라, 프로젝트 작업 공간 하나 안의 "질문 작업면"으로 바꾼다.** 셸(단계·라운드·전송·명령)은 고정하고 가운데 작업면만 질문/결과 글/가정·결정/기록으로 바뀐다.
2. **열린 질문이 있으면 질문 작업면이 기본**이다. 질문 카드에서 고치기·더하기·빼기·질문별 의견·중요도·기본값·재확인 필요를 모두 처리한다.
3. **결과 글은 읽기 전용 + 선택 도구**로 둔다. 글을 고르면 `첨언 / AI에게 묻기 / 할 일로`가 뜨고, 첨언 앵커 상태(`exact/moved/ambiguous/lost`)를 숨기지 않는다.
4. **가정·결정·반영 내역은 표로** 둔다. "해결됨 ≠ 적용됨"이고, `applied`에는 결과 버전·tx 증거가 있어야 한다(stage-1-db 11-5).
5. **Cmd/Ctrl+K 하나의 동작 목록**이 명령 메뉴·문맥 메뉴·단축키를 만든다. 같은 입력 칸에서 Tab으로 AI에게 묻기로 전환한다(notion-linear 3.7).
6. **프롬프트로 복사는 방식 B의 기본 통로**다. 복사 전에 포함·제외·경고를 미리 보여 준다.
7. **전송 허용 칩은 항상 보이고, 끄기 스위치는 소유자 사람만** 만질 수 있다. 끄기는 이미 나간 자료를 되돌리지 않는다(stage-1-db 11-6).
8. **인쇄는 라운드/단계/판 전체**를 고르고, 가능하면 봉인된 스냅숏 기준으로 찍는다. A4·표 머리 반복·흑백 대비.
9. **기술은 서버 렌더 + 작은 JS 섬 + 공유 논리없는 템플릿**을 추천한다. 3단계에 SPA 프레임워크를 넣지 않는다.
10. **접근성은 키보드·대비·한글 IME·200% 확대·색 비의존**을 완료 조건에 넣는다.
11. **2단계는 현재 화면을 DB/API로 바꾸는 것만** 한다(PR 18, 새 디자인 없음). 새 작업 공간은 3단계에서 연다.

### 3.3 기술 선택 — P0

**정할 것**: 서버 렌더/SPA/하이브리드, 로컬(Python)과 웹(Workers/D1)의 화면 공유, 빌드 도구 도입 여부.
**선택지**: 1) 정적 HTML + `POST /feedback` 확장 / 2) **서버 렌더 + 작은 JS 섬 + 공유 논리없는 템플릿** / 3) React/Vue SPA / 4) 서버 렌더 셸 + SPA 섬.
**판단 기준**: 로컬·웹 같은 HTML·접근성, 인쇄·첫 화면·키보드, Windows 무빌드 실행, 섬만으로 충분한 상호작용, 3단계 예산.
**추천: 2번.**
- 셸·목록·질문 카드·표·인쇄는 서버가 HTML로 만든다. 명령 메뉴, 선택 도구, 질문 편집, 초안 저장, 이벤트 갱신만 JS 섬으로 둔다.
- **논리없는 Mustache 부분집합** 한 벌을 `templates/workspace/`에 두고, 로컬은 Python의 작은 렌더러, 웹은 JS 렌더러가 같은 파일을 읽는다. `__TITLE__` 치환과 JS 문자열 조립을 늘리지 않는다.
- 프레임워크·번들러는 3단계에 넣지 않는다. ES 모듈과 `fetch`로 충분하다. 5단계에서 필요하면 다시 판단한다.
- 작업 공간은 로컬 서버(`pes serve`)가 필요하다. `file://`은 내보낸 HTML·인쇄본에만 쓴다.
- 이유: 지금 화면은 이미 서버 렌더이고(`scripts/pes.py` `build_index` 412-438), 인쇄·접근성·첫 화면이 강점이다. SPA는 빌드·상태 동기화·접근성 비용을 먼저 치른다. 웹이 Python을 못 돌리므로 HTML을 두 번 쓰지 않도록 공유 템플릿을 처음부터 정한다.
- 위험: Mustache 부분집합을 Python/JS에 두 번 구현하는 비용. U1에서 1주 안에 안 되면 "JSON + 얇은 클라이언트 렌더"로 후퇴하되 HTML을 포크하지 않는다.

### 3.4 URL·상태 — P0

**정할 것**: 화면 상태를 URL에 담는 범위, 짧은 번호와 내부 ID의 역할, 기존 `ask-*.html` 호환.
**선택지**: 1) 해시만(`#questions`) / 2) **경로 + 쿼리** / 3) 클라이언트 상태만.
**판단 기준**: 새로고침·뒤로/앞으로·링크 공유, 알림·첨언·질문 딥링크, 사람이 읽기 쉬움, 철회·삭제 링크가 404가 아님.
**추천: 2번.**
- 경로: `/p/<slug>/e/<edition_no>/s/<stage_key>/r/<round_no>`. 쿼리: `view=questions|result|decisions|record`, `focus=Q-12|C-7|D-3|A-5`, `peek=...`, `print=round|stage|edition`.
- 화면에는 내부 UUID 대신 `Q-12`, `C-7`, `D-3`, `A-5`를 쓴다. API에는 ID를 쓴다(notion-linear 128, 133).
- `ask-<id>.html`은 해당 질문 세트의 `?view=questions&set=<id>`로 리디렉트한다. 인쇄·내보낸 HTML은 그대로 둔다.
- 철회된 질문·잃은 첨언은 "철회됨/위치 잃음" 상태로 보여 주고 원문 버전 링크를 준다.
- 이유: 새로고침·공유가 되는 URL은 연구 기록에서 곧 인용 가능한 주소다. 해시만 쓰면 서버가 화면을 복원할 수 없다.

### 3.5 단계·라운드 이동과 순서 넘기기 — P0

**정할 것**: 단계·라운드 이동, 질문·첨언의 순서 처리, `재확인 필요` 표시.
**선택지**: 1) 단계 탭만 / 2) **단계 레일 + 라운드 탭 + `3/12 ↑↓` + `J/K`** / 3) 별도 검토 모드.
**판단 기준**: 목록으로 돌아가지 않고 연속 처리, 현재 위치 유지, 승인·reopen과 단축키 분리.
**추천: 2번.**
- 왼쪽 레일에서 단계를, 작업면 위에서 라운드를 고른다. `R1/R2/…` 탭에는 봉인·현재·승인을 글자로 병기한다.
- 질문·첨언 목록 위에 `3/12`와 `↑↓`를 두고, 입력 칸에 초점이 없을 때 `J/K` 이동, `Enter` 열기, `Esc` 닫기.
- `재확인 필요`는 단계 배지와 질문 배지 두 곳에 둔다. 앞 단계가 바뀌면 "앞 단계가 바뀌었습니다 — 다시 확인" 배너를 띄우되 읽기를 막지 않는다(stage-1-db 57).
- 승인·reopen은 단계 헤더에만 두고, 명령 메뉴의 AI 모드에서는 노출하지 않는다.
- 이유: Linear의 `3/4 ↑↓`(notion-linear 3.7)는 긴 질문 목록을 연속 처리하는 데 유용하다. 다만 되돌리기 어려운 동작과 같은 단축키를 쓰지 않는다.

### 3.6 질문 작업면 — P0

**정할 것**: 질문 목록의 배치, 카드 구성, 고치기·더하기·빼기, 질문별 의견, 중요도·기본값, 재확인.
**선택지**: 1) 기존 폼을 그대로 / 2) **질문 카드 목록 + 인라인 편집 + 질문별 스레드** / 3) 표 한 줄씩.
**판단 기준**: 긴 질문을 읽기 좋은가, 고친 질문과 옛 답의 관계가 보이는가, 답과 의견이 섞이지 않는가, 한 화면에서 여러 질문을 처리하는가.
**추천: 2번.**
- 상단 요약: `질문 7 · 답 4 · 필수 2 · 높음 2 · 재확인 1`. 필터는 `전체 / 높음 / 재확인 / 내가 AI에게` 네 개만 둔다.
- 질문은 **한 열**로 둔다. 1600px 이상에서도 두 열로 나누지 않는다. 질문·선택지·의견이 길어 두 열은 읽기 순서를 깨뜨린다.
- `반영 내역`은 질문 위에 접힌 요약 막대로 둔다. 새 라운드 첫 방문에만 자동으로 펼치고 그 뒤에는 사용자가 펼친다.
- 맨 아래 `+ 질문 더하기`. 기본 방향은 `내가 AI에게`, AI가 만든 질문은 `AI → 나`로 표시한다(00-brief 19).

```text
Q-12  [높음] [열림] [재확인 필요]                    고치기 · 빼기 · 의견 2
이 질문의 문장…
도움말…
( ) 선택지 A  (•) 선택지 B [기본값] [추천]   기타·덧붙일 말 [        ]
[이 질문만 저장]  [답 제출에 포함]
```

- 머리: `Q-12`, 중요도(`높음/보통/낮음`), 상태(`열림/보류/합침/철회/닫힘`), `재확인 필요`, 방향.
- 몸: 질문 문장, 도움말, 선택지, `기타·덧붙일 말`. 기존 `_questions.html`의 `__other`와 `show_if`를 유지한다(templates/_questions.html 33-47, 66-75).
- `기본값`과 `추천`을 다른 칩으로 표시한다. 기본값은 미리 채워진 값, 추천은 선택지 표시다. 기본값을 그대로 제출하면 `used_default=1`로 남긴다(DDL 565).
- 필수는 `*`와 글자 `필수`를 함께 쓴다. 색만으로 표시하지 않는다.
- `의견 2`는 질문별 스레드(`question_comment`)다. 답과 의견을 한 칸에 섞지 않는다(stage-1-db 87).
- `고치기`는 인라인 편집, `빼기`는 `철회/합치기`, `미루기`는 `보류(defer_until)`, `합치기`는 대상 질문 선택이다(DDL 493-504).
- 저장은 새 질문 버전을 만든다. 저장 전에 "이 질문의 기존 답은 `재확인 필요`가 되고, 옛 답은 그대로 보존됩니다"를 보여 준다(stage-1-db 24).
- 답은 `이 질문만 저장`(초안)과 `답 제출에 포함`(제출 봉투)으로 나눈다. 초안은 로컬에만 두고, 제출은 `submissions`로 한 번에 보낸다(stage-1-db 85).
- `질문 더하기`는 문장·유형·선택지·중요도·필수·기본값·`show_if`·도움말·방향을 받고, 새 질문 객체와 첫 버전을 한 트랜잭션에서 만든다(DDL 480-483).
- `빼기`는 삭제하지 않는다. `철회`는 흐리게 남기고, `보류`는 `나중에` 필터에, `합치기`는 대상 질문으로 링크한다. 답은 보존한다. 추가·제외·순서 변경은 새 `question_set` 버전을 만들고 `이 라운드 질문지 v3`를 표시한다(stage-1-db 82).
- `재확인 필요`는 현재 답의 `question_version_id`가 현재 질문 버전과 다를 때 읽기 모델에서 계산한다(DDL 562). `옛 답 보기 (R1 문구 기준)` + `다시 답하기`를 주고, 새 답 전까지 옛 답을 승격하지 않는다.
- 이유: 질문을 고치면서 답을 조용히 승계하면 연구 기록의 의미가 바뀐다. 기본값·추천·답을 각각 다른 것으로 보여 주는 것이 사용자의 판단을 돕는다.

### 3.7 결과 글·선택 도구·첨언 — P0

**정할 것**: 결과 글의 편집 범위, 글 선택 시 동작, 첨언·대화의 위치.
**선택지**: 1) 직접 편집 / 2) **읽기 전용 + 선택 도구(첨언/AI에게 묻기/할 일로)** / 3) 별도 편집기.
**판단 기준**: 원문 버전과 첨언의 관계 보존, 사람/AI 글 구분, 수정이 다음 라운드·reopen으로 이어짐, 3단계 범위.
**추천: 2번.**
- 결과 글은 버전 선택기(`현재 / R1 / R2 / 승인본`)와 함께 읽기 전용으로 보여 준다. 직접 고치기는 4단계 제안 모드로 미룬다(notion-linear 48, 132).
- 글을 고르면 `첨언 / AI에게 묻기 / 할 일로` 도구 막대가 뜬다(notion-linear 3.7, 112-113). `Alt+M`으로도 열어 키보드만으로 닿게 한다.
- `첨언`은 인용문·앞뒤 문맥·위치를 저장하고 오른쪽 스레드에 쌓는다. `AI에게 묻기`는 그 인용을 문맥으로 한 질문/스레드를 만든다. `할 일로`는 기본적으로 PES의 `다음 라운드 할 일`(followup)을 만든다.
- `할 일로`의 Linear 내보내기는 **기본 꺼짐**이고, 사용자가 그때그때 `Linear로 내보내기`를 고른 경우에만 미리보기 후 보낸다. 연구 내용 전체를 보내지 않고, PES 개발 할 일처럼 명시적으로 고른 것만 보낸다(notion-linear 140, 149). 프로젝트별 on/off를 서버에 둘지는 새 표 없이 SEL-21·22와 확인한다. 사용자 결정 6-1로 올린다.
- 스레드에서 답글을 고르고 `이 답을 결론으로`를 누르면 `해결됨`이 된다. 결론은 `글 수정 / 다음 라운드 할 일 / 앞 단계 다시 열기 / 그냥 닫기` 중 하나로 남긴다(notion-linear 99, 130).
- `해결됨`과 `반영됨`을 분리한다. `반영됨`은 결과 버전·tx가 있을 때만 표시한다(stage-1-db 11-5).
- 작성자 표시: `사람 / AI(내부, 모델) / AI(외부, runtime) / 브라우저 에이전트`. `대신 씀`이면 원래 사람도 함께 보여 준다(notion-linear 46, 136).
- 이유: 3단계의 목표는 "글을 직접 고치는 것"이 아니라 "첨언을 두고 AI와 대화해 글 수정·다음 라운드·reopen으로 잇는 것"이다(00-brief 21). 읽기 전용이면 원문 버전과 첨언의 연결이 깨지지 않는다.

### 3.8 첨언 앵커 상태 — P0

**정할 것**: `exact/moved/ambiguous/lost`를 화면에서 어떻게 구분하고, 다시 붙이기를 어떻게 받을지.
**선택지**: 1) 찾은 위치로 자동 이동 / 2) **상태를 보여 주고 사람이 확인** / 3) 못 찾으면 첨언 삭제.
**판단 기준**: 원래 앵커를 훼손하지 않는가, 사람이 잘못된 위치에 붙이지 않는가, 잃은 첨언의 스레드가 남는가.
**추천: 2번.**

| 상태 | 화면 | 할 수 있는 일 | 저장 |
|---|---|---|---|
| `exact` | 원문에 정확히 하이라이트 | 스레드 열기, 해결 | 기존 앵커 유지 |
| `moved` | 새 위치에 하이라이트 + `위치 이동됨` | 확인, 다시 붙이기 | 새 `anchor_resolution` |
| `ambiguous` | 후보 2~3개를 앞뒤 문맥과 함께 | 후보 선택 또는 `인용문으로만` | 사람이 고른 결과를 새 판정으로 |
| `lost` | 인용문 카드 + `원문에서 찾지 못함` | 다시 붙이기, 옛 버전 보기, 닫기 | 원래 앵커는 고치지 않음 |

- `ambiguous`에서 첫 후보를 자동 선택하지 않는다. 후보를 고르면 원래 앵커를 고치는 것이 아니라 새 판정을 덧붙인다(stage-1-db 25).
- `lost`는 첨언을 지우는 것이 아니다. 인용문과 스레드는 남기고, `다시 붙이기`에서 새 범위를 고르게 한다.
- 앵커 이력(`R1 exact → R2 moved → R3 lost`)을 접힌 상세에 보여 준다. 인쇄에서는 각주 말미에 상태를 적는다.
- 이유: 인용문은 남고 위치는 틀릴 수 있다. 화면이 `lost`를 숨기면 사용자는 첨언이 사라졌다고 오해한다.

### 3.9 가정 — P0

**정할 것**: 가정 목록의 위치, 맞다/틀리다/고침 입력, AI 제안과 사람 확정의 구분, 새 판·재확인.
**선택지**: 1) 질문 폼 안 문장 / 2) **가정 탭 + 질문·결과 문맥 칩** / 3) 결정 기록에 합침.
**판단 기준**: AI가 깔고 있는 가정이 보이는가(00-brief 24), 틀린 가정의 영향을 볼 수 있는가, 사람 판단과 AI 제안이 구분되는가.
**추천: 2번.**
- 표 열: `A-5 / 가정 / 상태 / 판단자·시각 / 근거·메모 / 영향`. 상태는 `제안/확인/틀림/고침`(DDL 595).
- `맞다`는 한 번에 확인하고 토스트에 `되돌리기`를 둔다. `틀리다`는 짧은 이유를 받되 `이유는 나중에`를 허용한다. `고침`은 새 문장 버전을 만든다.
- AI는 제안·고침을 할 수 있지만, `확인/틀림`은 사람이 누른다. 판단자와 시각을 항상 보여 준다.
- `needs_review=1`이면 `재확인` 배지를 붙이고, 새 판으로 복사돼도 자동 확인하지 않는다(stage-1-db 11-4, DDL 598).
- 질문·결과에는 관련 가정을 칩으로 보여 준다. 틀린 가정이 범위를 바꾸면 결정 또는 followup을 제안하되, 가정을 자동 삭제하지 않는다.
- 이유: 가정은 질문보다 먼저 사람의 머릿속을 드러내는 장치다. 결정 기록과 섞으면 "가정이 틀렸다"와 "결정을 바꿨다"가 구분되지 않는다.

### 3.10 결정 기록 — P0

**정할 것**: "정해진 것"의 위치, 판 범위(프로젝트/판), 대체·철회 표시, 새 판으로 넘길 때 복사.
**선택지**: 1) 단계별 메모 / 2) **프로젝트/판 범위의 살아 있는 결정 표 + 문맥 칩** / 3) 별도 위키.
**판단 기준**: 근거·결정자·시각으로 돌아갈 수 있는가, 새 판에서 프로젝트/판 결정이 구분되는가, 대체·철회가 과거를 지우지 않는가.
**추천: 2번.**
- 표 열: `D-3 / 결정 / 범위 / 상태 / 결정자 / 근거 / 영향`. 상태는 `제안/채택/대체/철회`(DDL 626).
- `새 결정`은 인라인. `대체`는 새 결정을 만들고 `supersedes`로 잇는다. 기존 결정을 덮어쓰지 않는다.
- 프로젝트 결정은 모든 판에 보이고, 판 결정은 그 판에서만 보인다. 새 판에는 프로젝트 결정을 참조하고, 판 결정은 당시 버전을 고정해 복사한다(stage-1-db 23).
- 복사된 결정에는 `이 판에 복사됨 · 원본 D-3 v2`를 붙이고, 원본을 조용히 고치지 않는다.
- 질문·결과 문맥에는 `정해진 것` 칩을 보여 주고, 충돌하면 `기존 D-3와 충돌 — 대체할까요?`를 띄운다.
- 이유: brief의 "정해진 것 목록을 프로젝트 전체의 살아 있는 결정 기록으로"를 만족하려면, 결정이 화면 곳곳에서 보이되 한 곳에서 관리되어야 한다(00-brief 29).

### 3.11 반영 내역 — P0

**정할 것**: 다음 라운드 첫머리의 표시, `적용/부분/반영 안 함/보류`의 판정과 증명, 사용자 이의 통로.
**선택지**: 1) AI 요약 문장만 / 2) **표 + 출처 링크 + 결과 버전 증거** / 3) 사용자가 직접 체크.
**판단 기준**: 내 의견의 반영을 한눈에 보는가, `적용`에 증거가 있는가, 반영되지 않은 이유를 보는가.
**추천: 2번.**
- 표 열: `내 의견(답/첨언/질문) / 어디에 / 처리 / 이유 / 결과(버전·tx) / 시각`.
- `적용`과 `부분`은 결과 버전 또는 followup이 있고, 적용 tx가 있어야 한다. 없으면 `증거 없음` 경고를 붙이고 초록 체크를 쓰지 않는다(stage-1-db 11-5, DDL 811-812).
- 질문 위에는 `적용 3 · 부분 1 · 보류 1` 요약 막대를 두고, 펼치면 표가 나온다.
- 읽기 전용이다. 이의는 원문 스레드에 답글로 남긴다. 사용자가 처리 상태를 직접 바꾸지 않는다.
- 이유: 반영 내역은 신뢰의 핵심이다. AI가 "반영했다"고 말하는 것과 결과 버전이 있는 것은 다르다.

### 3.12 대화·AI에게 묻기 — P0

**정할 것**: 질문·첨언·일반 대화의 스레드 모델, A/B의 "AI 답변" 상태, 실행 수준 질문의 위치.
**선택지**: 1) 하나의 채팅 / 2) **대상별 스레드 + `내가 AI에게` 질문 목록 + 실행 질문 분리** / 3) 이메일식 목록.
**판단 기준**: 연구 질문과 실행 권한 질문이 섞이지 않는가, B에서 답이 없는데 답처럼 보이지 않는가, 대기 중 lease/run 상태가 정확한가.
**추천: 2번.**
- `첨언`은 글 위치 스레드, `질문별 의견`은 질문 스레드, `일반`은 프로젝트/단계 스레드다. 모두 `threads/messages`를 쓰되 `context_kind`로 구분한다(DDL 688).
- `AI에게 묻기`는 `human_to_agent` 질문으로 만들고 `내가 AI에게` 필터에 모은다. 자유 대화는 같은 질문의 스레드에 답글로 쌓는다.
- 방식 A: PES가 run을 만들고 `AI 답변 중` + `중단`을 보여 준다. 답이 오면 스레드에 메시지로 붙는다.
- 방식 B: `외부 에이전트 대기`로 표시하고 `프롬프트로 복사`를 함께 준다. 답이 올 때까지 가짜 타이핑·가짜 답변을 만들지 않는다.
- 실행 권한·폼 요청은 오른쪽 `실행` 패널에 `실행 권한` 라벨로 따로 보여 준다. 연구 질문 목록에 섞지 않는다(stage-1-db 144).
- 답을 기다리는 동안 run은 `waiting_human`, lease는 놓인 상태로 보여 준다(stage-1-db 32).
- 이유: 같은 스레드 모델을 쓰되 "연구 질문"과 "실행 권한"은 다른 것이다. B에서 없는 답을 있는 것처럼 보이면 사용자는 시스템을 믿지 않는다.

### 3.13 Cmd+K·AI 전환·맥락 동작 — P0

**정할 것**: 명령 메뉴·문맥 메뉴·단축키의 단일 동작 목록, AI 전환 위치, AI가 못 하는 동작의 차단.
**선택지**: 1) 화면마다 단추 / 2) **`{id, 이름, 키워드, 단축키, 적용 조건, 실행}` 동작 목록 하나** / 3) 브라우저 기본 단축키만.
**판단 기준**: 같은 동작이 메뉴·오른쪽 클릭·단축키에서 같은 이름인가, 지금 고른 것에 맞는 동작만 나오는가, 승인·reopen·전송을 AI가 못 하는가.
**추천: 2번.**
- `Ctrl+K`(Windows)/`Cmd+K`(Mac). 입력 칸에서 `Tab`을 누르면 `AI에게 묻기`로 전환하고 placeholder가 바뀐다(notion-linear 3.7, 109).
- 동작 예: `단계로 가기`, `라운드 바꾸기`, `질문 찾기`, `첨언 달기`, `AI에게 묻기`, `할 일로`, `프롬프트로 복사`, `이것 인쇄`, `전송 끄기`, `도움말`.
- 문맥: 글을 골랐으면 선택 동작, 질문에 초점이 있으면 질문 동작, 첨언을 보고 있으면 스레드 동작이 먼저 나온다.
- AI 모드에서 가능한 것: 읽기·검색, 답 초안, 첨언·질문 초안, 방식 A의 읽기 답변. **불가능**: 승인, reopen, 판 시작, 전송 재허용, 삭제. 시도하면 이유를 보여 준다(stage-1-db 29-31, webmcp 24).
- 접근성: `role=combobox` + `listbox`, `aria-activedescendant`, `Esc` 닫기, 포커스 트랩 없음. 결과는 `질문/첨언/결정/가정/출처/화면`으로 묶는다.
- 이유: Linear의 핵심은 "동작 목록 하나가 메뉴·단축키·문맥 메뉴를 모두 만든다"이다(notion-linear 3.2, 124, 131). PES도 CLI·API·에이전트가 같은 동작 이름을 쓰면 문서와 테스트가 줄어든다.

### 3.14 프롬프트로 복사·미리보기 — P0

**정할 것**: 프롬프트에 넣을 것/뺄 것, 복사 전 미리보기 수준, A/B에서의 위치.
**선택지**: 1) 화면 전체 Markdown / 2) **선택 범위 + 프로젝트/단계/라운드 + 관련 가정·결정 + 지시 + 버전 ID를 조립하고 미리 보기** / 3) 바로 클립보드.
**판단 기준**: B의 터미널 에이전트에 붙여 넣기 좋은가, 무엇이 나가는지 정확히 아는가, 민감 자료·키가 섞이지 않는가, 같은 프롬프트를 다시 만들 수 있는가.
**추천: 2번.**
- 구성: 역할·지시 → 프로젝트/판/단계/라운드 → 선택한 글 인용과 앞뒤 문맥 → 관련 질문·답 → 관련 가정·결정 → 제약(범위 밖 수정 금지, 출처 유지, 한국어) → 스냅숏/버전 ID → 방식 B에서는 `PES가 보내지 않음` 안내.
- 미리보기 모달: 포함/제외 섹션, 글자 수, `이 내용은 외부 AI에 붙여넣게 됩니다` 경고, `복사`·`Markdown 파일로 저장`.
- 방식 B의 기본 동작은 `대기열에 넣기 + 프롬프트 복사`다. 방식 A에서도 투명성을 위해 복사를 허용한다.
- `전체를 Markdown으로`는 라운드·단계 단위로 따로 둔다. 기본은 선택 범위다.
- 이유: 방식 B는 PES가 실행을 소유하지 않으므로 프롬프트가 사람과 외부 에이전트 사이의 계약이 된다. 미리보기 없이 복사하면 무엇이 나갔는지 기록이 없다.

### 3.15 전송 허용 표시·끄기 스위치 — P0

**정할 것**: 전송 허용의 위치와 눈에 띄는 정도, 끄기·켜기 권한과 확인, 진행 중 실행·이미 나간 자료의 설명.
**선택지**: 1) 설정 깊숙이 / 2) **상단 고정 칩 + 팝오버 스위치** / 3) 프로젝트 생성 때만.
**판단 기준**: 허용 상태를 항상 아는가, 소유자만 바꾸는가, 끄기의 한계를 오해하지 않는가, 정책이 없거나 손상되면 거부하는가.
**추천: 2번.**
- 칩 상태: `전송 허용`, `전송 꺼짐`, `정책 없음 — 실행 불가`, `전송 중`, `해당 없음(방식 B)`.
- 팝오버: 현재 정책 버전, 바꾼 사람·시각·이유, `보내는 것`(맥락·요약·첨부·재시도), `끄기` 스위치.
- 소유자 사람만 스위치를 만질 수 있다. 에이전트 토큰·브라우저 에이전트에게는 비활성 + 이유를 보여 준다(stage-1-db 29-31).
- 끄기 확인: "이미 나간 자료는 회수되지 않습니다. 준비된 전송은 막고, 진행 중 실행은 취소를 시도하며 상태를 기록합니다." 다시 켜도 멈춘 실행을 자동 재시작하지 않는다(stage-1-db 11-6, 29).
- 정책이 없거나 손상되면 `실행 불가`로 막는다. 기본값으로 허용하지 않는다(stage-1-db 18).
- 방식 B: `외부 에이전트(Claude Code) — PES가 전송하지 않음`. 스위치 대신 프롬프트 복사 경고를 둔다.
- 모든 변경은 기록에 남기고, 칩 팝오버에서 `최근 변경`을 볼 수 있게 한다.
- 이유: "허용 ≠ 자동 실행"이고, 끄기는 소급 회수가 아니다. 이 두 문장을 화면에서 계속 보여 줘야 사용자가 오해하지 않는다.

### 3.16 범위 인쇄 — P0

**정할 것**: 라운드/단계/전체의 정의, 포함·제외 항목, 스냅숏 기준 여부.
**선택지**: 1) 현재 화면 브라우저 인쇄 / 2) **범위 선택 + 프리셋 + 스냅숏 기준 인쇄용 HTML** / 3) 서버 PDF.
**판단 기준**: 연구 기록으로 재현 가능한가, 표·각주·첨언이 A4에서 읽히는가, Windows Chrome/Edge에서 PDF가 되는가, 큰 범위에서 실수로 수백 쪽을 찍지 않는가.
**추천: 2번.**
- 범위: `현재 라운드` / `현재 단계 전체` / `판 전체(6단계)`. `모든 판`은 고급 옵션으로 따로 둔다(사용자 결정 6-4).
- 프리셋: `검토용`(질문·답·가정·결정·반영·첨언·출처·변경) / `보고용`(결과·출처·결정·요약).
- 가능하면 봉인된 라운드/단계 스냅숏을 쓴다. 스냅숏이 없으면 `현재 내용 · 출력 시각`을 머리에 적는다(stage-1-db 60).
- 인쇄 CSS: A4, 18mm 여백, 본문 11pt, 표 9pt, `thead` 반복, 질문·첨언 카드 안에서 페이지 나눔 금지, 페이지 번호, 프로젝트/단계/라운드 머리글, 흑백 대비, `@media print`에서 조작 요소 숨김.
- 첨언은 본문 옆 여백이 아니라 절 말미 각주(`C-7`)로 둔다. `ambiguous/lost` 상태도 각주에 적는다.
- 예상 쪽수·항목 수를 먼저 보여 주고, 200쪽을 넘으면 확인을 받는다.
- 서버 PDF는 3단계에서 하지 않는다. hwpx는 마지막으로 미룬다(00-brief 45).
- 이유: 인쇄는 "예쁘게"보다 "그때 무엇을 승인했는지 재현"이 중요하다. 스냅숏 기준이 그 역할을 한다.

### 3.17 접근성 — P0

**정할 것**: 키보드만으로 핵심 작업이 되는가, 대비·확대·고대비·한글 IME, 색·아이콘 비의존.
**선택지**: 1) 마우스 중심 후 보완 / 2) **처음부터 WCAG 2.2 AA를 완료 조건으로**.
**판단 기준**: 질문 답하기·첨언·명령 메뉴·인쇄를 키보드로 끝내는가, 200% 확대에서 가로 스크롤 없이 읽히는가, 한글 조합 중 Enter가 제출되지 않는가, 상태가 색 없이 읽히는가.
**추천: 2번.**
- 키보드 맵: `Tab` 이동, `Ctrl+K` 명령, `J/K` 다음/이전, `Enter` 열기, `Esc` 닫기, `Alt+M` 선택 도구, `Ctrl+Enter` 답 제출.
- 초점: `:focus-visible` 3px, 건너뛰기 링크, 대화상자 포커스 트랩, `Esc` 닫기, 명령 메뉴는 트랩 없음.
- 스크린리더: `aria-live=polite`로 저장·오류·새 결과 알림, `aria-current`로 단계, 표는 `th scope`, 오류 요약은 해당 칸 링크.
- 대비: 본문 4.5:1, UI 3:1. `--muted`(#6a737d)는 배경에 따라 확인하고, 상태는 항상 글자(`승인/진행/재확인/대기`)를 병기한다(card-redesign codex-spec 15).
- 한글 IME: `event.isComposing`일 때 Enter 제출 금지, `compositionend` 뒤에만 제출. Windows 기본 IME에서 시험한다.
- 확대: 200%·400%, 320px 리폴로, 표는 캡션 있는 가로 스크롤. `prefers-reduced-motion` 존중.
- 현재 화면의 `2px` 초점선(ask.html 37)은 3px로 올리고, 입력 중 새로고침(ask.html 141-143, dashboard.html 831-833)은 "배너만"으로 바꾼다.
- 이유: 정책 연구자의 주요 작업은 긴 글 읽기·질문 답하기·인쇄다. 마우스 정밀도와 시력에 기대면 반복 작업에서 피로가 커진다.

### 3.18 시각 규칙(카드·표) — P1

- `docs/archive/card-redesign/`의 합의를 토큰으로만 쓴다: 작은 모서리(4/6px), 얇은 테두리, 같은 크기 KPI 그리드, 항목 제목의 옅은 배경+구분선, `Malgun Gothic` 추가(card-redesign codex-spec 9-16, preview.html 15-32).
- **같은 크기 카드는 요약·KPI에만** 쓴다. 질문 카드는 머리·여백·동작 위치를 같게 하되 높이는 내용에 맡긴다. 억지로 같은 높이를 만들면 긴 질문이 잘린다.
- 질문은 한 열, 결과 글은 최대 72자 폭, 표는 숫자 오른쪽 정렬·`tabular-nums`.
- 본문 14px, 보조 13px 이상, 줄간격 1.6. 10~11px 보조 글자는 쓰지 않는다(card-redesign codex-spec 14).
- 이모지 최소. 아이콘을 쓰면 항상 글자 라벨을 붙인다. 장식용 그라데이션·그림자 남용 금지.
- 색: 밝은/어두운 모드 모두 기존 변수 계열. 인쇄는 흑백.
- 지금 카드 시안을 코드에 적용하지 않는다. 3단계 U1에서 토큰으로 옮긴다(00-brief 53).

### 3.19 갱신·초안 보존 — P1

- 화면은 `event_seq` 커서로 바뀐 부분만 갱신한다. 로컬은 5~10초 폴링, 필요하면 SSE. 웹소켓은 3단계에 넣지 않는다.
- 입력 중이면 절대 새로고침하지 않는다. `새 결과가 있습니다 — 새로 보기` 배너만 띄운다(stage-1-db 11-7).
- 초안은 `project/round/question_version` 키로 로컬에 저장한다. 제출하면 지운다. 자동 제출하지 않는다.
- 질문 버전이 바뀌면 초안에 `질문이 바뀌었습니다 — 새 문구를 확인하세요`를 붙이고, 그대로 제출하지 못하게 한다.
- 여러 탭·원격: `base_rev` 충돌 시 `다른 곳에서 먼저 저장했습니다` + `새로 고치기`/`내 초안 복사`를 준다.
- 복원 후 `cursor_epoch`가 바뀌면 전체 새로고침 + 안내(DDL 950-955).
- 이유: 현재 화면은 입력 중이면 배너만 띄우지만(ask.html 141-143), 새 작업 공간은 질문별 초안이 많아 보존 규칙이 더 중요하다.

### 3.20 API에 요구하는 것 — P0

이 절은 API를 다시 정하는 것이 아니라, 화면이 필요로 하는 **읽기 모델·명령·오류**를 SEL-22로 넘기는 것이다.

| 화면 동작 | 필요한 명령(예) | 권한·확인 | 오류 |
|---|---|---|---|
| 작업 공간 열기 | `GET /workspace?edition=&stage=&round=&view=` | reader | `not_found` |
| 변경분 받기 | `GET /changes?since=&epoch=` | reader | `cursor_expired` |
| 질문 고치기/더하기/빼기 | `question.edit/add/withdraw/defer/merge` | editor, `base_rev` | `stale_rev` |
| 답 제출 | `answer.submit(set_id, answers, client_request_id)` | human/editor | `invalid_answer` |
| 질문별 의견 | `thread.message.add` | editor | `stale_rev` |
| 가정 판단 | `assumption.assess` | human만 확인/틀림 | `forbidden` |
| 결정 채택/대체 | `decision.adopt/supersede/revoke` | human만 채택 | `conflict` |
| 첨언 달기/다시 붙이기 | `annotation.create/reanchor` | editor | `anchor_invalid` |
| 스레드 해결 | `thread.resolve(message_version_id, outcome)` | human | `invalid_transition` |
| 할 일로 | `followup.create(kind, target)` | editor | `invalid_target` |
| 프롬프트 복사 | 서버 명령 없음(클라이언트 조립) | reader | — |
| 전송 끄기/켜기 | `policy.set(allow_opencode_go, reason)` | **owner human만** | `forbidden` |
| 인쇄 | `GET /print?scope=&snapshot=` | reader | `snapshot_missing` |

- 모든 쓰기는 `client_request_id`로 멱등, `base_rev`로 충돌 감지, 0행이면 실패. 화면은 `stale_rev`를 받으면 덮어쓰지 않고 충돌 UI를 띄운다(stage-1-db 111-112, 122).
- 이벤트 종류 예: `question.version.created`, `answer.submitted`, `assumption.assessed`, `decision.adopted`, `thread.message.created`, `anchor.resolved`, `followup.applied`, `policy.changed`, `run.status.changed`, `reflection.created`.
- WebMCP 노출: 읽기·검색, 답 초안, 첨언·질문 추가까지. 승인·reopen·판 시작·전송·삭제는 노출하지 않는다(webmcp 19-25).
- 이유: 화면이 DB를 직접 읽으면 권한·rev·멱등이 화면마다 복제된다. 읽기 모델 하나와 명령 하나를 두고, 화면은 그 위에서 상태만 그린다.

## 4. 방식 A·B 차이

| 기능 | 방식 A (PES 안 OpenCode Go) | 방식 B (Claude Code·Claude 앱) | 공통 |
|---|---|---|---|
| 질문·답 | PES 질문이 원본. OpenCode form은 실행 수준 | 같음 | 같은 표·같은 화면 |
| AI에게 묻기 | PES가 run을 만들어 답변 | `human_to_agent` 질문을 쌓고 외부 에이전트가 가져감 | 스레드에 쌓임 |
| 답변 상태 | `AI 답변 중` + 중단 | `외부 에이전트 대기` + 프롬프트 복사 | 가짜 답변 금지 |
| 질문 수정 | 실행 중이면 다음 run부터 적용 경고 | 다음 poll부터 적용 | 새 질문 버전 |
| 첨언·대화 | PES 내부 AI가 요약·후속 제안 | 외부 에이전트가 API로 읽고 씀 | 같은 스레드 모델 |
| 프롬프트 복사 | 보조(투명성) | **기본 통로** | 같은 조립 규칙 |
| 전송 표시 | Go 정책 칩·끄기 스위치·`outbound_dispatches` | `PES가 전송하지 않음` | 정책은 사람만 |
| 실행 상태 | PES가 세션을 멈추고 이어 감 | heartbeat/lease, 끊기면 대기 | `waiting_human` |
| 실행 권한 질문 | OpenCode permission/form을 `실행` 패널에 | 터미널 프롬프트 | 연구 질문과 분리 |
| 행위자 표시 | `AI(내부) · DeepSeek` | `AI(외부) · Claude Code/Claude 앱` | 사람/에이전트 구분 |
| 장애 | OpenCode 서버 없으면 A 실행 불가 | 터미널 에이전트 없으면 대기 | 읽기·답은 계속 가능 |

- 같은 DB 상태라면 화면은 같아야 한다. 다른 것은 `runs.mode`, `actor.kind`, 전송 칩, 대기 문구뿐이다(stage-1-db 138-144).
- 방식 B에서 "AI 답변 중" 애니메이션을 보여 주지 않는다. 답이 없으면 없다고 표시한다.
- Claude 앱은 지속 연결·heartbeat를 가정하지 않는다. 끊긴 뒤 재접속·입력 반영 확인 방법은 SEL-24 완료 조건으로 넘긴다(stage-1-db 214).

## 9. 위험과 열린 질문

1. **공유 템플릿 비용**: Python/JS 두 렌더러 유지가 3단계 예산을 넘을 수 있다. U1에서 1주 안에 안 되면 "JSON + 얇은 클라이언트 렌더"로 후퇴하되 HTML을 포크하지 않는다.
2. **인쇄 재현**: Chrome/Edge/Firefox의 페이지 나눔·표 머리 반복이 다르다. Windows Chrome/Edge 기준, Firefox는 "읽을 수 있음" 수준.
3. **앵커 모호성**: 후보가 3개를 넘거나 문맥이 같을 수 있다. 자동 선택하지 않고 `인용문으로만`을 항상 제공한다.
4. **방식 B 대기**: 외부 에이전트가 없으면 질문이 오래 쌓인다. `대기 3일` 같은 경과와 `프롬프트 복사`를 보여 주고, 자동 재시도·가짜 답변은 하지 않는다.
5. **전송 끄기의 오해**: 끄기가 이미 나간 자료를 회수하지 않는다는 문장을 확인 대화상자·도움말·감사 기록에 반복한다.
6. **Linear 범위**: 연구 내용을 Linear로 보내는 것은 사용자 결정 6-1에 달려 있다. 기본은 PES 안에서 끝낸다.
7. **다중 사용자**: 3단계는 로컬 단일 사용자·소유자 중심이다. 역할·초대·알림은 5단계로 미루고, 화면은 `owner/editor/reader` 자리만 둔다.
8. **모바일**: 3단계는 읽기·답하기·인쇄 미리보기만. 편집·첨언 작성은 데스크톱 우선.
